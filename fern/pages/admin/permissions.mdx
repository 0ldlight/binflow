# 用户、组与权限

权限模型分三层，各归其位：

| 层 | 承载 | 决定什么 |
|---|---|---|
| **角色**（users 行，闭集三值） | `adminRole` | 管理面（仓库/用户/组/权限/审计/GC/复制/配额）能看什么、能改什么 |
| **permission target 的 `manage` 动作** | target principals | 仓库级管理员——谁能管某个仓的配置与权限下放 |
| **permission target 的 `read/write/delete`** | target principals | 内容面——谁能读写删哪个仓的哪些路径 |

模型与 Artifactory 一致（术语不变）：permission target = `{name, repos[], includePatterns[], excludePatterns[], principals{users, groups}}`，动作 `read / write / delete / manage`；**excludes 优先**；admin 隐式拥有全部权限（不进矩阵）。

## 三步授权流（组 → 用户入组 → target）

```bash
export BASE=http://localhost:8080
export ADMIN_PW=<你的管理员口令>

# 1. 建组（创建 201；已存在为更新 200）
curl -su admin:$ADMIN_PW -X PUT $BASE/binflow/api/security/groups/devs \
  -H 'Content-Type: application/json' \
  -d '{"name":"devs","description":"开发组"}' -o /dev/null -w '%{http_code}\n'   # 201

# 2. 建用户并入组（email 必填；groups 引用不存在的组 → 400）
curl -su admin:$ADMIN_PW -X PUT $BASE/binflow/api/security/users/jane \
  -H 'Content-Type: application/json' \
  -d '{"name":"jane","password":"<jane口令>","email":"jane@example.com","groups":["devs"]}' \
  -o /dev/null -w '%{http_code}\n'                                                # 201

# 3. 建 permission target
curl -su admin:$ADMIN_PW -X POST $BASE/binflow/api/v1/permissions \
  -H 'Content-Type: application/json' \
  -d '{"name":"devs-rw","repos":["generic-local"],"includePatterns":["devs/**"],
       "principals":{"users":{},"groups":{"devs":["read","write"]}}}' \
  -o /dev/null -w '%{http_code}\n'                                                # 201
```

验证：jane（devs 成员，无直接授权）可写 `devs/**`（201），删除 403（组没给 delete），写 `other/**` 403（不在模式内）。

**并集与即时生效**：有效权限 = 用户直接授予 ∪ 所属各组授予，**逐请求现算**——移出组下一次请求即生效，无重启无窗口：

```bash
curl -su admin:$ADMIN_PW -X POST $BASE/binflow/api/security/users/jane \
  -H 'Content-Type: application/json' -d '{"groups":[]}' -o /dev/null   # 清空组（缺 groups 字段则不动）
# 此刻起 jane 对 devs/** 的写立即 403
```

## 组管理 API（admin only）

错误体为用户管理族**纯文本**（非 JSON 信封）。组名规则 `[a-z][a-z0-9._-]*`；保留字 `anonymous` / `_system_` → 400。

| 操作 | 请求 | 行为 |
|---|---|---|
| 列组 / 查单组 | `GET /api/security/groups[/{name}]` | `{name, uri, description}`；不存在 404 |
| 建组/更新 | `PUT /api/security/groups/{name}` | 创建 **201 无 body** / 已存在 **200 更新**（脚本请以状态码区分） |
| 改描述 | `POST /api/security/groups/{name}` | 200 |
| 删除 | `DELETE /api/security/groups/{name}` | 200 纯文本；**被 permission target 引用 → 409** 并列出引用方 |
| 组员花名册 | `GET /api/security/groups/{name}?includeUsers=true` | 附 `userNames: []`（空组 `[]` 恒非 null）；其余拼法回无参形态 |

## 用户管理 API

| 操作 | 请求 | 行为 |
|---|---|---|
| 建用户/替换 | `PUT /api/security/users/{name}` | create-or-replace，两态皆 **201**；`email` 必填（缺省 400）；`groups` 引用未知组 → 400 |
| 部分更新 | `POST /api/security/users/{name}` | 指针字段：`"groups":[]` 清成员、缺 `groups` 不动；`enabled` 同为指针字段（显式 `false` 禁用登录） |
| 用户详情 | `GET /api/security/users/{name}` | `{name, email, admin, adminRole, enabled, groups, realm, ...}`——**无口令字段** |
| 用户列表 | `GET /api/security/users` | 条目含 `email/adminRole/enabled/groups`（恒渲染，单请求即含列表所需全部字段） |
| 删除 | `DELETE /api/security/users/{name}` | admin only；护栏 + 级联见[治理 · 删除用户](/admin/governance) |
| 改密 | `PUT /api/security/password`（自己）；`POST users/{name}` 带 `password`（admin 改他人） | — |

**人员离场的既定路径是禁用**（`{"enabled":false}`，可逆可审计），不是删除。

## 角色三值模型（adminRole）

角色是**闭集**三值（snake 形，仅 admin 可写；不存在自定义角色/继承）：

| 角色 | 语义 |
|---|---|
| `user`（缺省） | 管理面全拒，内容面走 permission targets |
| `readonly_admin` | 管理读面全通、一切变更面 403；**数据面全域只读**（角色短路） |
| `admin` | 全权（≡ `admin` 布尔；`admin=true ⇔ adminRole=admin` 两写法等价，矛盾同传 → 400） |

**readonly_admin 短路语义（重要）**：readonly_admin 的内容面与仓库域求值**不查 permission targets**——target 行对其无任何效果。把它加进带 write 的组**不会**让他能写：组合结果是**静默无效**，不是报错。这是有意设计（安全不变量：「只读管理员还能删」的矛盾配置在求值层被结构性排除）。readonly_admin 管理读面含：仓库列表/单查、health、users/groups、permissions、audit、replications/status、storage stats。

```bash
# 分配（建号即带角色；部分更新臂同形）
curl -su admin:$ADMIN_PW -X PUT $BASE/binflow/api/security/users/alice \
  -H 'Content-Type: application/json' \
  -d '{"name":"alice","email":"alice@t.io","password":"<alice口令>","adminRole":"readonly_admin"}' \
  -o /dev/null -w '%{http_code}\n'          # 201
```

**角色变更对该用户的存量 Token 即时生效**（无重启、无需换发 token）；每次变更记审计 `user.role.change`（detail 含 user/old/new）。非 admin（含 readonly_admin）写任何用户的角色字段 → 403。

**组不带角色**：角色只在用户行，组 principals 永远不能授予 admin 或角色（防「建个组把自己提权」）。

## 仓库级管理员：manage 动作

给组或用户授 `manage` + target 命中某仓 = 该主体成为**这些仓的仓库级管理员**。`manage` 的 target 匹配**只看 `repos[]`**——includes/excludes 不参与。

```bash
# 建 target：app-admins 组对 app-local 全权 + manage
curl -su admin:$ADMIN_PW -X POST $BASE/binflow/api/v1/permissions \
  -H 'Content-Type: application/json' \
  -d '{"name":"t-app","repos":["app-local"],"includePatterns":["**"],
       "principals":{"users":{},"groups":{"app-admins":["read","write","delete","manage"]}}}' \
  -o /dev/null -w '%{http_code}\n'       # 201
# 此后 app-admins 成员可编辑覆盖集内的 target（如给他人开只读），无需平台 admin
```

> permission target 的编辑臂是 **`POST /api/v1/permissions`（create-or-replace，201）**——没有 `PUT /api/v1/permissions/{name}` 路由（404）。删除为 `DELETE /api/v1/permissions/{name}`（204）。

**覆盖集规则**：manage 持有者可编辑的 target 须满足 `target 的 repositories ⊆ 其 manage 覆盖仓集`。越界 → 403；部分交集同样 403；同名替换判定取 **body ∪ 存量 target 的 repos** 的并集（防「换壳吊销他人在越界仓上的既有授权」）；DELETE 臂同理。

| 能（覆盖集内） | 不能（全部 403） |
|---|---|
| 读单仓配置 `GET /api/repositories/{key}` | **建仓**与**删仓**——全局 admin-only |
| 编辑仓配置/配额 | 全局仓库列表 `GET /api/repositories`（无 filter） |
| 编辑 ⊆ 覆盖集的 permission target | 用户/组/角色写、token 吊销、GC（含 dry-run）、复制写 |
| `GET /api/v1/permissions?filter=manage`（自己可编辑的 target 子集，字段与全量一致；未知 filter 值 400） | — |
| 读配额用量 `GET /api/v1/storage/usage/{repo}` 与批量端点 | — |

**`manage` 不是数据面权限**：不隐含 read/write/delete——制品读写仍需显式授予。manage 永不进入 docker token 的 scope 词表。

## 有效权限视图：?permissions

```bash
curl -su admin:$ADMIN_PW "$BASE/binflow/api/storage/generic-local/devs/w.bin?permissions"
# {"uri":"...","principals":{"users":{},"groups":{"devs":["r","w"]}}}
```

key = 主体名，value = 权限字母集（r/w/d/m）。admin only，仅 local 仓（virtual/remote → 400）；无任何权限的主体不出现。

## OIDC / LDAP 的组映射

联邦用户每次登录由 IdP 权威重写角色，本地手改会被下次登录覆盖。求值阶梯：`admin_group` 命中 → `admin` **>** `readonly_group` 命中 → `readonly_admin` **>** 其余 → `user`。

| 键 | 值 |
|---|---|
| `auth.oidc.<provider>.admin_group` / `readonly_group` | 组 claim 值 |
| `auth.ldap.admin_group` / `readonly_group` | 组 **DN** |

配置全解见[认证（LDAP / OIDC / SAML）](/admin/auth)。

## 有意不兼容

| 项 | BinFlow 行为 |
|---|---|
| **组无 admin 位** | 组不能授予 admin 或角色；admin 组成员的非 admin 用户对管理面仍是 403（有意设计，防组内自提权） |
| `PUT groups` 已存在 → 200 | 创建 201 / 更新 200 分态（脚本以状态码区分） |
| `PUT users` 已存在 → 201（create-or-replace） | replace 覆盖全部字段；未提供的字段不保留旧值 |
| `/api/v2/security/permissions/**` | **404**——权限面是 `/api/v1/permissions` |

## 常见报错对照

| 症状 | 原因 | 处置 |
|---|---|---|
| 400 `Unable to find group by name 'nope'.` | 写入引用了不存在的组 | 先建组再入组（三步流顺序） |
| 409 `Cannot delete group 'devs': it is referenced by ...` | 组仍被 target 引用 | 先删/改引用方 target |
| 400 `conflicting 'admin' and 'adminRole' fields: ...` | 两写法矛盾 | 二选一（`admin=true` 等价 `adminRole=admin`） |
| 400 `unknown adminRole "..."` | 值拼错（如 kebab 形） | 值用 snake 形三闭集 |
| 403（readonly_admin 的一切写操作） | 角色设计如此（含 GC dry-run） | 需要变更能力 → 提升 admin |
| 403（manage 持有者建仓/删仓/编辑越界 target） | 建/删仓与越界不下放 | 由平台 admin 操作 |
| readonly_admin 被授了 write 却不能写 | 角色短路（组合静默无效） | 写需求 → user 角色 + target |
