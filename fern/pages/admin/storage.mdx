# 存储后端（磁盘 / S3 / 双写）

BinFlow 的 blob 引擎可在**本地磁盘**（默认）与 **S3 兼容对象存储**（AWS S3、MinIO 等）之间选择；元数据仍在本机（SQLite），切后端不迁移元数据。存储链有两种配置形态：内嵌 `storage:` 段（binflow.yaml）与独立的 **`binstore.yaml`** 链文件（新部署推荐）。

## binstore.yaml（独立存储链文件）

与**实际生效的主配置文件同目录**（跟随 `-c` 解析序）；文件缺席 = 零行为变化。

```yaml
# binstore.yaml —— 与 binflow.yaml 同目录
version: 1                  # 可选；出现必须为 1
chain:                      # 有序 provider 链，声明序即链序
  - type: filestore         # 本地盘 provider（无参数）
  - type: s3                # 参数 = 内嵌 storage.s3 键族平移：
    bucket: my-bucket
    region: us-east-1
    endpoint: http://minio.local:9000
    access_key_id: minioadmin
    # use_path_style / upload_part_size / upload_concurrency / bucket_prefix 同内嵌拼写
    # secret_access_key 永远不进文件 —— 只认 env（见下）
migration:                  # 仅 [filestore, s3] 双员链合法且必填
  mode: dual-write          # 闭集 bypass | dual-write | completed
  concurrency: 5
```

| 链 | 语义 |
|---|---|
| `[filestore]` | 本地盘 |
| `[s3]` | 纯 S3（含迁移完成后的终态） |
| `[filestore, s3]` + mode | `bypass`=仅 disk；`dual-write`=双写 + 读 S3 先磁盘兜底 + 后台拷贝；`completed`=S3 单写 |

保留名 `cache-fs` / `azure` / `gs`：出现即**拒启**（保留位未实现，不静默忽略）。

### 与内嵌链键的并存裁决

| 分支 | 形态 | 行为 |
|---|---|---|
| ① | 无 binstore.yaml + 内嵌链键显式设置 | 照常启动 + 每次启动 WARN（迁移提示） |
| ② | binstore.yaml 在 + 内嵌链键缺席/全默认 | 文件生效，静默 |
| ③ | 两者**语义等价**（归一化后同链同参） | 文件生效 + WARN |
| ③′ | 两者**语义分歧**（会装配出不同的链） | **拒启**——错误指明两处来源与分歧键 |

注意：显式拼写默认值也算「显式」——`backend: disk` + binstore 声明 `[s3]` → 分歧拒启。

### 凭据纪律

- **明文 secret 恒拒启**：全文件递归扫描，`secret_access_key` 出现 → 拒启 + 行号 + env 逃生口。S3 secret 只认 `BINFLOW_STORAGE_S3_SECRET_ACCESS_KEY`，恒注入生效链的 S3 provider。
- binstore.yaml 生效时，链相关 env 覆盖键（`BINFLOW_STORAGE__BACKEND` 等）**忽略 + WARN**（secret env 例外）。
- 文件权限宽于 0600 → 启动 WARN（卫生建议）。
- 拒启错误一律含**绝对路径 + 行号 + 违规键名**（YAML 语法错 / 明文 secret / 保留名 provider / 双源分歧四形态）。

## 内嵌 S3 配置（storage 段）

```yaml
storage:
  backend: s3
  data_dir: /var/lib/binflow        # 迁移期与元数据仍用它
  s3:
    bucket: binflow                 # 桶必须已存在——BinFlow 不建桶
    region: us-east-1
    endpoint: https://s3.amazonaws.com   # MinIO 用 http://minio:9000 + use_path_style: true
    access_key_id: AKIA...
    use_path_style: false           # MinIO/自建 true；AWS 虚拟主机风格 false
    # bucket_prefix / upload_part_size（5MiB）/ upload_concurrency（4）可选
```

| 键 | 必填（backend=s3） | 说明 |
|---|---|---|
| `storage.s3.bucket` | 是 | 桶不存在则启动拒绝（BucketExists 预检） |
| `storage.s3.region` / `endpoint` / `access_key_id` | 是 | endpoint 带 scheme：`http://` 明文、`https://`/无 scheme TLS |
| `storage.s3.secret_access_key` | 是 | **仅 env**：`BINFLOW_STORAGE_S3_SECRET_ACCESS_KEY`（唯一单下划线特例） |

env 覆盖（双下划线映射）：`BINFLOW_STORAGE__BACKEND=s3`、`BINFLOW_STORAGE__S3__BUCKET=...` 等。

验证：启动日志 `s3 storage backend active bucket=...`；`/healthz` 与 `/readyz` 的 storage 子系统对 S3 做 **HeadBucket → PutObject（哨兵）→ DeleteObject** 三连，全过才算 ok。

## docker-compose（--profile s3）

自带 MinIO + 一次性建桶任务：

```bash
cp deploy/compose/.env.example deploy/compose/.env
# .env 设置：MINIO_ROOT_PASSWORD / BINFLOW_STORAGE__BACKEND=s3 /
#           BINFLOW_STORAGE_S3_SECRET_ACCESS_KEY（同 MINIO_ROOT_PASSWORD）/ BINFLOW_ADMIN_PASSWORD
docker compose -f deploy/compose/docker-compose.yml --profile s3 up -d --build
```

默认桶名 `binflow`；MinIO 控制台在 `127.0.0.1:9001`；对象在 `minio-data` 卷。

## 本地 → S3 在线迁移

三段式：**双写 → 后台搬 → 收口单写**，全程服务在线：

```yaml
storage:
  backend: s3
  data_dir: /var/lib/binflow       # 磁盘侧原地保留
  s3: { ... }
  migration:
    enabled: true                  # 双写：写双份、读 S3 优先回落磁盘、删双删、GC 双侧
    completed: false               # 迁移收尾后手工改 true
    concurrency: 5
```

```bash
# 启动后台搬运（admin；幂等——运行中再调返回当前进度）
curl -su admin:$PW -X POST $BASE/binflow/api/v1/storage/migration/start
# {"running":true,"total":927,"migrated":0,...}

# 进度（total 是本轮待搬数，不是全量 blob 数；已在 S3 的记 skipped；重启后重扫，断点天然安全）
curl -su admin:$PW $BASE/binflow/api/v1/storage/migration
# {"running":false,"done":true,"total":927,"migrated":925,"skipped":2,"failed":0,...}
```

收尾三步：`done:true` 且 `failed:0` → 把 `migration.completed: true` 写进 binflow.yaml（**手工改配置**，无端点代改）重启 → 日志出现 `storage migration completed; s3 is the source of truth` → 磁盘侧 `blobs/` 退役前先备份再清。

约束：`migration.enabled: true` 必须同时 `backend: s3`（否则拒启）；迁移期磁盘空间只增不减；失败项重跑 start 时重扫重试。

## dual-write 停机窗 fail-open

`[filestore, s3] + mode: dual-write` 链在 **S3 停机/故障窗内**：

| 面 | 停机窗内行为 |
|---|---|
| 写（PUT/MPU 分片/remote 落盘） | **本地优先落盘成功** + 内容入重放队列 `<data>/replay-queue/<sha256>.json`（per-sha 幂等；重启幸存） |
| 读（GET/HEAD/Stat） | **回退读磁盘**——disk 恒为超集（迁移方向 disk→S3 且 disk 副本不自动删），读己之写保持 |
| 治理面（GC/Delete） | **诚实失败**——fail-open 只覆盖数据面 |
| 开窗判定 | 进程内断路器：S3 臂任一操作失败即开窗；S3 正常应答的 miss（迁移滞后）不开窗 |
| 恢复 | 首个成功拷贝关窗 → 立即排空队列 → 存在性对账（≤3 轮收敛兜底孤儿 blob） |

- **S3 桶是引擎私有物**：带外直读会看到旧集合（滞后量 = 窗口 + 排空时长）。
- **`mode: completed` 且 replay-queue 非空 → 拒启**（防「声明迁移完成但数据没到」）——切回 dual-write 排空，或确认可弃后删目录。
- 观察窗：`/metrics` 的 `binflow_replay_*` 族（`queue_depth` / `window_open` / `drained_total` / `read_fallback_total` 等）。

## 常见报错对照

| 症状 | 原因 | 处置 |
|---|---|---|
| 拒启 `looks like a secret` | 文件里写了 `secret_access_key` | 移到 `BINFLOW_STORAGE_S3_SECRET_ACCESS_KEY` |
| 拒启 `would assemble differently` | binstore.yaml 与内嵌链键分歧 | 对齐两文件或删内嵌链键 |
| 拒启 `reserved slot` | `cache-fs`/`azure`/`gs` | 从链中移除 |
| 每启 WARN `compatibility window` | 还在用内嵌链键 | 搬迁到 binstore.yaml 收口 |
| 启动报 `s3 ... bucket does not exist` | 桶未预建 | 先建桶（compose minio-init / `mc mb`） |
| `/readyz` 503 + `s3 PutObject ...` | 键无写权限 / endpoint 拼错 | 核对 access key 权限与 scheme |
| dual-write 下 S3 故障期 PUT/GET 仍 200 | fail-open 行为（本地优先 + 队列重放） | 无需处置；看 `binflow_replay_*` 指标等自动排空 |
| 拒启 `completed` + replay queue 非空 | 切了 completed 但停机窗置的债未排 | 切回 dual-write 排空，或确认弃队列后删目录 |
