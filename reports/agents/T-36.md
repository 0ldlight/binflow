## 一、设计定案

**落点是 PUT 端推断存储，不是 GET 端响应时猜测。** 两个协议事实支撑：

1. `curl -T x.json` **完全不发 Content-Type 头**（curl 8.7.1 实测：`nc -l` 抓包，PUT 请求头仅 Host/UA/Accept/Content-Length；显式 `-H 'Content-Type:'` 清空亦同）。PRD 验收命令正是 `curl -T` 上传 + `curl -TI` 查询——若只在 GET/HEAD 响应时推断，PUT 的 FileInfo `mimeType` 字段与存储值会失一致。推断在 PUT 落盘进 `node.Mime`（唯一事实源），下载头、FileInfo、/api/storage 全部自动一致（真栈已证：三者对 x.json 均为 application/json）。
2. 客户端声明优先、逐字保留：声明 `application/x-custom-thing` 上传 .json 文件，GET 仍回该值（真栈验证）。映射只填空缺，绝不覆盖。

**推断链**：BinFlow 自有兜底表（18 项）→ 标准库 `mime.TypeByExtension`（builtin 表 + OS 数据库，覆盖 png/pdf/svg 等）→ `application/octet-stream`。自有表**优先**于标准库：`mime.TypeByExtension` 会查 OS mime 数据库，裸 linux 容器与 macOS 对同一扩展名可能返回不同值（本机 darwin 实测 .yml/.md/.sha1 为空），自有表在前保证跨主机确定性。

**映射表**（值出处）：json/xml/txt/csv/html/md（RFC 拼写，md 带 charset）/yml+yaml（RFC 9512 `application/yaml`）/gz+tgz（RFC 6713）/zip/tar/jar+war/sha1+sha256+md5（config-formats.md §3 高置信度，application/x-checksum）。~18 项，满足票面 ~15 项。

## 五、真实客户端验证（curl = generic 协议指定客户端）

真栈（HEAD+本票构建的 `binflow-server serve`，127.0.0.1:18236，sqlite+本地目录）：

1. **PRD §6.4 验收原样场景**：`curl -T x.json`（无 CT 头）→ 201；`curl -I .../x.json` → `Content-Type: application/json`（GET 同）。
2. **全表 14 扩展名 curl 实测**：xml→application/xml、txt→text/plain; charset=utf-8、yml/yaml→application/yaml、md→text/markdown; charset=utf-8、tgz/gz→application/gzip、zip→application/zip、jar/war→application/java-archive、tar→application/x-tar、csv→text/csv; charset=utf-8、html→text/html; charset=utf-8、sha1→application/x-checksum，全部与映射表一致。
3. **回退不变**：unknown.zzz 与无扩展名（Dockerfile）→ application/octet-stream。
4. **声明优先**：`-H 'Content-Type: application/x-custom-thing'` 传 .json → GET 回 application/x-custom-thing。
5. **一致性**：/api/storage/gen/x.json `mimeType: application/json`、unknown.zzz `application/octet-stream`；大小写不敏感（UP.JSON → application/json）。

以上均已沉淀为自动化用例（mime_test.go 表驱动 + curl_test.go 黑盒），非一次性手工验证。
