## 2. 核心发现（批删 207 状态机的真实形态）

- **207 只属于批删**：批建（PUT）= 全有或全无（任一失败整单 400 + 已建项回滚，实测 dupe 批内新 key 未落地）；批改（POST）= 分阶段 400/403/404（整单无副作用）；批删（DELETE）才是逐仓独立聚合。
- **批删聚合的怪癖族**（全部活体实锤）：不存在键 → `success:true` + `statusMsg="Cannot delete repository: 'x', repository config does not exist"`；并发中删（官方 202 语义）→ 批内同样 `success:true`；因此**全 ghost 批、真删+ghost 混合批均返回 200 "All repositories were removed successfully"**——只有「逐仓真失败」才触发 207 "Some repositories failed to be removed"。
- **预校验失败=整单中止**：非 admin / trash 键 / 导入中等预校验失败不进逐仓段，返回单报告 `{"statusMessage":"<该仓消息>"}`（无 reports 键），状态码 = 该仓码（实测 403 臂逐字）。
- **批改 = ADR-0050 merge 方言的批量面**：省略字段保留存量（实测只发 `xrayIndex:true` 的仓 description 原值保留）——BinFlow 实现可直接复用 update-merge 底座。
- **v2 读的字段集是 v1 的「公共字段投影 + rclass→type 改名」**；非 admin 只见 5 键；类型协商输入是请求 **Content-Type** 而非 Accept（GET 带 Remote vendor CT 对 local 仓 → 406）。
- **批读（GET batch?names=）的值是 v1 全量 schema**（含 rclass，61/61 键与单仓读一致），不是 v2 子集——三个「读」端点三种 schema。
