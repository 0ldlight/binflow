## 一、做了什么

M1 观察项 O1（T-19-qa 报告）：慢上传被客户端中断时，generic 上传 handler 的错误收卷分支以 500 + ERROR 结束该请求的日志——客户端可见行为完全正确（路径 404、blob 不计、session 即清），但日志语义上无法与「真 5xx 故障」区分，QA 的 5xx 计数被 aborted upload 污染。

本票在 **middleware 层**（accessLog + statusRecorder + recoverPanic）实现「日志标注案」（票面暂行口径：不引入 499 状态码，对外响应形态不变）：

### 1. statusRecorder 记录写路径首错

`Write()` 返回的错误（broken pipe / connection reset）记入 `writeErr` 槽位（首错即定格）；`recoverPanic` 的断连分支把 panic 值也经 `panicDisconnect` 槽位向外传（context 只能向内流，recorder 是两层共享的唯一可变缝）。

### 2. accessLog 分类器与降级

```
level := INFO; status >= 500 → ERROR（M1 起补齐——原先 5xx 也是 INFO）
status >= 500 && isClientDisconnect(ctx.Err(), writeErr|panicDisconnect)
  → WARN + client_disconnect=true + disconnect_reason=<classifier>
```

`isClientDisconnect` 两腿判定（探针实证，见下）：
- **主腿**：`r.Context().Err() == context.Canceled`。net/http 在连接关闭即刻取消请求 context，FIN 与 RST 两种关闭方式在 handler 返回时刻均可观测到；正常完成请求该时刻 ctx 为 nil，不误伤。
- **兜底腿**：写路径 broken-pipe 类错误（`EPIPE`/`ECONNRESET`/`http.ErrAbortHandler`，sentinel/errno 匹配，绝不做消息文本匹配）。darwin 上首次写常被内核缓冲（错误不一定浮出），此腿覆盖 context 腿未及的场合。

`DeadlineExceeded` **不算断连**（服务端超时，客户端可能仍在线）→ 维持 ERROR（AC3 三态之 deadline 态）。

### 3. recoverPanic 断连降级

panic 值（或 recorder 上的写错误）为断连类 → WARN + `client_disconnect=true`，**不注入信封**（字节本来就无法投递）。确认：断连场景按定义已有字节上线 → 必然走 T-14 既有 `committed()` 分支的「只记日志 + markStatus + 截断」路径，本票把该分支的日志级别同步降级并把 panic 值外传给 accessLog 分类器（AC1 的 recover 子句）。普通 panic（非断连）维持 ERROR + 信封 500，行为不变。

### 4. generic 与 docker 域同一生效

降级位于 middleware 链（requestID → accessLog → recover），`/binflow/**` 与 `/v2/**` 共用同一链（ADR-0010 第 1 条），零 adapter 改动。测试双向断言。

## 二、实现前探针（代码不落地证据，判定面据此选定）

临时探针程序（/tmp，已清理）验证三点：

1. **FIN 关闭**（graceful Close）：handler 内 body read 得 `unexpected EOF`；access-log 时刻 `ctx.Err() == context.Canceled`。
2. **RST 关闭**（SO_LINGER 0，kill -9 类比）：read 得 `ECONNRESET`；access-log 时刻 `ctx.Err() == context.Canceled`。
3. **正常完成**：客户端读走完整响应再关闭，access-log 时刻 `ctx.Err() == nil`（不误伤的根据）。
4. darwin 上断连后**首次 Write 常返回 nil**（内核缓冲）——写路径错误不可靠，故只作兜底腿。

结论：主判定信号 = context.Canceled（两关闭方式均可靠），兜底 = 写路径 errno。

## 六、设计取舍与说明

1. **「不进 5xx ERROR 计数」的实现载体**：M1 无 metrics 面（M5 才有 Prometheus），「计数」的现行语义即日志级别（T-19 QA 的 5xx 统计口径就是 grep 服务日志）。故降级 = 级别降为 WARN + 标注字段；将来 metrics 落地时以 `client_disconnect` label 为同一分界（遗留项）。
2. **status 字段保留 500**：日志行仍记 `status=500`（与 T-14 的「日志须暴露失败，不镜像 transport」语义一致——收卷分支确实调了 WriteHeader(500)），分界靠 `client_disconnect=true` 标注而非改状态码。票面两案取一的「日志标注案」。
3. **M1 行为变化点（有意）**：accessLog 对 ≥500 从 INFO 升为 ERROR 基线（原先所有请求一律 INFO）。这是本票 AC 的前提（「不进 5xx ERROR 计数」隐含 5xx 平时计入 ERROR），也让 `TestV2RepoLookupFailureIs500`（T-33）等「真 500 须 ERROR」的语义有了日志面落点。T-14 既有断言只查字段不查级别，零冲突。
4. **DeadlineExceeded 不降级**：服务端超时不是客户端断连（客户端可能仍在等），保持 ERROR——AC3 三态明确要求。
5. **firstErr 优先级**：活写错误 > panic 标记（reason 字段应指向驱动分类的那个错误）。
6. **无新依赖**：syscall 标准库 errno sentinel（EPIPE/ECONNRESET）跨平台（linux/darwin/windows 均导出）。

## 七、遗留 / 需上游确认

1. **M5 metrics**：`client_disconnect` 需要从日志字段升格为 metric label（本票日志面先行，票面范围外）。
2. **docker 域 blob 上传端点级验证**归 T-38（端点落地后 QA T-43 复验 D 序列时 middleware 降级自动生效）；本票以同链 `/v2` 路径驱动 + 全栈 generic 域双向覆盖。
3. `disconnect_reason` 的 `write_failed` 兜底值理论上不可达（isClientDisconnect 通过后才走到），保守保留。
4. 观察项：QA 若以 `grep -c 'status=5'`（而非 level）统计 5xx，断连行仍计入——口径须按「level=ERROR」或「client_disconnect 排除」表述（T-43 派单时建议注明；PRD §6.4 O1 的验收措辞已是「不出现 5xx 级 ERROR 计数」，与实现一致）。
