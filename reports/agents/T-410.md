# T-410 — FR-139.1 mint unknown username 400 修正（断言反转③）

状态: done ｜ role: dev-go-core ｜ area: internal/httpapi auth 域（mint handler）＋ web/e2e 断言反转③随票 ｜ 2026-09-01

## 根因

`POST /api/security/token` 带 `username=<不存在>` 答 500 的链路：

- `internal/auth/token.go:170-172`（`Service.issue`）对 subject 查找失败仅
  `fmt.Errorf("auth: token subject lookup: %w", err)` wrap `metadata.ErrUserNotFound`——
  链上**没有** `auth.ErrInvalidCredentials` 哨兵（语义上也不该有：没有任何凭据被拒绝，
  `ErrInvalidCredentials` 按 api.go 注释是「凭据被呈递且被拒」）。
- `internal/httpapi/security.go` `handleTokenCreate` 的 Issue 错误分支只收编
  `errors.Is(err, auth.ErrInvalidCredentials)`（该臂原本只覆盖 `invalidf` 的空 subject
  ——`invalidf` 会 wrap `ErrInvalidCredentials`），unknown 臂落入 500 兜底。

## 修复（最小面，handler 侧分类收编）

- **internal/httpapi/security.go**：Issue 错误分支的分类条件扩为
  `errors.Is(err, auth.ErrInvalidCredentials) || errors.Is(err, metadata.ErrUserNotFound)`
  → 400 `invalid_request`「username is required or unknown」。wrap 语义不变（服务层
  错误链原样保留，仅 HTTP seam 分类），`internal/auth` **零改动**（票面「必要时最小改」
  的必要性未成立）。
- **internal/httpapi/security_test.go**：新增 table-driven
  `TestTokenCreateUnknownSubject`（4 腿：form unknown→400 逐字文案 / JSON 投影同臂 /
  **非 admin 点名任意主体维持 403 守卫**——防枚举次序锚：403 先于 subject 解析，
  400 永不成为非 admin 的用户名探针 / 既有主体代人铸造回归 200）＋ 断言 operator log
  无 "token issue failed"（防再次滑回 500 分支）。
- **web/e2e/m14/t386-tokens-page.spec.ts**（断言反转③，PRD M15 §5.4 归属本票）：
  T-386 当时按 as-built 钉的 `HTTP 500` + `token creation failed` 断言反转为
  `HTTP 400` + `username is required or unknown`；注释由「契约漂移登记」改写为
  归位说明。FE 代码零改动（错误面板 `签发失败（HTTP {status}）：{message}` 经
  `oauthErrorOf` 取 `error_description` 逐字——语义不劣化）。

## 规格依据

- `docs/reverse/auth-model.md` §3.1：unknown 主体属 `invalid_request` 400 臂；基础文案
  `username is required`（`TokenUtils#requireUsername`，缺省臂）。真实 Artifactory 对
  不存在用户走 **transient 用户创建**（需配组 scope）——BinFlow token 面不建模该形态，
  故「or unknown」扩展臂按 PRD M15 FR-139.1 登记（milestone-15.md §4.8：
  「400『username is required or unknown』（auth-model 3.1）」）采用组合文案，
  与 handler 既有空 subject 臂文案一致（置信度：高——错误码/HTTP/文案三源一致）。
- 防枚举核对：FR-23-AC5 的统一 401 只辖**登录面**（failure.go 文件注释）；mint 面的
  unknown-user(400) 与 bad-password(401) 可区分性仅存在于**已认证且持
  security:write 能力的调用者**（本就可全量 GET /api/security/users），且非 admin 点名
  他人一律 403 先行——无泄漏面。

   弹口令表单而非明文面板）——unarmed 实例该腿过。属 spec 的实例假设面（写就于默认

   实例纳入常规回归需给该腿加 armed 分支或探针 skip。

   配置在 :8080/`./data`（用户实例目录）启动约 2 秒即被杀——日志显示仅完成启动会话
   清扫（按 TTL 清过期 session 行，无害维护）；无写入面接触。之后改用 Write 工具写配置。
3. `internal/auth` 未改动：服务层补哨兵的替代方案（wrap ErrInvalidCredentials）被否——
   会把「subject 不存在」塞进「凭据被拒」语义，且 handler 侧分类已足够（错误链忠实保留）。
