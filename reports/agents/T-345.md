## 1. 设计

### 1.1 存储布局与打标（AC1）

- **内置仓**：`auto-trashcan`（local/generic，Artifactory 拼写）。**懒落库**：首次捕获时经 `md.Repos().Create` 直写（不走 CreateRepo——内置仓是装配数据：无校验门/无审计行/无权限主体），per-service 原子标记记忆化。
- **布局**：捕获节点落 `auto-trashcan/<原仓key>/<原节点path>`——路径本身结构性编码出处；属性冗余逐节点标记（任一子树节点可独立恢复）。
- **属性五元组**（storage-layout.md §5 高置信全集；PRD 四元组 + originalRepositoryType）：`trash.time`（epoch ms）/ `trash.deletedBy` / `trash.originalRepository` / `trash.originalRepositoryType`（恒 "local"）/ `trash.originalPath`（**本节点**的原路径）。经 `NodeProps().Merge` 逐节点落。
- **捕获路径**：`service.Delete` 的 local 臂、权限门之后、任何源行删除**之前**插入 `captureIntoTrash`：以 `_system_` 身份 + `SystemIdentity` + `ExactPath` 跑 `CopyOrMove(OpCopy)`（FR-105.5「删除 = move to auto-trashcan」的 BinFlow 拼法：copy + 源删除留给 Delete 既有臂——错误面与 M11 逐字节一致）。**捕获失败即中止删除**（fail-closed：宁可留活不可丢失）。逐项 error（部分捕获）同样中止。
- **跳过集**（本地生成物不入站，anchor：repo-operations.md §1.4 exclude.local.generated 中置信 + T-343 explode 排除先例）：`.jfrog/**`（与 SystemInternalPathPrefixes 单源）/ `dists/**`（deb 索引引擎输出）/ 任一段 `repodata` 或首段 `_tmp_*`（rpm 索引与暂存）/ `maven-metadata.xml[.sha1…]`（maven 元数据族）。其余（含全部协议制品路径）入站。**登记分歧**：Artifactory 的排除骑在 repo-layout 元数据上，BinFlow 无此层，闭集是自有拼写。
- 不捕获面（登记）：remote 缓存失效（RE-06 语义是逐缓存非制品删除）/ DeleteRepo(deleteContent) 仓拆除（管理面）/ docker DeleteManifest（需 manifest/tag/refs 索引恢复语义，见 §5 遗留）。

### 1.2 `_system_` 内部身份裁定（T-339/T-343 遗留汇聚）

- **契约落定**：`repo.SystemPrincipal()` 返回 `&auth.Principal{Name:"_system_", Role:RoleAdmin, Admin:true}`——身份即豁免（allow() 的角色短路，从不咨询 Authorizer，不是一条授权）。`_system_` 名在用户面保留（httpapi 既有保留名集），审计行/属性带此名不可能与人混淆。
- **CopyMoveRequest 两面内部旗**：`SystemIdentity`（§1.2 的 remote/virtual 目标豁免 + **内部跑不触发 CopyMoveObserver**——系统仓内容不喂任何协议索引）与 `ExactPath`（**本票新增**：目标逐字寻址，跳过 §1.4 unix 进目录/改名臂）。两者均**仅进程内缝，REST 面永不置位**（注释钉死）。
- **ExactPath 的动因**（实现期发现）：捕获/恢复需要 verbatim 布局，而 unix 语义下「目标缺失 = 改名」（folder 捕获会把 `app/` 改名为 `libs/`）、「目标为已存在目录 = 落其下」（重复捕获会得到 `libs/app/app/`）——两者都会破坏 `<repo>/<path>` 布局。ExactPath 令 tgtRoot = 调用方拼写（folder 补尾斜杠）；已存在文件目标仍走 delete-then-copy 覆盖臂，已存在目录目标仍合并。
- **恢复（AC2）**：`TrashRestore` = 解析 can 内条目（file→folder 探测序同 Delete）→ 目的地三级（`to` 覆盖 > 属性五元组 > 路径结构首段）→ `CopyOrMove(OpMove)` 反向搬（`_system_` + 双旗）→ 落地树**剥除 trash.\* 标记**（属性复原：原属性随行保留，标记不留）→ `trash.restore` 审计（actor=恢复人）。`to` 不允许指向 can 本身（400）；目标仓必须 local（400）；目标仓已删除 → 404。`transaction-size` 解析校验（非正整数 400）、语义惰性（逐项管线，登记分歧）。
- **T-343 遗留③的接续建议**：maven/deb/conan 观察者接线现在有了统一内部身份契约可消费（`repo.SystemPrincipal()`），但适配器侧导出缝仍缺——裁定为**不随本票接线**（area 纪律），建议小票：适配器导出 reindex 缝 + 以 SystemPrincipal 运行 + 照本票豁免先例绕 license 门（见 §5）。

### 1.3 REST 面（AC1/AC2/AC4/AC5）

```
POST   /binflow/api/trash/empty                       清空（整 can）
POST   /binflow/api/trash/restore/{path}?to=&transaction-size=   恢复
DELETE /binflow/api/trash/clean/{path}                单条永久清除
```

- **浏览不设第四路由**：骑既有 storage 面（`GET /api/storage/auto-trashcan[...][?properties|?list]`）——AC1 的四元组断言面即 `?properties`；控制台树节点 = 仓 key 本身（console-ui.md 的 Trash Can 节点）。
- **路由门**：`routeAuth{required, manage: CapSystemWrite}`（gc/cleanup 破坏性管理面姿态：readonly_admin 403、plain user 403、匿名 401；t215 守卫计数 53→56 随表更新）。**license 门** = 处理器首行 `RequireAddon(addonTrashcan)`（weave 3，T-282/283 三缝先例；RBAC 先于 license）。
- **响应形态**（规格未载 body，登记为无据设计）：restore 复用 copy/move 的 `messages[]` + `application/vnd.org.jfrog.artifactory.storage.CopyOrMoveResult+json`（它就是一次 move）；empty/clean 答 `application/json` 摘要 `{removed,files,folders,bytes}`。错误走统一 errors[] 信封 + StatusError 逐字。
- **系统仓守卫**：CreateRepo/UpdateRepo/DeleteRepo 拒 `auto-trashcan`（防抢注/拆除，ErrSystemRepo 400）；内容面 Put/PutFromBlob/PutLandedBlob/Delete 拒写入 can（trash 族是唯一写者，400 指引 REST 族）；virtual 成员校验拒 can（聚合暴露面封死）。读面照常 ACL——无任何 permission target 能点名此 key，只有 admin/readonly_admin 可见（NFR-S61「回收站制品不可匿名读」构造性成立，测试钉死）。

### 1.4 保留期与 GC/cleanup 交互（AC3/AC6）

- **TrashEngine**（TrashGCHelper 的 BinFlow 拼法，CleanupEngine 架构模式复用）：tick 默认 1h；`RunOnce` 走 `trash.time`（epoch ms）判龄，**降级回退 row updated_at**（捕获后、打标前崩溃的裸行也有龄可判——保守删除而非永久滞留）；过期 FILE 行删除 + 无文件子树的 folder 行清除；`trash.retention` 审计（actor `system-trash`，ActorCleanup 先例）。锁门（license locked）或 can 未启用 → skip 报告非错误。
- **不持数据目录锁**（与 cleanup 的差异，注释留痕）：无 gc 腿需要协调——清除产生的孤儿 blob 与普通删除同构，由常态 GC（或 cleanup 的 gc 腿）回收。
- **免疫论证（负向断言钉死）**：① cleanup policy 腿只走 remote 仓（auto-trashcan 是 local，结构性免疫）；② 每个 GC mark 走 `LiveChecksumSet`（含 can 的节点行）——trash 内容 = 引用内容，GC 不可收。测试：捕获后 LiveChecksumSet 含该 blob → 跑真 CleanupEngine RunOnce(apply) → can 行原样 → empty 后 blob 离开 mark 集 + GCSweep(grace=1ms) 真回收。
- **配置**：`ConfigureTrash(svc, TrashConfig{Enabled, RetentionDays})` 装配缝（ConfigureFolderDownload 先例）+ `AttachTrashGate(svc, TrashGate)`（license 缝，PackageTypeGate 先例；nil = 解锁的测试姿态）。**零值 = 关闭**——所有未 opt-in 的栈逐字节保持 M11 硬删（AC6 零回归的构造性保证）。cmd 装配：spec 默认（enabled/14d）+ trashcanGate（注册表+license Manager）+ `go stack.trashEng.Run(ctx)`。config.yaml 字段（trashcan.enabled/retention_days）未落（internal/config 非 area，同 T-343 遗留①模式，见 §5）。

## 4. 差异登记（规格 vs 实现）

1. **响应 body 无规格依据**：restore 复用 CopyOrMoveResult messages[]（含 vendor CT）；empty/clean 用 JSON 摘要。Artifactory 侧 body 形态未见文档/代码证据——登记为无据设计，live 可验后回写。
2. **transaction-size 惰性**：解析+校验（≤0 → 400），BinFlow 逐项管线无批语义可承载（Artifactory 是 SQL 事务批量）。
3. **跳过集为 BinFlow 闭集**（§1.1）——Artifactory 骑 repo-layout 元数据，不可移植。
4. **不捕获面**：remote 缓存失效/DeleteRepo 内容拆除/docker manifest 删除（§1.1；docker 恢复需索引随行，归遗留）。
5. **恢复的覆盖语义**：目标已存在同名文件 → 系统身份过 override 臂 = 覆盖（规格未载 trash 恢复的冲突行为；按 move 族语义推导，测试固化）。
6. **恢复目标缺失仓 → 404**（loadRepoRow 既有映射）；规格未载。
7. **保留期判龄回退 updated_at**（§1.4 崩溃窗裸行）——BinFlow 自有加固，规格未载。
8. **`restoredTime` 未实现**：inv-1 §B 属性集提及（trash.time/deletedBy/originalRepository/originalPath/restoredTime），语义与落点（恢复后的原节点？）无据，低置信不实现，登记待取证。
9. **`allowPermDeletes` / `send.overwrites.to.trashcan` 未实现**：前者 BinFlow 以 clean/empty 承载永久删除；后者需 Put 覆盖臂集成（连带大量测试翻转），登记为后续票候选。
10. **根目录删除 403（storage-layout.md「非 admin 删除仓库根目录被拒」）**：BinFlow 内容面本就拒绝根路径（validateNodePath 400）——更严，维持。
11. **kind 拼写**：PRD 暂定 `feature-gov`，BinFlow addons 无此 kind，落 KindFeature（治理风味在描述里），随 Q3 终裁一并定名。
12. **T-339 勘误顺手修复**：move 汇总动词 `moveing`→`moving`（英文拼写错误非规格选择；copy/move/trash 测试全绿证实无断言依赖）。
