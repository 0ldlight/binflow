## 做了什么

### 1. REST GC 面：POST /binflow/api/v1/system/gc（internal/httpapi/system_gc.go，新文件）

- **body** `{"apply":bool,"graceHours":int?}`（GE-03 / ADR-0015 勘误①）：`apply` 缺省 false = **dry-run 默认姿态**，apply 的确认形态就是「先 dry-run 看报告、再显式 `"apply":true`」两步（ADR-0015 勘误①：dry_run+confirm 双字段形态已废；控制台侧的二次确认归 T-102）。空 body / EOF 容忍为 dry-run；非法 JSON / 类型错 / graceHours 越界（<0 或 >100 年——溢出会被 storage.GC 当作「用默认 grace」静默改义，故显式 400）→ 400 E-01。
- **graceHours 指针语义**：缺省 → `storage.gc_grace_hours`（config 默认 24h）；**显式 0 = 无宽限**，以 `time.Nanosecond` 传入（架构 §3.1：grace <= 0 会被 kernel 当 24h 默认，无宽限必须传亚秒级 duration——PRD W24「配 graceHours:0 令其可回收」即此读法）。缺省与 0 的区分有专测钉死（`TestT94GCGraceDefault`：config 调成 no-window 后缺省可见孤儿；默认 24h 实例上新鲜孤儿不可见）。CLI 的 `--grace-hours 0` 仍是「用 config」（flag 哨兵语义），两面差异为有意、已在 handler 注释与本日志登记。
- **grace 基准 = blob mtime 零变更**（ADR-0006）：mark-sweep 完全复用 `storage.Engine.GC` 既有实现，本票零改动 kernel；在线触发不缩短 grace（它不是紧急删除通道）。
- **响应** `{"candidateCount","candidateBytes","deletedCount"}`：dry-run `deletedCount` 恒 0 且 stats 不动（W24）；apply 报「预扫看到的候选」+「实际删除数」——安静实例两者相等（W25 断言），serve 写入在两遍间竞态时诚实分歧不算错误。实现为 apply 时两遍扫描（先 dry 拿候选清单并 stat 出物理字节，再 apply 删），candidateBytes 恒为磁盘物理字节（`storage.BlobPath` + stat；不依赖 blobs ledger——崩溃残留的「有文件无 ledger 行」孤儿也能正确计量）。
- **ledger 清理**：apply 删除后逐 sha 删 blobs ledger 行（镜像 CLI runGC 的收尾；`ErrNotFound` 容忍）——stats 的 blobs 计数不残留幻影行。
- **互斥（W25b / ADR-0015 勘误③）**：取 `storage.AcquireDataLock(dataDir, DataLockOpGC)`，失败且 `errors.Is(err, ErrDataLockHeld)` → **409** E-01，body 同时含：操作词、`ErrDataLockHeld` 原句、持有者诊断（pid/op）。绝不排队。同进程两个 fd 也互斥（flock 语义），并发 REST gc / REST↔CLI 双向都走同一原语。其余取锁错误 → 500 + Error 日志。
- **409 文案按持有者 op 映射（T-96 架构 review N1/N2/N3 采纳）**：
  - N1：不 parse acquire 错误串——storage 新增 `LockHolder(dataDir)`（读 `.maintenance.lock` 首行）+ `HolderOp(holder)`（提取 op token），httpapi 只消费这两个编程面；
  - N2：op 词表钉死为 storage 常量 `DataLockOpGC/DataLockOpExport`（期间并行波次又补了 `DataLockOpImport`，共存），cmd 两处调用点的字面量已换成常量防漂移；
  - N3：记录读不到（Windows 独占字节锁 / 空记录）→ generic 文案 "another maintenance operation is in progress"，绝不猜 export。单测以 truncate 空记录钉死该分支。
  - 已知边界（如实登记）：unix 上 flock 不阻止读，`LockHolder` 读到的是**最后持有者**记录——外来持有者（如 python flock）不写记录时，文案会沿用上一个 BinFlow op 的词（body 同时带 `pid=<n>`，运维可查活性）；语义即 datalock 注释的 "last holder, not a guarantee"。
- **审计**：`gc.run`（消费 T-93 的 `audit.ActionGCRun`，未重复定义），actor=请求的 admin principal、RemoteAddr 合入 detail；detail = `{apply, graceHours(null=缺省), candidateCount, candidateBytes, deletedCount}`（FR-30-AC5「候选数/释放字节」）。成功路径才落审计（含 dry-run）；失败 500 只 Error 日志——「失败的 gc 尝试也审计」未在 AC 内，不擅自加戏。完成时 INFO 结构化日志（mode/grace/candidates/candidate_bytes/deleted/elapsed）。
- **mark 集**：httpapi 侧 `liveChecksumSet`（nodes ∪ docker_refs，架构 §4.4/§11.12）——与 cmd 的同名 walk 同形的消费者侧实现（storage 不读 metadata 是铁律、metadata 无 DISTINCT 助手，架构 §3.2 明言回调由调用方实现）。两处需保持同步，双侧注释已互指。docker 半边有专测（`TestT94GCDockerRefsMarkSet`：仅被 docker_refs 引用的 blob 不是候选）。
- **admin only**：route gate `required+admin` + handler 复核（审计要写 actor，不依赖 route 编辑保持谨慎）；GC seam 缺失的装配 → 503（不假装跑过）。
- **GET /api/v1/system/gc 不做**（AC③，ADR-0015 勘误② P2 债务）：上次运行走 audit `gc.run` 查询；GET/DELETE 等落 E-26 404（有专测）。
