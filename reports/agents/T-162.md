# T-162: [P1] push 复制引擎（事件驱动 + cron 兜底）

- **Area**: `internal/replication`（引擎主体）+ `internal/repo`（仅 Put 链末 Enqueue 挂钩点最小接线）
- **Status**: done（Q6/Q7 按暂行口径实现，见下）
- **Dep**: T-161（done，Store/009 schema 复用）

## 做了什么

1. **AC ① — Put 链末 Enqueue 挂钩（非阻塞）**
   - `internal/repo/api.go`：新增消费侧接口 `Replicator`（`Enqueue(ctx, repoKey, path, sha256)`，
     fire-and-forget、无错误返回）——接口放消费侧（repo），replication 包的 `*Engine` 结构化满足，
     两包互不 import、无环。
   - `internal/repo/service.go`：`service` 增 `repl Replicator` 字段；`PutWithOptions` 文件分支
     audit 之后调用 `notifyReplicator`——`context.WithoutCancel(ctx)` + 独立 goroutine + recover
     护罩，上传路径零等待零失败（Put/PutWithOptions 共尾，maven 元数据面写入同样触发，见偏差说明）。
   - `repo.AttachReplicator(svc, r)` 装配入口（nil replicator = M1~M5 原行为，零开销）。
   - `Engine.Enqueue`：ListConfigs → 每个 enabled 且 source_repo 匹配的配置插一条 pending
     ReplicationTask（无去重，ADR-0021 注记 28 的口径）→ 非阻塞 wake（cap-1 channel）。
2. **AC ② — 失败重试指数退避**
   - `DefaultRetryBackoff = 1s→2s→4s→8s→16s`，总尝试 = 1 + 5 = 6 次；`EngineOptions.Sleep`
     注入（生产 = ctx 可取消 timer；测试 = 记录延迟值断言，不睡真时间）。
   - 不可重试类失败（`ErrNotRetryable`：SSRF guard 拒绝的目标、密文无主密钥、源 blob 丢失、
     目标 409、目标同路径不同 sha256 冲突）直接终态 failed（attempts 记满 6，防 cron 复活）。
   - 状态转移严格走 T-161 Store：pending → in_progress(attempts+1) → success | failed；
     中断（进程停机 ctx 取消）把 in-progress 行改回 pending（用脱离 shutdown 信号的短超时 ctx
     写入，保证停机时行不会卡死在 in_progress），下次启动 Run 的首轮 drain 恢复（H41 语义）。
3. **cron 兜底**
   - `Engine.Run(ctx)`：启动即 drain（接管崩溃残留的 pending/in_progress 任务）→ 之后每个
     wake / 每 `SweepInterval`（默认 1m，可注入缩短）drain 一轮；drain 的候选扫描（每配置
     ListTasks 新事件在前，limit 10000）= 兜底重入队：pending、failed 且 attempts<6、
     in_progress 残留（单 worker 模型下扫描时不可能有合法 in_progress）都会被重新处理，
     按 (created_at, id) 升序 FIFO。
   - 进程退出排空：ctx 取消 → Run 返回；在途 attempt 在下一个 ctx 边界中止并回退 pending；
     不再领取新任务。
4. **push 传输面（走目标现有 REST 上传面，不直连目标存储）**
   - `pushOnce`：HEAD `{TargetURL}/binflow/{TargetRepo}/{path}` → 200 且 X-Checksum-Sha256
     一致 = 幂等成功（零传输、不打开源 blob）；不同 = Q7 暂行冲突（终态 failed、不动目标）；
     404 → 打开源 blob（`storage.Engine.Open`，结构化满足 `BlobSource` 接口）→ PUT，
     声明 `X-Checksum-Sha256`（目标 ingest 时校验，不一致 409→终态），ContentLength 取 BlobRef.Size。
   - SSRF：复用 `internal/remote` 的 Guard（`guard.CheckURL` 每跳 + `guard.Dialer` 连接期二次检
     + DNS-rebinding pinning）。`DenyPrivateTargets` 选项（默认 false = 允许私网目标——复制目标
     几乎必然是内网/同主机实例；默认 true 会让功能在所有现实部署不可用，见暂行假设）。
   - 凭据：`remote.Cipher`（AES-256-GCM `enc:v1:`）解密 `TargetPasswordEnc`；无主密钥遇密文 =
     终态失败（fail-fast，错误文案只提 `BINFLOW_REMOTE_CREDENTIALS_KEY` 不泄密文/明文）；
     legacy 明文与空密码照放。Basic 头只在 username/password 非空时附加。
   - 审计：成功 `replication.push`、终态失败 `replication.push.failed`（actor=`replication`，
     detail JSON 含 config/target/sha256/attempts），经可选 `AuditSink` 注入，失败只 WARN。
   - URL 构造：逐段 `url.PathEscape`，段为空/`.`/`..` 拒绝（纵深防御，测试钉死）。
5. **测试（table-driven + 两实例集成）**
   - `engine_test.go`（11 个测试，含多子用例）：enqueue 扇出过滤（enabled/源仓匹配/其他仓）、
     happy path（Basic 凭据解密后逐字节断言、audit 事件）、幂等命中（HEAD 一致 → 0 次 PUT、
     0 次源 blob 打开）、Q7 冲突终态（1 HEAD/0 PUT、attempts=cap、零退避）、退避时刻表
     （值断言 [1s 2s 4s 8s 16s]、PUT 恰 6 次、attempts=6、completed_at 非空）、三次瞬败后成功、
     409 终态、cron 兜底三臂（崩溃残留 pending / failed<cap 重试 / failed=cap 不动）、
     停机回退（sleep 阻塞到 ctx 取消 → 任务回 pending、Run 返回）、坏目标配置三臂
     （ftp scheme / 空 target_repo / `..` 路径——零出站包）、密文无主密钥终态（凭据不泄漏）、
     源 blob 丢失终态。
   - `engine_integration_test.go`：**两个真实 BinFlow 实例**（storage engine + sqlite metadata +
     auth + repo.Service + generic adapter + httpapi 路由，仅监听器是 httptest，同进程）：
     - `TestTwoInstancePushReplication`（AC ③ 全链）：A 上传 201 → 引擎 HEAD 404 + PUT 201 落
       B 的 backing local → B 的 replica 视图 GET 同路径 200、X-Checksum-Sha256 与源一致、
       字节一致；backing local 直读同 checksum；replica 视图 PUT → 405、DELETE → 405。
     - `TestUploadUnaffectedByUnreachableTarget`（AC ① 非阻塞）：目标宕机（绑定后关闭的监听器）
       时 A 上传仍 201（<5s 断言，实测 ~170ms），后台任务烧满 6 次尝试落终态 failed。
   - `internal/repo/replication_hook_test.go`（5 个测试）：文件 Put 触发（repo|path|sha256 逐项）、
     folder Put 不触发、replicator 永久阻塞时 Put 不等（<2s）、nil replicator 原行为、
     replicator panic 被护罩吞掉（进程存活即断言）。

## 规格依据

- **ADR-0021 决策 2**（push：Put 链末异步 goroutine、走目标 REST、失败记 replication_tasks +
  指数退避最多 5 次、sha256 幂等秒传、SSRF guard 复用、凭据 AES-GCM 复用）——高置信，直接实现。
- **architecture.md §8 replication 段**（scheduler 为服务内 goroutine、周期可配）：SweepInterval
  默认 1m 与 `scheduler_interval_seconds: 60` 对齐。`max_concurrent_tasks`（并发上限）与
  `task_retry_delay_seconds` 未消费——本票按 AC ② 的 1s→2s→4s→8s→16s 固定时刻表实现，见偏差。
- **PRD FR-57/RE-04/RE-05**（H39/H40/H41/H42/H47）：幂等存在性检查、replica 仓库只读 405、
  崩溃残留恢复、目标宕机上传不受影响、冲突不动目标。
- 时间戳 RFC3339 UTC 文本、布尔 0/1：沿 T-161 Store 契约（ADR-0007）。

## Q6/Q7 暂行假设（待用户定案，可能调整）

1. **Q6（replica 仓库类型）暂行落法**：目标端 receiving 仓 = 配置里 `target_repo` 指向的
   **可写 local 仓**（本票测试中为 `replica-local`），「replica 仓库只读、PUT/DELETE 405」由
   **未配置写路由的 virtual 仓**（`replica`，members=[replica-local]）作为只读门面实现——
   全部复用 M3 已有行为（virtual PUT/DELETE 405、GET 两桶解析），零越区改动。PRD FR-57 待定项
   的另一种落法（`rclass=local + replica=true` 标志或新 `rclass=replica`，对本机用户拒写但对
   复制通道豁免）需要 repo 模型 + httpapi/adapter 侧改动，超出本票 area；定案后引擎侧只需改
   推送落点（传输面 `PUT /binflow/{targetRepo}/{path}` 的寻址），引擎骨架不动。
   注意：暂行落法下 backing local 本身仍可被目标实例上的用户直写（只有门面只读）。
2. **Q7（冲突策略）暂行落法**：目标同路径已存在且 **checksum 一致 → 幂等成功**（零传输）；
   **不一致 → 记 error 任务（status=failed、attempts 记满、completed_at 置位）、不动目标**。
   与 ADR-0021 决策 4 的字面（比较 updated_at、first-write-wins、记 `skipped`）及 PRD H47 的
   `status=conflict` 词汇不一致——009 的状态闭集（T-161）没有 conflict，本票按派单暂行口径取
   failed+conflict 文案；定案时若选 skipped/覆盖，改 `pushOnce` 的 HEAD 分支即可。
3. **私有目标默认放行**：`DenyPrivateTargets` 默认 false（Guard 的 AllowPrivateUpstream=true）。
  理由：复制目标几乎必然是内网/同主机 BinFlow 实例，默认拒绝等于功能不可用；scheme/host 校验、
  逐跳重检、DNS-rebinding pinning 仍然生效。建议 config 桥接票加
  `replication.allow_private_target`（默认 true）落到该选项。
4. **主密钥复用**：`target_password_enc` 沿用 `BINFLOW_REMOTE_CREDENTIALS_KEY`（ADR-0021 留的
  「改名或新增 BINFLOW_REPLICATION_CREDENTIALS_KEY 二选一」归实现票定——取复用，运维只管一把
  key；如需独立 key 只动 Cipher 注入处）。

## 偏差与说明

- **挂钩位置**：AC 写「`repo.Service.Put` 链末」；实现放在 `PutWithOptions` 的文件分支尾
  （Put 委托 PutWithOptions，Put 的链尾就是这里）。副作用：走 `PutWithOptions` 的 maven
  可再生内容写入（checksum 旁车/maven-metadata.xml）也会触发复制——语义上正确（目标也该看到
  新元数据），且目标端幂等。`PutFromBlob`/`PutLandedBlob`/`PutManifest`（checksum-deploy、
  docker 链）未挂钩——AC 只点名 Put；docker/maven/npm/pypi 协议面的推送编排见遗留。
- **冲突终态的 attempts 记满 6**：为让 cron 兜底不无限复活确定性失败，把不可重试失败的
  attempts 写成上限（实际只试了 1 次）。语义偏差已在测试注释与本文档标注。
- **`MaxItemsPerPush`/`MaxBandwidthBytesPerSec` 本票未消费**（沿 T-161 只持久化）：前者属于
  手动全量 trigger（REST 票）的语义，后者需要限速 reader，均记遗留。
- **单 worker 串行**：`max_concurrent_tasks` 并发上限未实现（Run 单 goroutine 顺序 drain）。
  死目标会把队列顶住（31s/任务的背压是有意设计——不拿整个队列去砸死目标）；并发化是
  后续增量（worker 池 + 每任务 ctx），引擎骨架已按"候选扫描→逐任务处理"分好层。

## 遗留（需上游/conductor 知悉）

1. **cmd 装配未接线**（与 T-161 遗留同源，area 限制）：`cmd/binflow-server` 尚未构造
   replication store/engine、未调 `repo.AttachReplicator`——生产路径要等桥接票（需要
   metadata.Open 暴露子仓或 *sql.DB 句柄 + config `replication:` 段消费）。
2. **replications REST 端点**（POST/GET/PUT/DELETE `/api/v1/replications`、`/{id}/trigger`、
   `/api/v1/replication/status`）不在本票 area（httpapi 由 T-157 在途占用）——配置创建目前
   只能直接写库（测试即如此）。
3. **`audit` 包动作词汇**：`replication.push`/`replication.push.failed` 目前是本包字符串常量，
   internal/audit 的 M6 词汇表（§3.5 增补）待补——补齐后改别名引用即可。
4. **candidate 扫描 O(limit)**：每配置扫最新 10000 行过滤状态；009 的
   `idx_replication_tasks_pending(status, created_at)` 就是为状态优先扫描建的，但 T-161 的
   Store 接口没有对应方法——接口扩一个 `ListTasksByStatus`（或 sweep 专用查询）是显然的
   优化位，本票未动 T-161 已定稿接口。
5. **postgres 方言**：store 层限制沿 T-161（unique violation 文案匹配 modernc）。
6. 协议面推送（docker /v2 三式、npm/maven/pypi 布局）当前走 generic REST 面——对
   docker/maven 仓的 source_repo 配置复制，落点路径是 node 路径直 PUT，对纯 generic/maven
   语义可用；docker manifest 的协议化推送（blob session + manifest PUT）是 M6+ 增量。
