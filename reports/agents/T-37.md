## 实现

### 1. token 端点（AC①，DE-13）

`internal/adapter/docker/token.go`：

- **GET/POST /v2/token**：query（GET）与 form body（POST，form 值优先于 query）都接受；参数 `service`/`scope`（可多值、空格分隔多 scope）/`account`/`client_id`（后两者读取不校验——规格 §5.2：权限在资源端点判）。
- 成功 200 `{"token","access_token"(同值),"expires_in","issued_at"(RFC3339 UTC),"scope"(收窄后)}` + `Docker-Distribution-Api-Version: registry/2.0`（全 /v2 响应带，DE-17）。
- 签发复用 `auth.TokenRegistry.Issue`（ADR-0010 第 4 条：不平行一套）；**TTL 取 `auth.token_default_ttl`（默认 720h），下限 1h**——非正 TTL 被 floor 到 1h，绝不落「永不过期」（本端点姿态是有限 TTL，AC①/Q3）。
- **任意有效用户可签**（双入口设计，FR-11 v1.1：管理面 `POST /binflow/api/security/token` admin-only 是另一入口）；主体 = Basic 解出的 principal 本人（token 表 username 归属调用者，审计/吊销链可依）。
- **匿名 + anonymous_access=true → 直发**（pull scope 按 ACL 收窄——匿名主体在 Can 里只有 read 规则，push/delete 自然被剔）；匿名关 → OAuth 形 401 `invalid_client` + `WWW-Authenticate: Basic realm="BinFlow Registry"`（本端点客户端在 OAuth 语义中，回 spec 体 Bearer 挑战会让它绕回死循环）。
- `offline_token=true` → 400 `invalid_request`（§6.5②定案）；`grant_type=refresh_token` → 400 `unsupported_grant_type`（non-goal）；其他方法 → 405 + Allow 头。
- **token 域非 2xx 用 OAuth 形错误体**（`{"error","error_description"}`）——与 spec 错误体、E-01 信封三格式并存按域分层（M1 三分层延续 + FR-11）。

### 2. 匿名 token 的主体（关键设计裁定）

token 表 `username NOT NULL REFERENCES users`，且**真实账号绝不能拥有公 anonymous 可获取的 token**（否则该账号任何授权都会注入每个匿名 pull）。`internal/adapter/docker/anonseed.go`：

- 合成账号 `_docker_anonymous`：`enabled=0`、非 admin、无任何授权、密码 hash 为无主随机字节的 argon2id PHC 串（行形状合法，即使有人改库翻 enabled 位也无法登录）。
- 惰性 seed（进程内 `sync.Once` + 幂等 insert，冲突即赢）；seed 失败 → 500 fail closed（匿名 token 宁可不发，不 fallback 到任何真实账号）。
- **验证器对 disabled owner 拒绝**（auth.Verify 既有规则），所以匿名 token 作 Bearer 时表现为「被拒凭证」→ 401 挑战；匿名 pull 的通行始终走 anonymous-open 规则，不经过 token。闭环方向正确：操作员若误启用该账号，匿名 token 立即全部失效（fail closed）。

### 3. 401 挑战与 scope 推导（AC②）

`internal/adapter/docker/scope.go`：

- **scope 推导**（挑战头 + 权限门共用一张表，docker-registry.md §5.1）：GET/HEAD → `repository:<repoKey>/<image>:pull`；PUT/POST/PATCH → `pull,push`；DELETE → `pull,delete`（T-32 AC②「DELETE 含 delete」）；catalog → `registry:catalog:*`（T-40 端点本体，占位路由已带）。subject 用客户端寻址的**完整 name**，客户端协商到的 token 与被拒资源一致。
- **scope 解析**：多 scope 空格分隔（strings.Fields 合并后逐 token）；三段式 `<type>:<name>:<action[,action]>`，action 合法集 pull/push/delete/*；**无效 token 容忍并丢弃**（不 400——规格 §5.2：Artifactory 也不在 token 端点逐项校验 scope；AC③ 矩阵的 invalid-scope 行落此）。
- **scope→Can 映射**（ADR-0010 第 5 条）：pull→r、push→w、delete→d、`*`→{r,w,d}；subject 首段=repoKey、余段=path（`repository:team1/acme/app:pull` → Can(team1, "acme/app", r)）；单段 subject（官方名形态）退化为 repo-key-only 提问（不发明 path）。
- **【暂行】token 响应 scope 按 ACL 收窄输出**（AC④）：admin 直通全量（Authorizer 规则 1 的镜像，不经 store 提问）；非 admin 逐 action 提问 Can，剔除未授权项；无存活 action 的 scope 整条消失；`registry:catalog:*` 对任何已认证主体授予（行级过滤归 T-40 端点，Q5）。**强制仍逐请求 Can**——收窄字段是客户端提示，不是授权。
- 挑战头不泄露内部细节（NFR-S9）：realm 只有 `<base>/v2/token`、service 固定 `binflow`、scope 是协议数据；无堆栈/内部 ID（真栈 curl 抓头验证）。

### 4. 资源端点权限门（AC② 前置落地，T-38~T-40 继承）

`handler.go` `authorizeRoute()`：name 路由过了 repo 门后，用**同一张推导表**把请求方法映射成 Can 提问。匿名写 → 带 scope 的 401 挑战；已认证权限不足 → 403 `DENIED`（spec 体，errors.go 新增码）；授权通过 → 落到 T-38+T-39 的基座 404。nil Authorizer（纯测试装配）对写 fail closed、对读随匿名开关。T-38/T-39/T-40 无需再各自推导权限映射。

### 5. 错误体三格式按域隔离（AC① + NFR-S10）

- `/v2/token` 全部非 2xx → OAuth 形（含 401/400/405/503）+ api-version 头。
- `/v2/**` 其他路由 → spec 体（既有）。
- 两者都不出现 E-01 `"status"` 信封字段（测试以字段判别断言）。
- **被拒凭证（坏 Basic/过期/吊销 Bearer）经 T-33 的 context 信号由 router 渲染**：/v2/token 上的坏凭据得到 spec 体 + Bearer realm=/v2/token 挑战（生产链真路径）——docker 客户端必须看到它能解析的 registry 平面挑战；OAuth 形 401 保留给「无凭据 + 匿名关」这一分支（客户端此时在 OAuth 语境）。测试对两分支分别断言并写明理由。

### 6. 吊销联动（D23，AC②/FR-11-AC6）

/v2/token 签发与管理面同一 token 表 → `POST /binflow/api/security/token/revoke`（按值）即可吊销；吊销后 Bearer 请求 → 401 + Bearer 挑战（spec 体）。真栈验证见下。

### 7. 装配

`docker.New` 签名扩展：`(svc, repos, authz auth.Authorizer, tokens auth.TokenRegistry, users metadata.UserStore, opts, log)`——authz/tokens/users 均可为 nil（测试装配；nil tokens → 诚实 503，nil authz → scope 收窄为空，强制不受影响）。Options 增 `TokenTTL time.Duration`。装配点：`cmd/binflow-server/main.go`（传 authSvc 双角色 + md.Users() + cfg.Auth.TokenDefaultTTL）、`internal/httpapi/harness_test.go`（同法）、`docker_v2_test.go` 两处构造跟随。R7 边界内（middleware.go 本体未动）。

场景 C（LAN 绑定 192.168.1.149:18193，为 docker daemon 网络路径）：

- **完整 docker login 协商序列**（容器内模拟 daemon 行为：probe → 解析 realm/service → Basic 换 token → Bearer 复打 `/v2/`）：
  - challenge: `Bearer realm="http://192.168.1.149:18193/v2/token",service="binflow"` ✓
  - token 长度 64 ✓
  - `GET /v2/` with Bearer → **200** ✓
- **`docker login` 本体受阻（环境非协议）**：本机 docker daemon 在 VM 内、HTTP 代理 127.0.0.1:7897 系统级启用且 daemon.json 无 `insecure-registries` 项。表现：daemon 对 `127.0.0.1:18192` 报 connection refused（代理不转发本地回环）、对 LAN 地址报 "server gave HTTP response to HTTPS client"（plain-HTTP registry 未列入 insecure-registries，daemon 坚持 TLS）。修法唯一且是**用户本机 daemon 配置**（往 `~/.docker/daemon.json` 加 `"insecure-registries": ["192.168.1.149:18193"]` 并重启 Docker Desktop）——写用户配置/重启服务超出我的权限边界（安全底线：不动用户配置），故标 **blocked-环境项**，协议面以容器内全序列等效覆盖（上表）。D05 全量（login→push→pull→run）本就归 T-44，届时 QA 在可控 daemon 或 compose 环境跑（FR-14-AC1 的 compose 路径天然解决此问题）。此结论与注入说明已留待转交。

## 遗留 / 交接

- **docker login 本体**：环境项（见客户端验证节），D05 全量归 T-44；建议 T-44/T-45 用 compose + insecure-registries 或可控 daemon。技术事实：BinFlow plain-HTTP 直连可用（容器内全序列已证），daemon 侧需 insecure-registries 条目——这是 docker 对所有 plain-HTTP registry 的通用要求，非 BinFlow 特例（tech-writer T-46 宜写明）。
- **T-38/T-39/T-40**：`authorizeRoute` 已在 repo 门后把权限判定做完（同一张 scope 推导表），内容 handler 只需实现协议本体；403 DENIED / 401 scoped challenge 的渲染不要重做。
- **T-40 catalog**：挑战 scope `registry:catalog:*` 已定；`registry:catalog` scope 对已认证主体在 token 端点直授，行级 read-ACL 过滤留给端点（Q5 暂行）。
- **匿名 token 语义**（architect 复审点，非阻塞）：匿名 token 作 Bearer 时因 disabled owner 被 401——设计意图（匿名通行不经 token、fail closed），若未来要求「匿名 token 可作 Bearer 通行 pull」，需在 auth.Verify 为该合成主体开特例（不建议，会让吊销语义复杂化）。
- `expires_in` 恒 720h（config 可调）；规格「待动态验证」清单中 expires_in 恒 3600 一项，BinFlow 取 config TTL 不跟进 Artifactory 常量（与 Q3 暂行口径一致）。
