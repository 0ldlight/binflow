## 一、实现（全部在 internal/adapter/docker）

### uploads.go

1. **`sessionRegistry.resolve` — lazy 重建（architecture §5.3.1 伪代码逐条落地）**
   - 快路径 `lookup` → miss 后在 `r.mu` 内 double-check → 仍是 miss 则进入**per-id 单飞 funnel**：
     首个请求注册 `resumeAttempt` 成为唯一 flyer，调用 `engine.ResumeSession`；并发到达者等待
     `attempt.done` 后复用同一结果（up 或 err）。**重哈希 O(size) 的 ResumeSession 在 r.mu 之外
     执行**——不做全局串行化（一个 10GB 部分层的 rehash 不能拖住无关会话的 POST/GET）。
     funnel 防 engine 侧同 id 并发 ResumeSession 的 last-writer-wins（被顶替句柄 Append 报
     already finalized）漏成 500。
   - 成功：`liveUpload{sess, received: sess.Offset(), started: now}` 注册进表 + 一条 INFO
     （restart resume 可观测性）；失败：**不注册、不缓存**，下一请求重试重建（瞬时故障自愈，
     注册表不毒化）。
   - ctx 由调用方 `context.WithoutCancel` 传入：重建一旦被多个 waiter 共享，不能随触发请求
     断连而死。
2. **`Handler.resolveUpload` — 错误映射**：`errors.Is(err, storage.ErrSessionNotFound)` →
   404 `BLOB_UPLOAD_UNKNOWN`（未知 id / 过期未清扫行 fail-closed / S3 后端恒走此臂）；
   其它 → `writeStoreFailure`（500，ErrEngineClosed/busy 503）。
3. **五动词统一入口**：`serveUploadSession` 的 PATCH/PUT/GET/HEAD/DELETE 全部经
   `resolveUpload`（GET 状态腿重启前已有——T-211 勘误，未重做路由，零 httpapi 改动）。
   契约 2：PUT finalize 与 DELETE cancel 重建后立即可执行。
4. **offset 权威性转移（契约 1）**：新增 `liveUpload.authoritativeOffset()` =
   `sess.Offset()`（nil 会话防御性回退 received）。PATCH 的 Content-Range 起点校验、全部
   416 分支（错位/毒化/断连）与 GET 状态腿的 Range 头都改读引擎权威值；`received` 降级为
   缓存（成功 Append 后的 202 仍直接渲染 Append 返回的累计值——它本身就是引擎返回值）。
   锁序单向 up.mu → session.mu，无反向路径。
5. 注释回写：liveUpload（received=缓存）、sessionRegistry（「deliberately in-memory、
   重启 404」的 M1 措辞废除，改为 T-216 lazy 重建 + S3 404 例外）。

### 2. 真实栈探针（AC1）——`scripts/m7-resume-probe.sh`

- **`--stop kill`：GREEN，EXIT=0**。关键输出：POST 202 → PATCH chunk1 202 Range: 0-524287 →
  kill -9 → boot #2 → **GET (post-restart): 204, Range: 0-524287** → PATCH chunk2 202
  Range: 0-589823 → PUT finalize 201 → GET blob 200 →
  `bitwise: downloaded blob == chunk1+chunk2 (18613416b6…)`。
- **`--stop sigterm`：RED，EXIT=1** —— **跨 area 依赖，见「遗留」**。404 BLOB_UPLOAD_UNKNOWN
  的根因不在适配层：graceful 停机链 `stack.close() → engine.Close()`（internal/storage/
  engine.go:573-593）对每个 live session 调 `cleanup()` = `RemoveAll(uploads/<id>) +
  deleteRow`。**对照实证**（真实栈，同二进制）：
  - SIGTERM 停机后：`upload_sessions rows=0`，`uploads/<id>/` 目录消失；
  - kill -9 后：`rows=1`，目录存在（→ 重建可用，kill 臂绿）。
  即：SIGTERM 后会话在存储层已不存在，适配层的 404 是该状态下的**正确**渲染；绿皮需
  ADR-0028 的 Close 语义实现（**保留未过期会话**）落地——那是 T-220 的 area
  （internal/storage，波 6）。本票 area 纪律内无可行修法（适配层无法拦截 engine.Close）。

### 3. 错位 416 腿（AC2，真实栈 curl）

PATCH 512KiB → kill -9 → 重启 → `Content-Range: 0-65535`（错锚点）PATCH：

```
HTTP/1.1 416 Requested Range Not Satisfiable
Content-Length: 0
Location: /v2/m7-legs/img/blobs/uploads/<uuid>
Range: 0-524287        ← 权威 Range（sess.Offset()，非缓存）
```
416 body length = 0（空 body）。

### 4. 过期腿（AC4，真实栈 + sqlite 回填）

PATCH 4KiB → kill -9 → sqlite `UPDATE upload_sessions SET expires_at=<1min 前>` → 重启：
boot #2 sweep 清行清目录（rows 2→1，`uploads/<id>/` 消失）→ GET 与 PATCH 均
404 `{"errors":[{"code":"BLOB_UPLOAD_UNKNOWN",…}]}`。T-209 语义零回退。

### 5. MinIO / S3 腿（AC3，真实栈）

MinIO 容器（minio/minio:latest）+ `backend: s3`（endpoint http://127.0.0.1:18490 +
use_path_style，桶 binflow）：POST+PATCH 正常 → kill -9 → 重启 → GET / PATCH upload URL

ErrSessionNotFound → resolve 直落 404，契约 5）。引擎侧

### 6. M2 D 序列 P0 复跑（AC5，真实 docker 客户端 27.5.1）

BinFlow 服务器容器共享其 network namespace（registry 即 daemon 的 127.0.0.1:5000，

- `docker login 127.0.0.1:5000`：Login Succeeded（token 流）；
- `docker push m2d/app:v1` / `:v2`：Pushed（真实 PATCH 上传路径 + manifest PUT，走过本票
