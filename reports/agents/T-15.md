## 做了什么

在 T-14 的 httpapi 核心上补齐 M1 的 Artifactory 兼容 REST 面与自有权限面：
`/api/repositories`（E-04~E-08）、`/api/storage`（E-09/E-10）、`/api/security`（E-16~E-19）
与 `/api/v1/permissions`（E-24）。路由全部挂在 `dispatchAPI` 的 switch 里（T-14 预留的
扩展点），终端 handler 走同一条 `enforce`（authenticator→authorizer→handler）链。

### 关键设计决策

1. **`routeAuth` 增加 `admin` 位**。T-14 的 routeAuth 只有 required/action 两个语义；
   管理面的「已认证但非管理员 → 403」在 `authorize` 中间件里补一个分支（required 先
   行，admin 后行，保持 401/403 的先后次序）。仓库变更、用户/token/权限管理全部挂
   `admin: true`；`GET /api/repositories`、`/api/storage` 读、改密、token 创建只要求
   认证（与 Artifactory 对齐：非 admin 可列仓、可为自己发 token、可改自己的口令）。
2. **错误体三分层落在 emitter 函数上**（PRD §5.1 v1.3）：
   - 制品/通用层 → `writeError`（errors[] 信封，T-14 既有）：repositories、storage。
   - 用户/权限管理层 → `writePlainError`（text/plain）：security/users、changePassword、
     /api/v1/permissions。
   - token 层 → `writeOAuthError`（`{"error","error_description"}`）：security/token、
     token/revoke。
   所有 plain-text 发射统一走 `writePlainText`，附 `X-Content-Type-Options: nosniff`
   （gosec G705 的姿态：错误文案含客户端可控的标识符）。
3. **`/api/storage` 读面按内容平面处理**（PRD E-09 注：内容元数据按匿名可读实现）。
   route 不带 `required`，匿名与否由 Authorizer.Can 内的 anonymous_access 决定——
   这样 `anonymous_access=false` 时 item-info 匿名 401、开时 200，与内容 GET 完全同
   振。`?list` 是例外：规格明确匿名 403（rest-api §3 高置信度），所以它的 route 也不
   带 required（401 挑战会盖掉规格的 403），403 判定放在 handler 里。
4. **文件夹寻址双拼写**。存储行的文件夹路径带尾斜杠（`acme/`），而 /api/storage 的
   客户端通常省略（`acme`）。`storageNode` 先试原拼写、404 时补斜杠重试——顺序不能
   反，否则显式尾斜杠请求与宽松拼写不可区分，且 404 文案必须以客户端实际发送的拼
   写为准。
5. **token 请求的 form/JSON 双形态用「首字节嗅探」而非仅 Content-Type**。curl `-d`
   不发 Content-Type；脚本发 JSON 有时也不发。net/http 的 ParseForm 只在 Content-Type
   是 form 媒体类型时才解析 body。实现：读 body（1MiB 上限）→ 首个非空白字节是
   `{` 走 JSON、否则按 form 解析。
6. **`?list` 的 deep/depth 语义**：`deep=1` = 不限深度（depth 0）；`depth=N` 限定层
   数；缺省 depth=1（只有直接子项）。文件夹行本身（尾斜杠 row）不产生 files[] 条目
   ——其内容由父目录列出（与 Artifactory 的 FolderInfo children 语义一致）。
7. **用户名大小写**。Artifactory 创建时统一小写（auth-model §1.1），BinFlow 的认证
   路径大小写敏感——直接改拼写会造成「创建的名字」与「登录的名字」不一致。取 Reject
   而非静默改名：混合大小写 → 400 plain text，错误文案说明差异。
8. **`PUT /api/repositories/{key}` 的更新语义**（PRD v1.3 校准 R2）：key 已存在 → 走
   UpdateRepo（200 `Repository <key> update successfully.`）；不存在 → CreateRepo（200
   `Successfully created repository '<key>'`）。两者都是 200 纯文本，仅文案区分。remote/
   virtual 的 rclass 由 repo.Service 的 `ErrRepoTypeNotSupported` 拒绝（400，文案含
   "supported from M3"，E-07）。

## 与规格的低置信度项处置（不作为 AC，按 BinFlow 自有语义并记录）

- token 的 `audience` 参数：接受并忽略（M1 单实例无跨服务 token 概念）。
- `refreshable=true`：按规格要求有限 expires_in，但 M1 不实现刷新流——带
  refreshable=true + expires_in>0 的请求成功创建，响应不带 refresh_token（未实现刷
  新流就不发刷新凭据，避免发一个用不了的 credential）。
- `GET /api/repositories/{key}` 的 404 文案：规格写纯文本 `The repository <key> was
  not found`，但 BinFlow 的仓库面统一走 errors[] 信封（§5.1 分层里 repositories 属
  制品/通用层）——文案嵌入信封 message。
- 用户名大小写：Artifactory 静默小写，BinFlow 拒绝混合大小写（见设计决策 7）。
- `?list` 的 `listFolders`/`mdTimestamps`/`statsTimestamps` 等参数：M1 只做
  list/deep/depth（FR-3-AC8 子集），其余忽略。
