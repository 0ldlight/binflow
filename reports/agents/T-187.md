依据（现行 PRD 口径，均为 M6 / docs/prd/milestone-6.md）：

M4 PRD（milestone-4.md :129/:139/:551/:560）用的 `login.failed` 是 M4 时点词汇，M6 为现行口径、后者胜出——按票据 AC「以 PRD 为准」执行。实现上 `audit.ActionLoginFail("login.failed")` 常量**整体删除**（不留双词汇/不留别名），替换为 `audit.ActionAuthFail("auth.failed")`；`audit.Actions()` 选择器词表同步。生产代码仅两处发射点（session.go / oidc.go），全量收口。

`login.success` **保持不变**（不在本票缺陷范围；见 §5 遗留①）。

### AC2 method / reason 字段（D8 闭环）

字段随 Detail JSON 落库（`{"method":...,"reason":...}`，与 remote_addr 同模式，T-11 先例；audit_events 无新列、无迁移、append-only 不回填）。查询面把 detail 渲染为对象，消费方在 detail 内看到两字段。

**method**（票据口径 `local/oidc/ldap`，与 users.provider / whoami source 同源词表）：

**reason**（PRD FR-56 :345 的 snake_case 词形为准；票据派发的 kebab 词形按同义映射）：

| 值 | 来源 | 语义 |
|---|---|---|
| `bad_credentials` | PRD（派发 "bad-credentials"） | 口令错 / 令牌被拒 |
| `user_not_found` | PRD | 本地无行且（有 LDAP 臂时）目录亦无此条目 |
| `provider_error` | PRD（派发 "provider-unreachable" ≡ 此值） | 目录/IdP 不可达、服务 bind 失败、exchange 失败 |
| `tls_handshake` | 本票（O-2 / T-186 遗留） | StartTLS 升级被拒、证书被拒——与错口令可区分 |
| `user_disabled` | 本票扩展 | 行存在但被禁用（401 单独成因） |
| `bad_request` | 本票扩展 | OIDC callback 形态错误（缺 code/state、tx cookie 缺失/畸形） |

**分类机制**（新文件 `internal/auth/failure.go`）：

- `Failure{Method, Reason}` 错误类型：**链上始终可达 `ErrInvalidCredentials`** → HTTP 面统一 401 映射零变化（FR-23-AC5 不泄露语义保持，H34/H37 回归绿）。
- 哨兵 `ErrProviderUnreachable` / `ErrTLSHandshake` 由 provider 层（LDAP dialer / StartTLS 包装 / OIDC 校验）携带，登录路径折算为 reason。
- 归因规则（`Service.classifyLoginFailure`，session.go）：
  1. 服务端故障（store 错误，链上无拒绝语义）**原样透传**——保持 500，不被折成 401；
  2. 基础设施类（provider_error/tls_handshake）**优先保留**——目录挂/StartTLS 失败不被行归属掩盖（O-2）；
  3. 否则**行属主定臂**：local 行→`local/bad_credentials`；oidc 行走口令登录→`oidc/bad_credentials`；禁用→`<provider>/user_disabled`；
  4. 无本地行：LDAP 臂的判定原样保留（目录 0 条目→`ldap/user_not_found`；bind 拒绝→`ldap/bad_credentials`）；无臂→`local/user_not_found`。
- `login.success` 事件补 `method`（成功也可按臂归因）；reason 仅失败事件携带。
- LDAP 侧细化：Bind 全路径分类（pool/dial→provider_error 或 tls_handshake；搜索 0 条目→user_not_found；bind 49→bad_credentials；服务账号 bind 失败→provider_error，此前与错口令同形）；`resolveUserDN` 以内部哨兵 `errNoLDAPEntries` 区分「目录答了没有」与「目录没答上」。
- OIDC callback `fail()` 携带 reason：IdP error 参数→provider_error；缺 code/state→bad_request；state 不匹配→bad_credentials；exchange 失败→`ProviderFailureReason`（TLS 形错误→tls_handshake，否则 provider_error）；id_token 被拒→authenticateOIDC 的分类（bad_credentials/user_disabled/user_not_found）。

### O-2 闭环（StartTLS 失败 vs 错口令）

线上行为不变（仍同 401 同文案，H34 的「非 hang 非 500」字面满足）；可诊断性走两条：

1. 审计：`auth.failed` + `method=ldap, reason=tls_handshake`（或 `provider_error`）vs `reason=bad_credentials`——管理员可查可分辨。
2. 服务端日志：基础设施类失败打**一条 WARN**（`httpapi: login failed: identity provider problem` + method/reason/error），错口令路径静默——补上 T-174 O-2 点名的「服务端零日志」缺口。

## 5. 遗留 / 需上游确认

1. **PRD §6.4 成功词表未实施**：M6 §6.4 还定义了登录成功新事件 `auth.login.{local,oidc,ldap}`（三动作）。本票 AC 只裁失败词（auth.failed），`login.success` 维持 M4 词汇并补 method 字段。若要落 §6.4 全集，是又一次消费面更名（控制台选择器/文档/M4 锚全动）——建议 PM 确认是否 M6 内收口或顺延。
2. **method 词表的 PRD 偏差（规格待验证）**：PRD FR-56 :345 枚举的是 `basic/bearer/session/oidc/ldap`（请求级认证机制），本票按派发 AC2 落 `local/oidc/ldap`（认证臂/身份属主，与 whoami source、users.provider 同源）——失败事件的诊断粒度需要臂维度（basic 下无法区分 local 错口令与 ldap bind 失败）。PRD AC 行（FR-56-AC3）本身只要求「含 method 与 reason 字段」未钉值域，按此实现；请 PM 确认词表口径或勘误 PRD :345。
3. **reason 词形**：PRD snake_case（`bad_credentials/provider_error`）为准；派发消息中的 kebab（bad-credentials/provider-unreachable/tls-handshake）按同义映射采纳 PRD 词形，扩展 `user_disabled`/`bad_request` 两个最小值（禁用行 401 与 callback 形态错误无既有词可归）。
4. **Bearer 面失败不记审计**（观察项，非本票范围）：PRD FR-56 :345 的「所有认证失败」若按字面扩到每请求 Bearer/Basic 401 会造成审计噪声，现行实现与 QA H38 验收一致地只记登录面；如需扩展请另立票。
5. **LDAP 服务账号 bind 失败语义变化**：原先与错口令同形（ErrInvalidCredentials 文案混同），现分类为 `provider_error`（目录对服务账号说了不，非用户口令问题）——对管理员是改进，对调用方仍是同一 401；无兼容性破坏，记录备查。
6. golangci-lint 全仓 53 条既有告警位于在途未提交文件（非本票引入，见 §3）——本票触及文件零告警，全仓清零需另立 chore 票。
