### 修复 1：CLI gc.run 审计（FR-30-AC5 的 CLI 腿，T-94 review 范围外①）

`cmd/binflow-server/main.go` runGC：

- **审计写入**：每次成功运行（dry-run 与 apply 都记，对齐 REST 面 T-94 语义）落一条 `gc.run`：
  - actor = `cliAuditActor`（"admin"，backup.go 既有常量——CLI 无已认证 principal 的既定口径，与 export.run/import.run 同款）；
  - 装配形态完全照 T-96 export.run 先例：`audit.BestEffort(audit.New(md, cfg.Audit.Enabled)).Record(ctx, ...)`，md 是 runGC 本就打开的 store，无新装配缝；
  - 失败路径（flag 错、锁被占、sweep 出错返回 err）不落审计——REST 面同语义（只有真正执行过的运行留痕），有专测钉死（锁被 foreign holder 占住时 gc 退出非 0 且无 gc.run 行）。
- **detail 形态逐字段对齐 REST 的 gcRunDetail**：`{apply, graceHours, candidateCount, candidateBytes, deletedCount}`。
  - `graceHours`：null = 用 config（REST 的「请求缺省」语义）；给了 `--grace-days`/`--grace-hours` 则记有效小时数（days 2 → 48）。CLI 的 `--grace-hours 0` = 用 config（flag 哨兵），故 CLI 面永远不可能出现显式 0——与 REST 面的有意差异维持不变。
  - `candidateBytes` = 物理字节（BlobPath + stat，不查 blobs ledger，崩溃残留孤儿也能计量）——与 REST 同源。
- **为此把 runGC 的 apply 从单遍改为两遍**（REST 已有形态）：pass 1 恒为 dry（拿候选清单 + 文件尚在时的物理字节），`--apply` 再跑 pass 2 真删。理由：apply 单遍返回的只有已删清单且文件已不在，物理字节无从计量；ledger Size 替代会与 REST 的「物理字节」语义分叉（孤儿行缺失时低报）。代价是 apply 的 mark 遍历跑两次（见遗留 2）。mark 集每遍重算不缓存——与 REST 一致（两遍间新落引用的 blob 在第二遍重新受保护，grace 之外再加一层）。
- **stdout 报告零回归 + 一处诚实增量**：`gc: mode=… grace=… data_dir=… candidates=N` + 清单行保持原样（apply 模式清单仍列**已删**集合，M2 形态）；apply 模式新增一行 `gc: deleted=N`（安静实例 deleted==candidates，竞态时诚实分歧）。TestGCFlagMatrix / TestGCConfigFlagResolvesLikeServe / TestGCTwoModesOnRealStore / TestGCDockerRefsExtendMarkSet 全部零改动通过。
- ledger 清理环从遍历 `candidates` 改为遍历 `deleted`（两遍化后正确源）。
- 新增 cmd 侧 `sumBlobFileSizes`（httpapi 同名 walk 的 CLI 孪生，注释互指防漂移——沿用 liveChecksumSet 的既定双份模式）。
- godoc 补审计语义一句。

### 修复 2：REST apply 断连防幻影（T-94 review N1）

`internal/httpapi/system_gc.go` handleSystemGC：

- 取锁后派生 `sweepCtx := context.WithoutCancel(r.Context())`（Go 1.21+，一行），锁内全程（referenced mark 集、两遍 GC、ledger 清理、gc.run 审计、完成 INFO 日志）全部换用 sweepCtx；body 解析与锁获取错误路径仍用 r.Context()。storage.GC kernel 零改动。
- 语义：维护锁已把这次运行与 export/CLI-gc 互斥，单条 HTTP 连接的寿命不得再约束它——断连/代理超时/排水超时中途取消 apply 会留下「已删 blob 的永久幻影 ledger 行」（sweep 只看磁盘，无自愈路径）且部分生效的删除不落审计。WithoutCancel 保留 values（principal 等）、只去掉取消传播；客户端已不在时响应写失败被静默吞掉（诚实的结局：运行本身完成且已审计）。
- dry-run 也一并挂 sweepCtx（统一、简单）：断连的 dry-run 仍会完整跑完并留痕——「一次 dry-run 执行过」是事实。
- 文件头契约注释补一句「run 绑维护锁而非连接」。

- `cmd/binflow-server/main_test.go` 新增 `TestGCAuditTrailCLI`：真实 data dir 上跑 gc（缺省 dry-run / `--grace-hours 2` dry-run / `--apply`）+ 一次被锁拒绝的运行；断言恰好 3 条 gc.run、actor=admin、detail 字段矩阵（graceHours null/2、candidateCount=1、candidateBytes=len(body)、apply 的 deletedCount=1）、被拒运行不落痕、apply 后 ledger 行随文件消失（无幻影）。
- `internal/httpapi/t114_gc_test.go`（新文件）`TestT114ApplySurvivesClientDisconnect`：自装最小栈，GC seam 用包装器把 **apply 遍 park 住**（拿到 handler 传入的 ctx），随后 cancel 请求 → 断言 sweepCtx.Err()==nil（断连不传播）→ 放行 → 轮询断言三件事：blob 文件已删、ledger 行已删（无幻影）、gc.run 落盘（apply:true、candidateCount=1、deletedCount=1）。release 用 sync.OnceFunc + defer，防断言失败时 parked handler 卡死 ts.Close。
