## 三、实现中值得 review 关注的三个决定

1. **FilterUnreferenced 用 keyset 分页而非 OFFSET**：GC 的消费模式是"边流边删"，OFFSET 分页在删除行后会跳过每页末尾的行。以 (created_at, sha256) 为游标后此问题不存在；`gc_pagination_test.go` 是防回归钉子。这是对 AC「分页流式」字面要求（未指定分页方式）的语义忠实实现。
2. **ListByPrefix/DeleteByPrefix 的边界语义**：`path = ? OR path LIKE 'prefix/%'`（转义 LIKE 通配符），保证 `a` 不匹配 `ab`——目录语义（T-12 的目录递归删/前缀列表）依赖此边界，测试固化。
3. **PrincipalsFor 用 LIKE 匹配 repos JSON 数组**：M1 够用（repo key 字符集 `[a-z0-9-]` 不含引号/JSON 特殊字符），auth 层再在内存里精解 JSON。已在遗留中记为 M2 前可换 JSON1 扩展的点。

## 七、Review 修复（2026-08-17，双 code-review 后）

评审输入：`reports/agents/T-10-review-arch.md`（REQUEST_CHANGES：B1/B2）、`reports/agents/T-10-review-correctness.md`（APPROVE，minor 参考）。conductor 裁定修 B1/B2，顺手 M7。

### B1 · LIKE 大小写误匹配（数据丢失路径）— 已修

- **缺陷**：SQLite `LIKE` 对 ASCII 默认大小写不敏感。ListByPrefix/DeleteByPrefix 的 LIKE 前缀臂会跨大小写匹配——reviewer 探针实证 `DeleteByPrefix("LIB")` 静默删掉 `lib/a.jar`。制品路径大小写敏感（Generic 任意路径/Maven groupId 可含大写），目录递归删是 T-12 的基础，属静默数据丢失路径。
- **修法**：`case_sensitive_like(1)` 进 DSN（见 B2 的 DSN 形态），一处修复同时覆盖两处查询；`PrincipalsFor` 的 LIKE 不受影响（repo key 字符集 `[a-z0-9-]` 全小写，review 已确认），不动。
- **实现细节**：`case_sensitive_like` 是 flag 型 PRAGMA，**读不回来**（`PRAGMA case_sensitive_like` 无返回行——临时探针实证后放弃读取断言）。改为**行为断言**：`SELECT 'A' LIKE 'a'` 为 true 仅当大小写不敏感。启动期 setupSQLite 与测试均用此探针。
- **测试证据**（`internal/metadata/case_like_test.go`，全部 PASS）：
  - `TestCaseSensitivePrefixMatch`：fixture `lib/a.jar`、`LIB/b.jar`、`Lib/c.jar`、`lib-x/d.jar`、`other/e.jar`。6 个列表子用例——`list/lib`→仅 `lib/a.jar`、`list/LIB`→仅 `LIB/b.jar`、`list/Lib`→仅 `Lib/c.jar`、`list/lib-x` 不串扰、大小写敏感的文件级命中/落空；破坏性方向 `DeleteByPrefix("LIB")` 恰删 1 行（`LIB/b.jar`），其余 4 行逐一断言存活（**跨大小写误删已消除**）。
  - `TestPrefixLikeWildcardsEscaped`（M5 一并补）：前缀含 `_`/`%`/`\` 时字面匹配——`my_lib` 不命中 `myXlib`、`100pct` 不命中 `100Xct`、`back\slash` 转义正确；DeleteByPrefix 同样不误伤。
  - `TestOpenPRAGMAsApplied` 增补 `case_sensitive_like` 行为断言子用例。

### B2 · MaxOpenConns=1 + per-connection PRAGMA 耦合 — 已修

- **缺陷**（两位 reviewer 一致）：`foreign_keys`/`busy_timeout` 是**每连接** PRAGMA，原先经 `db.ExecContext` 只配置了池中第一条连接——MaxOpenConns=1 时碰巧安全，谁按 ADR-0007 把池改大，FK 就在新连接上静默失效（正确性 reviewer 探针 F2 证实 4 连接基线全 0）。同时 MaxOpenConns=1 是 ADR-0007 明确弃选的方案 A，且我此前"单连接驱动管线"的论据不成立（modernc 对单连接不做查询交错）。
- **修法**（DSN 路线，驱动源码核实）：`modernc.org/sqlite@v1.56.0` 的 `applyQueryParams` 在 `newConn` 内对**每条**新连接执行 `_pragma` 列表（conn.go:135，sqlite.go:380 起，按 busy_timeout 优先、其余字典序应用）。DSN 形态：
  ```
  file:<path>?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=case_sensitive_like(1)&_pragma=journal_mode(WAL)
  ```
  `db.SetMaxOpenConns(NumCPUConcurrency())`（= `runtime.NumCPU()`，恢复 ADR-0007 原口径；`NumCPUConcurrency` 从死代码变为实际调用点，M6 一并消解）。`setupSQLite` 不再打 PRAGMA，改为**启动期断言**（journal_mode/foreign_keys/busy_timeout 读值 + case_sensitive_like 行为探针，任一不符 fail-fast 并指向 DSN）——DSN 回归会在启动时报错而不是等前缀查询出事。
- **测试证据**：`TestPRAGMAsHoldOnEveryPooledConnection`——4 个 goroutine 并发 `RawConn`（新增的导出诊断方法，走 `db.Conn`，不污染 Store 接口），强制池开到 4 条连接，逐连接断言 foreign_keys=1、busy_timeout=5000、LIKE 大小写敏感（行为探针）。NumCPU<4 的环境自动 Skip。
- **回归确认**：`TestFKBlocksOrphanNode`、`TestDeleteRepoCascadesNodes`、`TestOpenIdempotentMigration`、`TestConcurrentMixedWorkload`（4 写者+4 读者并发）在新池大小下全 PASS，-race 零告警。
