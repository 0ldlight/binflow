# T-161: [P0] replication 模型与 009 迁移（replications + replication_tasks 表）

- **Area**: `internal/replication`（新建包）、`internal/metadata`（仅迁移文件与测试适配）
- **Status**: done
- **Dep**: T-149（前置，已 done）

## 做了什么

1. **009 迁移（AC ①）**：开工时 `migrations/{sqlite,postgres}/009_replication.sql` 已以未跟踪文件形式存在
   （随 T-156 批次落盘，逐字段对照 `docs/design/architecture.md` section 6「009_replication.sql」定稿块——
   两个方言的列、索引、注释与契约完全一致，含 `ON DELETE CASCADE` 两条 FK）。本票核对后原样保留，
   未重写、未改名。`internal_test.go` / `usage_internal_test.go` 的 rewind 列表同样已包含 009 对象的
   DROP（先 tasks 后 configs、索引在前），顺序正确，无需再改。迁移注册无需改动：`migrate.go` 的
   `go:embed migrations/sqlite/*.sql` 自动发现新文件（无手工 map）。
2. **模型与 Store 接口（AC ②）**：新建 `internal/replication` 包。
   - `model.go`：`ReplicationConfig` / `ReplicationTask` struct（字段与 009 列一一对应）、
     `ConfigStatus`（T-159 面板所需的派生态：各状态计数 + LastSuccessAt——009 无这些列，从
     replication_tasks 聚合）、五个 `TaskStatus*` 常量、sentinel errors（`ErrConfigNotFound` /
     `ErrTaskNotFound` / `ErrDuplicateName` / `ErrInvalidStatus`）、消费侧 `Store` 接口
     （配置 CRUD + 任务 CRUD + `ListTasks`（新事件在前，T-159 事件列表）+ `Status`）。
   - `store.go`：`SQLiteStore`（`NewSQLiteStore(*sql.DB)`）实现 `Store`，直接跑在 009 迁移产出上；
     UNIQUE(name) 冲突归一为 `ErrDuplicateName`；busy 类错误挂 `metadata.ErrStoreBusy`（复用
     `metadata.IsStoreBusy`，上层 503-retry 语义与其它 store 一致）；status 白名单校验封住 DDL 的
     自由 TEXT 列；时间戳全部由调用方传入（ADR-0007）。
3. **单测（AC ③）**：
   - `internal/metadata/replication_internal_test.go`（= AC 所称 migration_test.go，按本包
     `*_internal_test.go` 命名惯例落位，模式同 T-156 的 `oidc_ldap_internal_test.go`）：
     `TestReplicationMigrationIdempotent`（open 两次 → 版本钉在 latest、契约对象各出现一次、
     迁移后写入的行重开后存活）、`TestReplicationMigrationSchemaShape`（PRAGMA table_info 逐列
     锁死两表列序，防漂移）。
   - `internal/replication/model_test.go`：用 `metadata.Open` 建真实全量迁移库、种一行 repositories，
     再以 `foreign_keys(1)` 的独立连接跑 CRUD——约束真的会触发。table-driven 覆盖：
     配置 CRUD 全路径（round-trip/list/update/delete）、not-found 三路径、重名（create/改名冲突/
     自身保留名对照组）、FK 拒绝未知 source_repo；任务 CRUD（空 status 默认 pending、
     pending→in_progress→success、failed 记 last_error）、非法 status 四例、not-found 三路径、
     FK 拒绝孤儿任务、ListTasks 新在前 + limit、删配置级联清空任务、`Status` 各桶计数 +
     LastSuccessAt=MAX(completed_at) + 未知 id 全零。

## 规格依据

- `docs/design/architecture.md` section 6「009_replication.sql（M6 增量，ADR-0021；架构定稿）」：
  两表 DDL、索引、状态枚举 `pending|in_progress|success|failed|skipped`、密文格式
  `enc:v1:<b64>`（同 ADR-0012 remote_configs.password 规）——高置信，直接实现。
- 时间戳 RFC3339 UTC 文本 / 布尔 0/1 / 命名与回退列表：沿 001_init.sql 与 ADR-0007 惯例。
- T-159 面板字段（URL/仓库/状态/上次成功时间/pending/error 计数）：BOARD.md T-159 AC ①；
  「上次成功时间」与计数在 009 中无落列，按架构保持派生（`Store.Status`），未擅自加列。

## 偏差与说明

- **迁移文件名**：AC ① 写的是 `009_replication_tables.sql`；实际（及 architecture.md 定稿块标题）为
  `009_replication.sql`。以架构契约为准保留现名，请 conductor 知悉（改名会与 architecture.md 及
  已落盘的 rewind 列表脱节）。
- **Store 实现位置**：任务说明「实现由 metadata 侧后续 ticket 桥接」，但 AC ③ 要求「CRUD 全路径」
  测试——没有真实现就只能测假件。落法：SQL CRUD 实现放本包 `store.go`（area 内），消费侧接口 +
  实现同票交付；「metadata 侧桥接」留给后续票的部分 = 把该 store 接进 `metadata.Open` 的子仓
  （如 `Replications()`）与 `Store` 接口面 / cmd 装配。

## 遗留

- `Store` 尚未接进 `metadata.Store` 子仓面与 `cmd/binflow-server` 装配（桥接票；桥接时需把
  `*sql.DB` 句柄或子仓方法暴露给本包）。
- `isUniqueViolation` 按 modernc sqlite 的 "UNIQUE constraint failed" 文案匹配（与 repo 包现行为
  一致）；postgres 方言启用时需补 "duplicate key value violates unique constraint" 分支。
- 复制引擎（Enqueue 触发、重试退避、带宽限速）是 T-162；`MaxBandwidthBytesPerSec` /
  `MaxItemsPerPush` 本票仅持久化，未消费。
- Q6/Q7（replica 仓库类型、冲突策略）待用户定案，不影响本票。
