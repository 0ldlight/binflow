## 关键逆向发现（选摘）

- 上传成功响应：201 + `Location` + `X-Checksum-Sha256` 头 + FileInfo 形态 JSON（官方文档只写 201）。
- 统一错误体 `{"errors":[{status,message}]}`（所有 REST 层，含非 /api 的制品路径）。
- **同 checksum 幂等重传不触发覆盖权限检查**（`isFileOverwrite` 的 differentChecksums 逻辑）——官方文档未记载，对 CI 重试行为关键。
- checksum 旁车文件（`.sha1`/`.md5`/`.sha256`）上传有 1024B 上限，409 文案与 repo checksum 策略联动。
- 回收站属性名 `trash.{deletedBy,originalRepository,originalRepositoryType,originalPath,time}`；默认开、14 天。
- 启动时清理 `tmp/` 下修改超 24h 的子目录。
- virtual PUT 未配 local deployment → 405 + `Allow: GET`。

## 与公开文档的冲突 / 出入

1. `GET /api/repositories/{key}` 不存在时：官方文档写 404；代码由 `respondWith404ForNonExistentRepo` 开关控制（默认 404，旧默认 400）。规格建议 BinFlow 固定 404。
2. `gcConfig.cronExp=0 0 /4 * * ?`（一手模板原文）：按 Quartz 分钟域 step 语义这是「每 4 分钟」而非「每 4 小时」，疑为官方模板笔误（意图 `0 0 0/4 * * ?`）。已在 storage-layout.md 标注，建议 BinFlow 用 `interval: 4h` 语义实现，勿照抄表达式。
3. `_pre` 清理周期：cached-fs provider 官方文档提「daily cleanup job」，默认 file-system 模板下未在已反编译代码中定位到清理点（逻辑疑在未反编译的 `org.jfrog.storage.binstore` 三方库），标低置信度。
4. JFrog KB `_pre` 文章页面（jfrog.com/help）反爬无法直接抓取正文，内容经搜索摘要双源印证，置信度按「高」但注明渠道。
