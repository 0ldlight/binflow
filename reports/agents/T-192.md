## 1. 做了什么

T-172 D-1 的根因：`Service.authenticateBasic` 每请求直接调用 `VerifyPassword`
（argon2id m=64MiB/t=1/p=4，单次 ~64MB 瞬态堆 + 4 lanes CPU），无并发上限、
不观察 ctx——瞬时大并发 Basic 认证全部同时开算，客户端批量断连后 ~800 个
socket 各挂一个为死连接计算的推导，CPU 337%、RSS 4.8GB、匿名面饿死 10min+。

修复（internal/auth，信号量闸 + ctx 感知排队）：

1. **`hashGate`**（新文件 hashgate.go）：buffered channel 计数信号量。
   `acquire(ctx)` 先做 `ctx.Err()` 预检（预取消必失败、必不占位），再
   select「拿位 vs ctx.Done」——排队者随客户端断连即刻弃位（net/http 在
   连接关闭时取消请求 ctx，即 T-41 已证实的主判别腿）。弃位错误 wrap
   ctx.Err()，**刻意不满足 `ErrInvalidCredentials`**：断连不是登录失败，
   T-187 审计面不会把它记成 auth.failed。
2. **默认上限** = GOMAXPROCS，钳到 [1, 16]（`maxHashConcurrency`）：
   argon2 内存带宽受限，超钳位几乎无吞吐收益、只放大最坏瞬态堆
   （上限 × 64MB；16 把宽主机钉在 ~1GiB 量级）。操作者旋钮
   `Service.WithHashConcurrency(n)`（n<1 panic——装配期 bug 快速失败）。
   x/sync/semaphore 与 channel 信号量等价（权重恒 1），选 channel：
   x/sync 目前不在 go.mod require（仅 go.sum 残留），避免为零收益引入直接依赖。
3. **接线点**：`authenticateBasic` 重构（廉价拒绝在前：disabled / 空 hash
   用户绝不触闸 → 闸内 verify → 成功/落 API-token 对偶，各分支语义与
   原 switch 逐一等价）；`ChangePassword` 的旧口令校验与新口令哈希同样入闸。
   测试缝 `hashVerify`（默认真 argon2，内部测试注入观察并发）。
4. **日志治理**（断连风暴不淹没运维面）：httpapi 登录处理器对「非凭据类
   失败」先以 T-41 分类器判 ClientDisconnect → WARN + client_disconnect
   标注（原为 ERROR）；auth `fillGroups` 在 ctx 已结束时跳过注定失败的
   组员查询与其 ERROR 行。语义不变（响应/审计不变，只动日志级别）。

### AC1（并发闸 + ctx 取消）证据

- `TestHashGateBoundsConcurrency`（1/2/4 × 8/12/16 worker）：观测并发 ≤ limit，全部准入。
- `TestHashGateCancelAbandonsQueueNotHolder`：满闸时取消 4 个排队者 → 2s 内全部以
  context.Canceled 弃位；持有者不受影响（探针 DeadlineExceeded 证明无槽泄漏）；
  释放后新等待者照常准入。
- `TestHashGatePreCanceledContextFailsFast`：预取消 ctx 8 连发全失败且 4 槽仍全空。
- `TestVerifyPasswordGateErrorIsNotCredentialRejection`：闸错误不含
  ErrInvalidCredentials、含 ctx.Err()、hashVerify 零调用。
- 真进程日志（3 轮风暴 900 请求、450 断连）：240 条
  `WARN ... "acquiring hash slot (concurrency limit 16): context canceled"`——
  排队者弃位在生产面可见。

### AC2（内存回落，如实说明语义边界）证据

- 单测 `TestT192HashStormHeapRecoversNoLeak`（**真 64MiB 参数** ×12、gate=2）：
  `HeapInuse peak=259MiB → post-GC=3MiB（回收 256MiB）`；goroutine 回基线
  （±2 容差）。另一次运行 peak=325MiB→5MiB。
- 真进程缩放复现（自建二进制 25MB、127.0.0.1:18091、GODEBUG=gctrace=1，
  300 并发 curl 真 Basic 认证、每 2 个中 1 个 --max-time 0.3 断连；本机 16 核
  → 闸=16 即 GOMAXPROCS）：
  - 风暴墙钟 **4s 排空**（D-1 修复前：匿名 ping 饿死 10min+）；
  - gctrace 风暴期堆：live/spans ≈ 1027-1091MB（= 闸 16×64MB 模型值），
    heap goal 2055-2183MB（GC pacing 余量）——**有界**，对照 T-172 无闸时
    ~800 并发推导 RSS 4.8GB；
  - 风暴后轻流量触发 GC：spans 使用 **回落到 66MB**（堆完全可回收）；
  - RSS 曲线（KB）：基线 148,908 → 风暴峰 2,193,528 → 平台 2,193,544（+0/5/15/30/60s 持平）；
    第二/三轮风暴峰 2,587,624 / 2,784,532——**RSS 语义边界（如实）**：
    Go 侧无法强制还页给 OS，macOS MADV_FREE 下 RSS 水位记录高水位并待压
    力回收；可达的证明是 GC 后 HeapInuse/spans 崩落（66MB）与 goroutine
    无泄漏，峰值被闸模型钉住（~闸×64MB×2 pacing），不随队列深度增长。
  - 三轮风暴全程 access 行 1034 条、**5xx=0、ERROR 行=0**，SIGTERM 优雅退出。
