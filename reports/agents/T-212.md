## 一、做了什么

### 1. migration 011（双方言）

- `migrations/sqlite/011_rbac_role.sql` + `migrations/postgres/011_rbac_role.sql`（语句均在
  SQLite/Postgres 公共子集内，两方言逐字一致）：
  - `users.role TEXT NOT NULL DEFAULT 'user'`；
  - `UPDATE users SET role = 'admin' WHERE is_admin = 1`（回填）；
  - `permission_principals.can_manage INTEGER NOT NULL DEFAULT 0`。
- is_admin 兼容镜像（ADR-0026 决策 6）由**所有写路径同语句维护**：
  - `userStore.Create`：Role 为空时按 IsAdmin 派生（既有调用方——httpapi 建用户、seed、auto-create——零改动即得一致镜像）；
  - `SetRole`（UserStore 新方法）：`UPDATE ... SET role=?, is_admin=(role='admin')` 单语句——idp_sync 与 adminRole wire 的写缝；
  - `UpdateProfile`（签名不变，httpapi security.go 现有调用零改动）：升 admin → role='admin'；降 admin → role='user'；**readonly_admin 行在 email-only 部分更新下保持 role 不变**（布尔 seam 表达不了 readonly_admin，静默降级是行为地雷，CASE 语义防住）；
  - `seedAdmin`：INSERT 显式带 role='admin'（否则列默认 'user' 会让种子 admin 镜像漂移——实现中抓到的坑）。
- postgres README 版本史补 011 行。

### 2. internal/auth 角色与能力（新文件 `rbac.go`）

- `Role` 三值闭集（`RoleAdmin`/`RoleReadOnlyAdmin`/`RoleUser`）+ `ParseRole`（闭集校验；kebab `read-only-admin` 按 T-214③ 拒绝）。
- `ManagementCapability` 六能力闭集（system/security × read/write + repo:read/repo:write）+ `ManagementCapabilities` 枚举切片（QA 矩阵可穷举）。
- `CanManage`（§3.4a 链②：nil→false、admin 全能、readonly_admin 三读面、user 全拒；**未知 capability 值任何角色都拒**——路由门 typo 必须_fail closed_）。
- `CanManageRepo`（链③：admin true / readonly_admin !write / user → `Can(repo, "", "m")`）。
- `Principal.EffectiveRole()`：显式 Role 优先；裸 `Admin:true`（存量手搓 principal/旧测试）折叠为 admin；垃圾值→user。**`Authorizer` 接口零改动**（adapter/httpapi 的 fake 们不受影响）——`CanManage/CanManageRepo` 以 `ManagementAuthorizer` facet 经类型断言暴露（与 session/permissionViewer facet 同模式，T-215 消费）。

### 3. Can 动作集扩 m（authorizer.go）

- `ActionManage = "m"`；`rowAllows` m → `row.CanManage`（m 不隐含 r/w/d，反向亦然）。
- **m 的 target 匹配只判 repos[]**（`targetListsRepo`：decode 后仅判成员）——includes/excludes 不参与（对齐 auth-model §4：manage 无路径子域）。路径面沿用 targetCovers。
- **readonly_admin 短路**：`Can` 内 role 分支在 target 求值之前——r 恒 true、w/d/m 恒 false，target 行对其无任何效果（组合无效而非非法；本层只求值，错误口径归 T-215）。
- admin 旁路语义不变（EffectiveRole 归一化后与旧 `p.Admin` 判定逐 case 等价——全部既有 Can 测试零改动通过即证）。
- `PrincipalBits`（SE-08 视图）扩 `Manage` 位：repo 列出即并集，与 Can 的 m 判定逐字对齐。

### 4. 即时生效缝（Verify/Session 同路径重查 role）

- `TokenVerifier.Verify` 与 `authenticateSession` 的 owner 行重查本来就读全行——role 进 SELECT 后**同缝免费获得**（与 enabled 同路径，T-208 护栏③先例；V04 前提）。
- `newPrincipal(name, role, source)` 统一构造：Role 与 Admin 派生镜像永不分叉。Basic/OIDC/LDAP/Token/Session 五臂全接。

### 5. idp_sync 角色改写（ADR-0026 决策 6 / T-214④）

- 映射键落 `auth.OIDCConfig.ReadOnlyGroup`（组名，group claim 值；YAML 键 `oidc.<provider>.readonly_group`）与 `auth.LDAPConfig.ReadOnlyGroup`（组 DN；`ldap.readonly_group`）。
- 权威阶梯 `mapGroupsRole`（oidc.go）/ Bind 内同阶（ldap.go，`isAdminMember` 泛化为 `isGroupMember`+`groupNameFromDN`）：**admin_group > readonly_group > user**，双命中取 admin 永不合并；两键缺省 = 行为与今日完全一致（零配置零行为变化，测试钉死）。
- `Claims`/`ProviderUser` 增 Role（空值回退旧 `Admin` 布尔——`claimsRole` 归一，M6 代码与既有测试零改动）。
- `refreshProviderAdmin` → `refreshProviderRole`：漂移双向纠正（含**降级**——目录不再列 admin 组的行被重写回 user），写缝 `roleWriter{SetRole}`（替代 adminFlagWriter，`WithRoleWriter` 导出），落库经 `userStoreAdapter.SetRole` → `metadata.SetRole`（镜像同语句）。
- auto-create 首登录行带 role（readonly 组新用户直接落 readonly_admin）。

### 6. snapshot 往返保真

- VacuumInto 整库复制天然携带新列；测试钉死：快照内 users.role（admin/readonly_admin/user 四行）与 can_manage=1 位逐值还原（export→purge→RO 断言）。
