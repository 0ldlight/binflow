## 一、实现内容

### ① FR-20 六步请求流（RE-04）— internal/remote/fetcher.go（Engine）

`Engine.Fetch(ctx, repoKey, path)` 按序实现六步（`repo.Service.Get` 在**读权限门通过后**才分派——未授权主体绝不能借 BinFlow 触达上游 URL，测试钉死零上游包）：

1. **blocked_out 手动遮蔽** → 404（rest-api.md §1.2 step 6 文案 + RepoRejectException 默认 404 语义）。
2. **checksum 后缀**（.sha1/.md5/.sha256/.sha512）→ 404，message **逐字** `Checksums are not downloadable.`（M45 等值断言），零上游流量（含已缓存制品，测试断言上游计数不变）。
3. **负缓存**（remote_cache 行 kind=`negative`，T-62 的 kind 列对 store 是自由文本，无需扩 metadata API）→ 期内 404 零上游流量（M43：二次 miss 上游计数不增，1800s 后回源，时钟注入验证）。
4. **本地缓存命中**：node 落 remote 仓自身命名空间（无影子仓，§6.4-③ 收口）；新鲜期按**双类 TTL**——`adapter.ForProtocol(packageType).Classify(path)` 分流 content（remote_configs.content_ttl_seconds=7200）/ metadata（600）；无注册 provider（generic/未落地协议）默认 content（长 TTL 在不可变对象上无害，反向不是）。命中直发 `X-BinFlow-Cache: HIT`，零上游流量（M41 负断言）。
5. **过期/缺失回源**（T-65 client，per-repo 连接池 + 配置签名重建 + `CloseIdleConnections`）：
   - **200** → `storage.BeginSession→Append→Commit` 流式落盘（与本地上传同一协议，落盘与响应逐位一致，node digests = 实测值）→ blob-first（blobs 行→node 行）→ remote_cache 写验证器（ETag/Last-Modified）+ TTL 时钟 → `MISS`。上游 `X-Checksum-Sha256` 与实测不一致时 WARN 登记**不拒**（PRD v1.2「四值策略 M4」优先于架构 §4.5 的强校验草案——见遗留④）。
   - **404** → 写负缓存 + **有过期副本仍回发**（expired-but-serving，repo-semantics §7.2 step 5；服务端带 `X-BinFlow-Cache: STALE`）。
   - **401/403** → 资源 unfound 404，message 附上游状态摘要（§7.6）；**不写负缓存、不标 offline**（凭据态可热修，测试证明后续路径仍打上游）。
   - **5xx/超时/传输失败** → 仓标记 **assumed-offline 300s**（内存窗口，轻量熔断）+ 静默期零上游流量（M44-④：时钟注入验证期内外行为）；有副本（含过期）→ 200 旧内容 + `X-Binflow-Upstream-Error: <摘要>`（M44-①）；无副本 → **404**（message 含 "assumed offline"，M44-②）；`hardFail:true` → **502**（M44-③；勘误口径：hardFail 只改无副本分支的码值，有副本仍先服务副本）。
   - **其它 4xx** → unfound 404 + 摘要，不标 offline（**决策点**：§7.6「4xx/5xx 其它视同连接错误」为中置信度，PRD 基线只列 5xx/超时；BinFlow 从严取「确定应答非故障」，已在测试固化，推翻点为 mapUpstreamStatus 单分支）。
   - **非主动 304**（M3 不发条件头）：有过期副本 → 刷新时钟回发 `REVALIDATED`；无副本 → 502（不标 offline）。
   - **SSRF 链拒绝**（T-65 RejectionError）→ 400，message 含 "private or suppressed upstream"（M42 类字样）+ 类别，且**不开** offline 窗口（某路径被拒不能静默整仓）；`ErrBodyTooLarge`（64MB 缓冲型）→ 502（NFR-S13 第 5 点）。
6. **写面拒绝在 service 层**（见②），引擎永不接触写。

**并发（repo-semantics §7.3）**：per (repo,path) singleflight；等待者醒来后**重跑查找**（拿到锁后二次确认——获胜者落盘后等待者直接 HIT）；等待者至多自行接触上游一次；metadata 类等待上限 60s（§7.1 metadataRetrievalTimeoutSecs，EngineOptions.MetadataWait 可注入）超时回退 stale/unfound——**等待者绝不 5xx**（16 并发 miss 测试：上游恰好 1 次、全员同内容）。

**FetchResult 显式区分副本/真 miss（R10，T-71 消费）**：成功必有副本（`HasCopy=true`：HIT/MISS/STALE/REVALIDATED 全形态）；真 miss 一律走 `*FetchError{Unfound:true}`，绝不返回「空成功」。T-71 只需判 err。

**RE-11**：`Engine.Stats(ctx, repoKey)`（hits/misses/negatives/stales/upstream_bytes + cached nodes/bytes）为接口位；REST 端点 P2 未接（AC③ 允许延后）。

**日志（AC②/§6.3）**：每次 fetch 结局一条结构化行，字段 `repo/path/upstream_host/cache_result/upstream_status/upstream_duration_ms(/bytes/note)`；纯 HIT 走 Debug（热路径），上游接触面走 Info；**凭据零出现**（测试断言日志不含 password/Authorization）。

### ② repo.Service 分流（internal/repo/service.go，不改 Service 签名——R6 红线遵守）

- **Get**：`loadRepoRow`（任意类）→ **读权限门** → `type=remote` 分派 `Engine.Fetch`；`*FetchError` 映射为新增 `*repo.StatusError`（Code/Message/Header；Unfound 族 wrap `ErrNodeNotFound`，httpapi `/api/storage` 旧映射保持 404）；virtual 维持 ErrRepoTypeNotSupported（T-71 接管）。local 路径行为逐位不变（顺序亦同：repo 检查→权限→node）。
- **Put/PutFromBlob/PutLandedBlob**：`refuseNonLocalWrite` —— remote → `StatusError{405, "Remote repository '<key>' is a read-only proxy cache; …", Allow: GET}`（RE-05/M48；cause 仍 wrap ErrRepoTypeNotSupported，T-64 的 landed_blob 旧断言零改动通过）；virtual 维持现状。
- **Delete**：remote → 删**本地缓存**（node 行 + remote_cache 行 + 目录前缀形态），上游零接触（RE-06）；有缓存 204 / 无缓存幂等 404（E-14 语义）；审计 detail `"remoteCache":true`。DeleteRepo 级联时 `engine.Forget`（连接池/offline 窗口/计数）。
- **引擎装配在 repo.New 内部**（架构 §5.4「Get 内分流」的自然结果）：`newService` 构造 `remote.NewEngine(st, md, …)`——cmd 与 adapter 永远看不见引擎，既有 cmd 装配零改动即获得 remote 支持。**构造失败 = 进程失败**：ADR-0012「有行无钥启动 fail-fast」在新 `repo.New`（无 error 返回，M1 冻结签名）下以 panic 表达（对齐 adapter.Register 的「装配期错误启动即炸」先例；exit code 2 + stderr 指名 env，真机验证见下）。备选方案（NewWithRemote 构造器变体交 cmd 调用）会留下其它 repo.New 调用方无 remote 的分叉——**reviewer 请裁决此取舍**（见遗留②）。

### ③ 凭据 AES-256-GCM 全链（internal/remote/credentials.go + service 层）

- `Cipher`：AES-256-GCM、随机 12B nonce、`enc:v1:<base64(nonce||ciphertext+tag)>`；同明文两次密封不同密文（nonce 新鲜）；nil cipher = 无钥态（加密拒收、密文解密拒收、明文读容忍）。
- `LoadKey()`：env `BINFLOW_REMOTE_CREDENTIALS_KEY`（base64 恰 32B；未设=(nil,nil) 合法、设了但坏=错误必炸）。
- **建仓/更新加密入栈**：`parseRemoteConfig` 现返回输入 password（canonical JSON 仍恒不含）；service `sealPassword`——有钥加密入 remote_configs 行；**无钥则丢弃 + WARN**（不落任何未保护字节——T-62 review 的「明文窗口」红线延续；见决策点③）。UpdateRepo 全量替换语义：新 body 的 password（密封后）覆盖旧值，缺 password 即清空（T-80 定案的 PUT 语义）。
- **fetch 解密**：`clientFor` 解密行内密文构造 Basic 凭据（client 只透传，T-65 契约）；解密失败 → 500 类错误指名 env。
- **启动一次性迁移**（FR-15-AC9-④）：`NewEngine` 扫全量 remote 行——明文 + 有钥 → 原地加密（UpgradeConfig）；密文 + 无钥 / 明文 + 无钥 / 密文解不开（错钥）→ 构造错误（即上面的 panic 路径）。
- **日志/回显零明文（NFR-S14）**：GET repo config 掩码不变（T-64 面）；引擎日志字段不含凭据（测试断言）；真机 DB 文件 grep：明文 0 次、`enc:v1:` ≥1。

## 四、规格依据与置信度

- **高置信度直接实现**：六步序与各分支码（repo-semantics §7.2，主干可读）；负缓存 1800/制品 7200/静默 300/超时 15（§7.1 + PRD C4）；401/403 视为 unfound + 摘要（§7.6）；expired-but-serving（§7.2 step 5）；单飞+二次确认+metadata 60s 等锁（§7.3/§7.1）；checksum 后缀逐字文案（§7.2 step 2 + maven-npm-pypi §1.5）；凭据 AES-256-GCM/env/`enc:v1:`/fail-fast/一次性迁移（ADR-0012 决策 4，PRD v1.2 Q1 正式采纳）；故障 404/hardFail 502/静默期（ADR-0012 勘误一，FR-20-AC5 v1.1）；64MB 缓冲型 502（NFR-S13 第 5 点，勘误二③）；DELETE 仅删本地（RE-06/C6）。
- **决策点（已在测试固化，单点可翻）**：
  1. **负缓存与过期副本并存的次请求行为**：六步序把负缓存检查（步 3）置于本地副本（步 4）之前，故「上游 404 + 写负缓存 + 本次回发过期副本」后，**窗口内的下一请求 404**（即使副本还在）——按 PRD/RE-04 字面与步骤序实现并钉板；若 reviewer 判「有副本时不写负缓存」，改动点为 mapUpstreamStatus 的 404 分支一处。
  2. **panic 表达启动 fail-fast**：repo.New 签名冻结（R6）+「New 内自装配」架构口径下的唯一进程级信号；备选（cmd 侧构造器变体）已评估弃用（见①末段）。
  3. **无钥建仓带 password → 丢弃 + WARN**（不拒建仓）：FR-15-AC9 只定义有钥面与「有行无钥重启」面；拒绝会使 T-80 的 M02 用例（带 password 建仓期 200，httpapi 非本票 area）在无钥测试进程里变红。丢弃保持「未保护字节永不落盘」红线，fetch 走匿名。若 PM 定「应 400」，改动点 sealPassword 一处。
  4. **上游 original checksum 只登记不拒**（PRD v1.2 明示 M4 四值策略）与架构 §4.5「Commit(expect) 强校验」草案相抵——按 PRD 基线实现 + WARN 登记，**需 architect 回写 §4.5 措辞**。
  5. **其它 4xx → unfound 不开 offline**（§7.6 该行为中置信度，PRD 未列；见①）。
- **规格待验证**：无（本票无低置信度悬置项；上面 5 个决策点均有明确基线或已注记）。

## 七、双 review 修复记录（REQUEST_CHANGES → 本轮，T-66-review-correctness.md / T-66-review-arch.md 合并裁决）

### B1（正确性）— 单飞等待者不重跑负缓存检查、pass>=1 分支无单飞接触

**缺陷实证**（reviewer 探针 + 复核代码）：步 3 负缓存检查在重试循环**外**只跑一次；等待者被 winner 的 done 唤醒后进入 attempt，负缓存行虽已由 winner 写下却无人再看，flight 又已释放 → 等待者自己成为新 winner 再打上游。16 并发同 404 路径 = 上游被接触 16 次，契约 1 次。叠加 `pass>=1` 分支直接 `contactUpstream`（不持 flight），两处同源。

**修复**（fetcher.go，结构性）：
- 步 3（负缓存）移入 `Fetch` 的重试循环**顶部**——每一 pass 全量重查（负缓存→本地副本→offline 窗→flight）；
- 删除 `pass>=1` 旁路：attempt 的等待分支一律返回 `(nil, nil)`（「有并发 flight 结算，重跑查找」），**任何上游接触只发生在持有 flight 的 winner 路径上**——等待者重跑后要么吃到 winner 的状态（负缓存 404 / 新鲜副本 HIT），要么自己 acquire 成 winner（串行化），不存在无单飞的接触。

**回归钉板**：`TestFetchConcurrent404SingleUpstreamContact`（reviewer 同款探针：16 goroutine 同 404 路径，上游**恰好 1 次**，全员 404 FetchError；窗口期后再请求仍零接触）。原 `TestFetchConcurrentMissSingleFlight`（200 路径 16 并发 1 次）继续通过。

### B2（正确性）— 唤醒后跳过二次确认 + 等待超时不回发旧副本

**缺陷实证**：同源（pass>=1 旁路即「第二等待窗被唤醒后不重查自行回源」，reviewer 实测 winner+1 等待者 2 次接触）；且 §7.1 `metadataRetrievalTimeoutSecs` 的「超时回发旧缓存副本」（§7.3）未实现——超时与 done 走同一条重跑路径。

**修复**（fetcher.go）：
- `waitFlight` 改为返回原因三态（`waitDone` / `waitCanceled` / `waitTimeout`）；done → `(nil,nil)` 重入 attempt **全量重查**（B1 同点）；ctx 取消 → 包装 ctx.Err() 的显式错误；
- `waitTimeout`（metadata 类 60s 上限，`EngineOptions.MetadataWait` 可注入）→ **有旧副本（必然已过期）→ 回发旧副本**（`STALE`、无 UpstreamError 头——锁超时不是上游故障），计数入 stales；无副本 → unfound 404（无可回发物，§7.3 stale 臂为空的诚实读法）。

**回归钉板**：`TestFetchMetadataWaitTimeoutServesOldCopy`（npm 类 .json 路径：过期副本在场 + winner 被 800ms 慢上游阻塞 + metaWait=80ms → 等待者 80ms 超时回发旧副本 `STALE`、上游计数不含等待者、winner 落盘后下一读 HIT）。

### B3（架构）— generic `RepoTypes()` 补 remote

`internal/adapter/generic/handler.go`：`{"local"}` → `{"local", "remote"}` + 注释（remote GET/HEAD 经 service 内引擎、写面 405，本层无感知；virtual 待 T-71）。RepoTypes 为声明性元数据（T-33 裁定/T-48 勘误后零运行时消费者），全模块测试零回归证实。

### B4（架构）— 契约注释三补

`internal/repo/api.go`：① `Service.Get` 契约注释补 remote 分派 + `*StatusError`（unfound 族仍 wrap ErrNodeNotFound）+ `ExtraHeaders()` 结构化提示两点（T-71/T-74 按此编程的锚点）；② `New`/`NewWithClock` godoc 声明 **panic 条款**（凭据启动检查失败即 panic、指名 env、可用 `remote.NewEngine` 预检拿 error 形式）。

### 顺手三项（择易全收）

1. **304 分支保留验证器**：刷新时钟时沿用现存行的 ETag/Last-Modified（P1 条件协商的依赖），不再清空。
