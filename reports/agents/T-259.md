### 1.3 空集形态（任务项 3 的落法）

- **wire 事实先行**（T-254 实现推论，本票验证成立）：对普通用户，filter=manage
  200 ⟺ 覆盖集非空；而覆盖集 = ∪{授 manage 的 target 的 repos} ⟹ **每个授 manage
  的 target 自身必然全落入覆盖集** ⟹ 200 时列表必非空——**200 空数组构造上不可达**
  （等价命题：覆盖集空 ⟺ 403）。「覆盖集为空的 m-holder」在 wire 上就是 403 形态。
- 因此空集 UI 落在 **403 分支的角色分流域**：role=user 的 403 → 友好空态
  「**无管理范围内的权限目标**」+ 指引（覆盖集由携带 manage 的 permission target
  授予；当前会话覆盖集为空；刚获授权请刷新）——L2 收敛本体保留（仍是 empty-state
  卡、表格零渲染、数据面仅一次被拒请求），退役的是 T-241 的「无权限 + API-only」
  边界卡姿态。admin/readonly 的 403（理论态）维持原文案。
- 200 空数组分支按同文案族防御性呈现（构造上不可达，注释钉死该推论）。

## 3. 契约漂移与口径注记

1. **「覆盖集为空的 m-holder → 友好空态」的可达面**（非漂移，钉口径）：E6 下
   覆盖集空 ⟺ filter=manage 403（与无 filter 同形，零可区分面）且 200 空数组构造上
   不可达（§1.3 推论）。故空集 UI 落在 403 分支的角色分流域（文案升级、L2 收敛
   本体保留）。若 conductor/ architect 期望独立的「200 空列表」wire 形态，需先改
   E6 契约（§14.1.6），非本票实现偏移。
2. **任务面「删除覆盖集内 200」**：wire 事实是 DELETE 204（T-241 起既有登记）；
   本票 UI 删除腿走 toast + 列表回流断言，wire 对照腿（DELETE t-out）按 403 断言。
3. 主体/仓库名手动录入的存在性校验全在服务端（unknown → 400）：UI 不做客户端
   白名单预检（§14.1.6 name-entry 形态即「服务端终裁」；E2/E5 枚举闭集不开放）。
4. m-holder 编辑器会话对三个枚举端点各发一次 403 请求（驱动 forbidden 分支的
   四态事实）——本票网络断言只钉列表面（filter=manage 恰 1）；编辑器面未设请求数
   帽（无 PRD 预算句），如需收敛为「role=user 时跳过枚举请求、直呈手动录入」，
   属行为微优化，另议。
