## 1. 做了什么

### D1 — failed 终态任务的 cron 复活（AC ①）

- **根因**：T-162 的 drain 候选只收 `attempts < 6` 的 failed 行；退避烧满（6 次、~31s）后任务永久终态，目标恢复也无人再扫（T-175 H42④）。
- **修复**（`engine.go`）：
  - `EngineOptions.MaxRevives`：复活预算。**0=默认（无限）**、负数=禁用（T-162 行为）、正数 N=最多 N 次复活（总尝试上限 = 6+N）。默认无限的依据：PRD FR-57-AC4「恢复后定时 cron 增量复制兜底补齐」无期限措辞 + Artifactory 事件复制无限重连（replication.md §4.3 `eventBased.connection.maxDelay=30min`，置信度中）。
  - `EngineOptions.ReviveDelay`：failed 任务按 `completed_at` 计龄的最小复活间隔，默认 **5m**（对齐 architecture §8 `replication.task_retry_delay_seconds: 300`）。每个复活只买**一次**尝试（不重跑整个退避循环），死后目标的开销 = 每任务每 5m 一次探测，不放大 O4 背压。
  - **确定性失败与瞬态失败的区分**（无 schema 变更）：`ErrNotRetryable` 的文本 `"...failure is not retryable..."` 自 T-162 起就写进每条 not-retryable 任务的 `last_error`；drain 的 `revivable()` 以该子串为「终态标记」——冲突/配置错误/源事实丢失永不复活，退避烧尽的瞬态失败可复活。存量 DB 行为兼容。常量 `notRetryableText` + 单测钉死组合关系。
  - `completed_at` 为 RFC3339 秒精度：复活判定最多提前 1s 触发——对限速器无害（注释 + 测试说明）。
- **测试**：`TestCronRevivalAfterBackoffBurnout`（六连 500 烧满退避 → 目标恢复 → 第七次 PUT 复活成功；烧穿终态以 audit 台账 push.failed→push 证明，避开秒精度轮询竞态）、`TestCronRevivalGates`（四臂：not-retryable 标记阻断 / 未到期不复活 / 有限预算耗尽 / 负值禁用）、`TestNotRetryableMarkerComposition`；原 `TestCronSweepProcessesResidue` 的「exhausted stays terminal」臂改为 not-retryable 语义。
- **实测复活证据（真实部署）**：§4 的双实例冒烟中，npm tarball 任务对「目标仓未建」烧满 6 次后，建仓即被 cron 补投成功（status 里 `success attempts=6`）。

### D2 — docker 面协议化推送（AC ②）

- 新增 `push_docker.go`：按源仓 package_type=docker 分流。
  - **blob 任务**（`<image>/blobs/<hex>`）：`HEAD /v2/{targetRepo}/{image}/blobs/sha256:<hex>` 幂等探测（Docker-Content-Digest/X-Checksum-Sha256 对比）→ 单请求整体上传 `POST /v2/{targetRepo}/{image}/blobs/uploads/?digest=sha256:<hex>`（DE-02 单回合臂，流式不缓存）。
  - **manifest 任务**（`<image>/manifests/<hex>`，由新增的 PutManifest 挂钩产生）：`PUT .../manifests/sha256:<hex>`（Content-Type = 节点行存储的 mime，缺失时回退 body 的 `mediaType` 成员）→ 逐 tag `GET .../manifests/<tag>` 对比 digest 后按需 `PUT` 重指。**tag 指针是元数据非内容：源权威、可重指**（Q7 first-write-wins 管字节不管 tag 解析）。
  - FIFO 任务序（layer/config ← PutLandedBlob 挂钩、manifest body ← Put 挂钩、manifest 节点 ← PutManifest 挂钩）天然满足目标端引用完整性门；崩溃窗口内 400 MANIFEST_BLOB_UNKNOWN 按可重试处理，下一轮 drain 自愈。
  - `classifyV2`：400/405 终态；401/403/404(NAME_UNKNOWN)/5xx 可重试（配合 D1 复活收敛）。

### D3 — npm 面语义裁决 + 实现（AC ③，裁决记录见 §3）

- 新增 `push_npm.go`：**不走特权 raw-node 面**，走 npm 协议自身的 publish + dist-tag 面（裁决理由见 §3）。
  - 任一 npm 任务（tarball 或 packument 节点）归约出包名 → 整包收敛：读源 packument 节点（存储态、协议中性）→ GET 目标 packument（404=空）→ 对目标缺失的 version 逐个 PUT 单版本 publish 文档（tarball 以 base64 内联 `_attachments`，目标端复验 dist.integrity/shasum 并合并进 packument，**不整体覆盖**）→ 对漂移的 dist-tag 逐个 `PUT /binflow/{repo}/-/package/{name}/dist-tags/{tag}`（JSON 字符串体）。
  - tarball 任务先于 packument 落盘触发（publish 第 9/10 步之序）：源 packument 尚不可见时按**可重试**处理（非终态），退避后收敛；packument 引用的 tarball 缺失才是终态（真损坏）。
  - 读上限：packument 64MB / tarball 256MB（npm 协议本身要求 tarball 内联，目标端 publish 上限 512MB）。

### D4 — PutLandedBlob 链挂钩（AC ④）

- `internal/repo/service.go`：`PutLandedBlob` 与 `PutManifest` 链末（audit 之后）同样调用 `notifyReplicator`（与 `PutWithOptions` 对齐：detached ctx + 独立 goroutine + recover 护罩，非阻塞）。前者覆盖 docker layer/config finalize 与 pypi 上传（T-175 D4 零任务根因），后者产生驱动 /v2 manifest+tag 推送面的任务（tag 重指也会再触发 → 目标 tag 再收敛）。

### 协议面分流与元数据缝

- `meta.go`：消费侧接口 `MetaSource`（PackageType / Node(mime,sha256) / DockerTags），`StoreMetaSource` 基于 `metadata.Store` 实现（引擎不新增 principal、不经权限面读自身元数据）；`ErrMetaNotFound` → not-retryable。
- `engine.go` `pushOnce`：按源仓 package_type 分流 docker/npm/pypi，**其余（generic/maven/未来纯路径类型）走原 generic REST 面**（QA 已验证路径，零回归；集成测试在满适配器栈上重新钉死）。无 MetaSource 时全部走 generic（T-162 行为）。包类型按 drain 单 goroutine 访问的 map 记忆化。
- 共享助手：`targetBase`（配置校验抽出）、`planeURL`（内容面寻址）、`readAllBounded`（带上限整读）。
- `push_pypi.go`：`<name>/<version>/<filename>` → 裸内容路径 HEAD 幂等探测（同 sha=成功；不同=Q7 冲突终态）→ 仓根 multipart POST（`:action=file_upload`/name/version/sha256_digest[/md5_digest] + content 文件 part，io.Pipe 流式不整存内存）。simple 索引由节点派生，落文件即全量可达。

## 3. D3 语义裁决记录（报告留存，待 PM/用户终裁）

**问题**：replica 仓只读（PUT 405）是 Q6 暂行口径的安全面；复制引擎作为系统内部推送是否豁免只读/协议限制，走「带系统标记的内部上传面」？

**裁决：不设特权面，走 npm 协议自身的 publish + dist-tag 面。** 理由：

1. **QA D3 的 405/400 根本不是 Q6 的只读门面**——QA 推的是目标端 local npm backing 仓；405「tarballs are read-only」与 400「invalid dist-tag body」是 npm 适配器的**协议不变量**（tarball 与 packument 只能以 publish 文档成对写入）。Q6 的 virtual 只读门面与复制通道无关：引擎寻址的一直是 backing local（与 generic 面同落点），「只读豁免」问题在本故障上不成立。
2. 特权 raw-node 面会新增一块安全面（绕过 tarball/packument 配对与完整性校验），而 npm 状态完全节点内驻留（dist-tags 在 packument 文档里），协议面方案可以完备收敛，收益配不上风险。
3. 协议面方案保持一条不变量：**复制目标收到的一切都经过与真实客户端相同的校验**（integrity/shasum 复验、版本合并而非整体覆盖——目标侧用户自发布的版本不会被复制冲掉，这也顺带化解了 Q7 在 npm 面的冲突形态：同版本不同内容 → 目标 403 → 引擎记 not-retryable 终态，目标不动）。
4. ADR-0021 决策 2 的「传输协议：HTTP（目标 BinFlow 实例的 REST API）」措辞涵盖协议端点；Q6 终裁若改仓库模型，切换位仍在引擎寻址处（T-162 已预留的判断不变）。

**标注**：若终裁倾向特权面（如运维要求复制不占 publish 语义/审计），实现位在 `push_npm.go` + 目标侧新增内部端点，本票结构可平移。docker/pypi 面无此争议（协议面是唯一正确寻址）。

## 6. 偏差与越区说明

- **cmd/binflow-server/main.go 一处接线**（EngineOptions.Meta）：area 外但必要——不接则协议面在生产不生效。改动一行 + 注释，无行为面变化。
- **复活判定基于 last_error 文本标记**：009 schema 无终态分类列（加列需 internal/metadata 迁移，越区）；标记自 T-162 起稳定写入，单测钉死组合。若后续终裁引入 `skipped`/conflict 状态词（T-175 D9），切换点在 `revivable()` 与 not-retryable 写入处。
- npm tarball 以 base64 内联（协议要求）：引擎内存上限 256MB/包；超限任务终态报错。
- `MaxBandwidthBytesPerSec`/`MaxItemsPerPush` 仍未消费（沿 T-161/T-162 遗留）。
