## 做了什么（对照 AC）

### AC① start_tls 真实接线（D5）

`internal/auth/ldap.go` `NewLDAPProvider`：

- URL scheme 解析 + fail-fast：非 `ldap`/`ldaps` 拒构造（原来到首次 dial 才炸）。
- **单一生效 TLS 配置**：`cfg.TLSConfig` 为 nil 时从 URL host 构建（`ServerName`、`MinVersion=TLS12`）；非 nil 时 Clone 后合并——绝不改调用方的 config。**修掉一个真实 bug**（wire 测试抓出）：caller 提供 TLSConfig 且未设 ServerName 时，StartTLS 会握手失败（`tls: either ServerName or InsecureSkipVerify must be specified`）——ldaps:// 走 `tls.Dial` 能从地址推导 ServerName，而 StartTLS 包的是既有连接、Go 无法推断。现在统一在 merge 时补齐。
- **StartTLS 升级在 dialer 内**（ldap:// + start_tls=true）：每个新拨连接先升级、成功才进池——service bind 的凭据不可能明文出网。升级失败（目录拒绝/证书不信）→ 关连接 + 返回错误，**绝不静默回落明文**。
- **互斥语义**：`ldaps://` → 隐式 TLS（scheme 拥有加密），此时 start_tls=true 被忽略并打 WARN（`auth: ldap start_tls is ignored for ldaps:// URLs…`）。依据 PRD FR-55 原文「start_tls：默认 false；`ldaps://` 时忽略」（高置信度）；RFC 4513 StartTLS 扩展的是明文会话，go-ldap 对已加密连接会拒绝升级（"already encrypted"）。
- `DialWithTLSConfig(tlsConf)` 从条件追加改为恒定追加（对 ldap:// 无效果，go-ldap 只在 ldaps 分支用它）——两条 TLS 腿共享同一验证姿态。

### AC② skip_tls_verify / group_base_dn 键落地（D6）

- `internal/config`：raw 段 + build 映射 + `LDAPConfig` 字段（沿 T-179 模式；YAML-only，env 覆盖不在本票范围，与 T-179 遗留③一致）。
  - `auth.ldap.skip_tls_verify`（默认 false）；`auth.ldap.group_base_dn`（默认空 = base_dn）。
- `internal/auth`：`SkipTLSVerify` 并入 TLS 配置的 `InsecureSkipVerify`；启用时构造期打一条 WARN（`evaluation only, never use in production`，NFR-S36「仅限评估，生产必须 false」）。`GroupBaseDN` 空 → `defaults()` 回填 `BaseDN`；`searchGroups` 以 `GroupBaseDN` 为搜索基（PRD FR-55 步骤 5「搜索组：group_base_dn + group_filter」）。
- 严格解码器：两个新键精确拼写（`skip_tls_verrify`/`group_base_dns` 拼错仍拒启，测试钉死）。

### AC③ TLS 三态测试

新增 `internal/auth/ldap_tls_test.go`（约 700 行），两层证据：

1. **wire 层**（真 BER over TCP，真 TLS 握手，走真 `DialURL`/`StartTLS` 路径——接口 mock 看不到这些）：`tlsLDAPServer` 用 asn1-ber（go-ldap 自身依赖，**零新模块**，go.mod 仅从 indirect 提升）手写最小 LDAP 服务端：simple bind / search(entry+done) / unbind / StartTLS 扩展操作；单实例同时持有明文与 TLS 两个 listener；自建测试 CA + 服务器证书（SAN `localhost` + IP `127.0.0.1`——测试拨 127.0.0.1，ServerName 来自 URL host，IP SAN 才是命中的那条）。`TestLDAPProviderTLSPostures` 8 行 table-driven：
   - ldaps 信 CA 成功 ✅ / ldaps 不信 CA 拒绝 ✅ / ldaps + skip_tls_verify 自签可用 ✅
   - ldap + start_tls 升级成功 ✅（**服务端 upgrades 计数 >0** 钉死「StartTLS 真的做了」；bind 全部带 `@tls` 标记，无明文 bind）
   - start_tls 不信 CA 拒绝 ✅ / start_tls 被目录拒绝 → fail closed ✅（拒后零 bind 零流量）
   - ldaps 压过 start_tls ✅（upgrades=0 且无加密连接上的扩展请求）
   - 纯明文（不设 start_tls）照常工作 ✅（操作员显式选择，回归护栏）
   - `TestLDAPProviderGroupBaseDNOnTheWire`：服务端记录的搜索基同时出现 `base_dn`（用户）与 `group_base_dn`（组）。
2. **dialer 层**（接口 mock，`mockLDAPConn` 增加 startTLSCalls/Config/Err 记录）：升级何时发生（ldap✅/ldaps❌/无 flag❌）、失败关连接（不进池）、skip_tls_verify 并入升级配置（InsecureSkipVerify 断言）、MinVersion≥TLS1.2、GroupBaseDN 三态（空默认/专用基/基外组不可见）、两个 WARN + 干净姿态静默（slog 捕获，沿 hygiene_test.go 先例）、URL scheme fail-fast。

`internal/config/auth_ext_test.go`：全段解码含新键（字段级 DeepEqual）、新键默认值（false/空）、两个拼写错误拒绝。

### AC④ H35 断言形态更新（供 QA 复验）

T-174 H35 原观测「ldap:// + start_tls: true（无 CA）→ 200 登录成功」是 D5 假阳性。**新预期**：

| 配置 | osixia 自签证书（未导入系统 CA） | 预期 |
|---|---|---|
| ldap:// + start_tls=true + skip_tls_verify=false | 握手拒绝 | **401**（不再是假阳性 200） |
| ldap:// + start_tls=true + skip_tls_verify=true | 跳过验证 | 200 + 启动 WARN 一条 |
| ldap:// + start_tls=true + CA 已 `update-ca-certificates` | 验证通过 | 200（bind 密文） |
| ldaps:// + start_tls=true | start_tls 忽略 | WARN 一条 + ldaps 正常语义 |

复验环境注意（T-174 §1/§2 已记）：osixia 需 `olcTLSVerifyClient: never`（否则 Go 客户端一律 EOF）与 ACL `by users read`。
