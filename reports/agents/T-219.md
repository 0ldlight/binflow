### 2. auth 层（internal/auth/stepup.go 新文件 + Principal.SessionHash）

- **mint grant 台账**（进程内存，ADR-0027 决策 4：单实例事实、重启丢失=重走 re-auth、零 schema）：
  - `IssueStepUpGrant(ctx, username, sessionHash, ttl)`：32 字节 crypto/rand（256-bit，hex 64 字符），**只存 sha256**；绑定 {username, session_id}；签发时顺带清扫过期项。
  - `ConsumeStepUpGrant(grant, username, sessionHash)`：**值命中即删（burn-on-presentation）**——复用、错绑定、过期一律烧掉，不给第二次机会；过期/绑定不符 → false。
  - `New()` 初始化台账指针；`With*` 克隆共享同一台账（一个进程一本账，cmd 接线零变更）。
- **口令腿** `VerifyStepUpPassword(ctx, username, password)`：按 **users.provider 行**选腿——local → 门控 argon2 校验（复用 `s.VerifyPassword`，T-192 hashGate 同一门）；ldap → 复用既有连接器 `Bind` + `Resolve(provider_id)` 反查必须是本人（无 auto-create：step-up 调用者必有行）；oidc/其它 → 拒（腿不符）。所有失败 wrap 新哨兵 `ErrStepUpInvalid`（含目录停机：与登录面同姿态——对外统一 401、原因留服务端日志）。
- `Principal.SessionHash`（session 臂携带 web_sessions 行的 sha256——存储摘要非 cookie 明文）：authenticateSession 填充，grant 双向绑定用。

### 3. httpapi 门 + OIDC 流（internal/httpapi/stepup.go 新文件 + security.go/oidc.go）

- **触发**（决策 1 逐字）：`auth.token_step_up` ∧ `p.ViaSession` ∧ 非 admin（= `CanManage(security:write)` 判定，见 §2-T-215 移交）。豁免：admin session、Basic、Bearer/API-key、`/v2/token`、匿名（路由 401 在前）。
- **腿选择**（决策 3）：`Principal.Source`（session 臂=行 provider）。local/ldap → body `step_up_password`（缺→401 `step_up_required`；验败→401 `step_up_invalid`）；oidc → body `step_up_grant`（同分法）。**错腿凭据忽略**（所欠凭据缺失 → step_up_required）。两字段 form+JSON 双形态；不触发的请求不解析、不要求（wire 向后兼容）。
- **错误体**（决策 5 逐字）：`{"error":"step_up_required","error_description":"step-up authentication required to mint a token"}` / `{"error":"step_up_invalid","error_description":"step-up credential rejected, expired, or already used"}`（既有 OAuth 形通道）。
- **门位**：请求形态校验之后、subject/TTL 护栏之前（assurance 先于 authorization——未验 session 不泄露 403/401 护栏状态）。
- **facet 发现**：`Deps.Auth` 断言 `stepUpRegistry`（与 sessions/permView 同款）；缺失 + 开关 on → fail-closed 401 step_up_required。
- **OIDC `purpose=step_up`**（决策 4）：
  - login init：`?purpose=step_up`（未知 purpose 400）要求**活动 session**（401 fail-early，省 IdP 往返）；authorize URL 强制 `prompt=login`（OIDC Core 标准参数）；purpose 存 tx cookie 第三段（`state.verifier.purpose`，plain login 尾段空——HttpOnly 回读，不可外部伪造）。
  - callback：purpose=step_up → **不建新 session**；session principal 与 re-auth（ID Token 经共享 OIDC Bearer 臂）**必须同人**（不同人 → 401）；签发 grant 绑 {username, sessionHash}，TTL=config；302 `/binflow/ui/#step_up_grant=<grant>`（**fragment 承载**——不进服务端/代理日志；query 形态弃用）。
- **审计**（决策 7 逐字）：`token.issue` detail 增 `step_up: true` + `step_up_method ∈ {password, oidc_reauth}`——**仅 step-up 路径出现，豁免臂不写**（omitempty 落实）。票据任务文写「second_factor 维度（password|id_token|mint_grant|none(<reason>)）」但明示「具体拼写对齐 ADR-0027 终版」——终版拼写即 `step_up`/`step_up_method` 且值域 {password, oidc_reauth}（本地+LDAP 同为 password 腿；PRD v1.1 §FR-68 同），按 ADR 执行并在此登记。

### 4. T-215 移交项（token handler p.Admin → CanManage）

security.go 两处 `!p.Admin`（为他人铸 token 的 403 门 + 非 admin TTL 帽）统一为一次 `managementAllowed(Authz, CanManage(CapSecurityWrite))`，判定结果 `adminMinter` 同时用作 step-up 豁免。三角色逐字等价（CapSecurityWrite 仅 admin 持有；readonly_admin 只读、user 全无）——Q11 四护栏语义零变。revoke 判定：路由门 T-215 已迁 `CapSecurityWrite`（router.go），handler 内无裸 `p.Admin`，本票核验零残留。

## 四、规格对齐与自由度登记

- ADR-0027 决策 1~7 逐条落地（作用域/腿选择/grant 契约/错误体/config/审计）；错误描述逐字采用决策 5 文案。
- auth-model §3.7：Artifactory API 层无二次认证（UI 邻近面 `X-JFrog-Reauthentication` 属 profile 解锁族）——**未抄**；本特性即规格明示的「BinFlow 自有超集」路径，docker /v2/token（Basic 支撑）零影响已实测。
- **两处 ADR 未规定面的自选**（低置信自决，登记待 review）：
  1. grant 回传 console 的载体 = redirect **fragment**（ADR 仅言「302 回 console 铸造页」）——fragment 不进服务端/代理日志，SPA（T-218/T-225 面）读 location.hash 后入 body；若 review 裁 query 形态需改一行。
  2. 错腿凭据（如 OIDC 用户交 step_up_password）按「所欠凭据缺失」→ step_up_required 而非 step_up_invalid（ADR 只定义缺/败两分；此读法不泄露腿探查信息）。测试已固化该行为（t219 两处用例）。
- 交接面：console 铸造页交互（二次密码框 / 401 后引导 re-auth 流回跳续铸）= T-218/T-225；QA 矩阵 V21~V26 脚本化 = T-224（本文 §三 的 curl 序列可直接改写）。
