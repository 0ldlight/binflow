### 关键决策（reviewer 请重点看）

1. **同源双闸**：①fixtures 由 Go 表生成（`--check` 漂移即红）；②parity spec 逐条断言 TS 实现。无后端端点（ux R8 定案），漂移在 CI 两层可红。fixtures 生成 `.ts` 而非 `.json`——避免动 T-89 的 tsconfig（resolveJsonModule）。
2. **users 写面分工**：建用户走 PUT（create-or-replace，口令必填）；编辑/组员/口令重置走 POST 部分更新（指针语义：仅携带改动字段；`groups:[]` 显式清空≠未提及）。改密入口落 POST password（admin 路由无需旧口令——security.go handleUserUpdatePost 直 HashPassword+UpdatePassword）。
3. **无动作主体不提交**：矩阵中 r/w/d 全空的主体从 POST body 剔除（空动作 ≡ 未授权，后端会建零权限行）——「撤销全部动作 = 移除主体」的 UI 语义。
4. **W33c 409 呈现走行内冲突面板而非重开确认框**：解除路径是「跳去编辑器改 target」，留在对话框里给链接是死路；面板带服务端原文（mono）+ 解析出的 target 链接 + 稍后再试。
5. **403 收敛按 §3.6.3**：L2 三页各自 empty-state 无权限卡（缺省锚，scope 到页面根）；L4 创建/删除按钮仅 admin 渲染（whoami 预收敛）；数据卡零 admin 位硬编码。
6. **行级详情 N+1**（users 列表 admin 位/组员）：管理面用户量级小，对齐 T-99 usage 先例独立到达；副作用见观察项 1。

## 契约漂移（与文档/规范不一致处，供 conductor 逼回写）

1. **用户「禁用」与「删除」无 API 面**：AC③ 要求用户页「建/禁用/改密入口/删」，但 SE 域 users 仅有 GET/PUT/POST（router.go 434~449 行）——无 DELETE 用户端点，禁用位（`internalPasswordDisabled`/`disableUIAccess`）是 userDetail 回显字段且后端恒 false（security.go 493~501 行从不置位）。UI 不伪造入口，详情页给只读说明（清组员+撤 target 授权的替代路径）。需 PM/architect 裁决：补端点或修订 AC。
2. **`PUT /api/repositories/{key}` 建仓回 200 非 201**（repositories.go 374 行 `writeText(w, http.StatusOK, "Successfully created…")`）——「更新成功」与「创建成功」同为 200。与 users/groups 的「建 201」惯例不一致；E2E 按 200 断言（后端事实优先）。
3. **`GET /api/v1/permissions` 无单查端点 + 无时间戳**：编辑器从列表过滤；ux §4.9 列表行「更新时间」列无法呈现（permissionBody 无该字段）——已降级缺列，需后端补字段才可加。
4. **组无 admin 位（有意不兼容）在 UI 的呈现**：用户行 admin badge 只来自用户自身位（FR-27-AC9），组行无任何 admin 语义——符合预期，无漂移动作，仅备案。
5. **观察项（非本票面）**：users 列表行级详情 GET 在页面导航中被浏览器取消时，后端把 `context canceled` 记成 500+ERROR（access log `client_disconnect:true`）——客户端不可见、无用户可见错误；建议后端把 ctx 取消映射为 499/WARN（dev-go-core 面）。
