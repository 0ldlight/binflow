## 一、做了什么

### 1. routeAuth 能力化迁移（30 处全量，严格照 §7.1 清点表）

`routeAuth{admin bool}` 字段删除，替换为 `manage auth.ManagementCapability`（全局能力门）与
`repoManage *repoManageGate{repo, write}`（仓库域门，struct 承载防止 repo/write 拆散错配）。
`authorize()` 判定序不变（401 → 门位 → 内容 action）；门位经 `ManagementAuthorizer` facet
（消费侧类型断言，T-212 留缝）走 `auth.CanManage/CanManageRepo`；**无 facet / nil authorizer
一律 fail-closed**（守卫测试钉死）。403 文案沿用 `administrator privileges required`
（rest-api §1.4 既有面、t190 断言零改动；rbac.go 把 400/403 文案裁量权留给本票，取连续性）。

### 2. adminRole wire（FR-64，ADR-0026 决策 6）

- `PUT|POST /api/security/users/{name}` 与集合 POST 三臂 body 增 `adminRole`（camel ↔ DB `role`
  一处映射，quotaBytes→quota_bytes 先例）；值域 = `auth.ParseRole` 闭集（kebab 拒绝）。
- **冲突 400 纯文本**：`admin=true ⇔ adminRole=admin`，任何不一致（含 admin 缺省=false 配 adminRole=admin）
  → 400 `conflicting 'admin' and 'adminRole' fields: …`；未知值/kebab → 400 `unknown adminRole …`。
  T-212 review 移交②（metadata.Create 矛盾输入）由此在 handler 侧杜绝：`resolveCreateRole`
  校验通过后传库的 Role/IsAdmin 对不可能矛盾。
- **写入路径**：create 臂 Create 带 Role；replace/partial 臂 UpdateProfile 后 `SetRole` 收尾
  （SetRole 单语句写 role+is_admin 镜像，是 readonly_admin 的唯一可达写缝——布尔 CASE 表达不了它）。
- **回显**：GET 单查 `userDetail.adminRole`（DB 值经 `roleFromStored` 归一）；whoami/session 登录体
  `sessionWhoami.adminRole`（`p.EffectiveRole()`，ADR「whoami/session 同名回显」；T-218 控制台消费）。
- **即时生效**：T-212 的 Verify/Session 同缝重查 role + 本票 REST 写入走 SetRole —— 同一 Bearer
  token 403→200→403 三段实测（Go 测试 + 真实栈 curl 双证）。
- **越权**：readonly_admin/user 写 adminRole → 路由门 `CapSecurityWrite` 403（security:write
  admin-only 是 ADR-0026 不变量 1，无需 handler 二查）。

## 六、返修轮（correctness review B1 + N1，2026-08-23 第二轮）

**B1（测试缺口，红绿实证）**：族 6 建仓臂 `CapRepoWrite` 分支（repositories.go handleRepoPut
create arm）原先无判别性覆盖——全套零 m-holder 夹具，readonly_admin/普通用户的 403 全来自族 7
路由门，到不了该分支（reviewer 删分支后全套仍绿，属实）。

**可达性分析**（补测试的依据）：`targetListsRepo` 是 **精确成员匹配**（slices.Contains，无通配），
m-holder 要过 PUT 的路由门（repoManage write = Can(m)），其 target 的 repos[] 必须逐字列出所建
key——REST 建 target 时校验 repo 存在，故唯一活路径是 **target 先列一个已存在的仓、再删掉该仓**
（target 行无级联，删除仓后存活）：key 在覆盖集内、在 store 外，PUT 即建仓臂。今天
repo.Service.CreateRepo 的 requireAdmin 二道门兜底（无活提权），T-217 放宽 service 门后本分支是
建仓臂唯一守门——即本测试钉住的防线。

**新增** `internal/httpapi/t215_create_arm_gate_test.go`（TestT215ManageHolderCreateArmStaysAdminOnly，
夹具经 metadata 缝：`PutTarget` + `PermissionPrincipal{CanManage:true}`，REST 面到 T-217 才收
manage 字母）：
1. m-holder GET /api/repositories/{existing} → **200**（路由门 m 求值放行——夹具活性证明）+ 普通用户
   同行 → 403（对照腿，证明 200 来自 m）；
2. m-holder PUT /api/repositories/{ghost}（target 列名、仓已删）→ **403**，且 envelope message =
   `administrator privileges required`（**门源判别**：本分支的 gate 文案；service 兜底文案为
   `admin privileges required: permission denied`——删分支即翻红的那条断言）； denied 后 GET → 404（零副作用）；
3. m-holder 自取 `?permissions` 视图（路由门 m 放行、路径探针用同行 r 位）→ 200 且其字母集 =
