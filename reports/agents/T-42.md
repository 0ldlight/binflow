## 一、做了什么

### AC ① O3 旗标补齐

1. **`gc -c <yaml>`**：runGC 增 `-c` 旗标，直接复用 serve 的 `loadServeConfig` —— 解析语义完全一致：
   - 显式路径必须存在（`-c` 缺文件 → `config file <path>: stat ...` fail-fast，不静默回落默认值）；
   - 缺省回落链 `./binflow.yaml → $BINFLOW_HOME/binflow.yaml → defaults+env`；
   - `resolveHome`（`./data` → `$BINFLOW_HOME/data`）随之生效。
2. **`--grace-hours`**：与 `--grace-days` 并存。优先级裁定：**两者同给时 hours 胜出**（hours 是同一覆写的严格更精确拼写，days*24 恒可被 hours 表达，无歧义可拒）。负值拒绝（两旗标同规则）；0 = 用配置值（与既有 `--grace-days 0` 语义一致）。注意 flags 只能覆写**变大变小都行**，但 storage 层 `grace<=0 → DefaultGCGrace(24h)` 的零值语义不变（架构 §4.4 回写项 J）。
3. usage 文本更新（`--help` 列出三旗标）。

### AC ② GC mark 集合 = nodes ∪ docker_refs

- `distinctNodeChecksums` 重写为 `liveChecksumSet`，返回 `map[string]struct{}`（原来 []string + seen 去重是给集合回调前的中间形态，直接产集合更省一次拷贝）。
- nodes 半边：不变（Repos().List → 每仓 Nodes().ListByPrefix）。
- docker_refs 半边（本票新增）：每仓 `Docker().ListImages(repoKey, "", 0)` → 每镜像 `ListManifestsByImage` → 每 manifest `ListRefsByManifest`，聚合 `BlobDigest`。docker_manifests.Digest 与 Blob.Sha256 同 keyspace（api.go 注释明示 bare hex sha256），UNION 直接可并。
- **为什么不用 `RefsByBlob`**：它是 (repoKey, blobDigest) 二参 EXISTS 查询（删 blob 前置检查用途，idx_docker_refs_blob 服务对象），mark 用它 = 每个磁盘 blob 一次反连接查询 —— 正是 T-9 集合形回调废弃的反连接逐条路线。任务书授权「接口不敷用可在调用侧聚合，不改 metadata 包」，聚合是正确选择。
- **为什么不能用 `BlobStore.FilterUnreferenced`**：M1 起它已是的对账路径（架构 §3.2 注），且它只反连接 nodes、看不到 docker_refs 存活事实（其 SQL 无 FROM docker_refs），语义就不对。
- 语义澄清（重要）：nodes 与 docker_refs 的「每仓枚举」走 Repos().List 仓库集合 —— refs 不会超出仓库集合（删仓级联调 DeleteRepoRefs，metadata/doc.go 一致性契约）。PutRefs 的调用形态是「先 PutManifest 再 PutRefs」（T-35 服务层定约），因此 ListImages→manifests→refs 的聚合能覆盖所有合法 refs 行；纯 refs 行而无 manifests 行是契约外孤儿态，不在 GC 保护范围（对齐 doc.go「孤儿 tag 由服务层删除顺序防、QA 覆盖」的同类定界）。

### AC ③ 测试 + 真栈冒烟

## 四、发现与口径（供 review / conductor）

1. **子命令 `--help` 退出码现状**：`run()` 对 `flag.ErrHelp` 只抑制错误打印，`main()` 仍 `os.Exit(1)`；ContinueOnError 的 FlagSet 遇 `-h/--help` 返回 ErrHelp → run 返回 → main exit 1（实测 `gc --help` 与 `serve --help` 均 exit=1，冒烟第 8 步显示 exit=0 只是 shell 管道取了 head 的退出码）。这与顶层 `binflow-server --help`（exit 0）不一致。**未改**：M1 既有行为面、超出本票 AC（O3 只要求「正常」= 能解析出旗标清单），改它要动 run() 分发层 —— 记录为观察项，转 conductor 决定是否开收口票（建议：subcommand help 也走 usage 路径 exit 0，一处三行改动；serve/gc 两处同修）。
2. **`gc --grace-days 0` 语义**：0 = 用配置值（正）；storage 层 grace<=0 → 24h 默认。两层叠加后「配置零值 + 旗标零值」= 24h，不是立即回收 —— 与架构 §4.4 回写项 J 一致，测试固化。
3. **env > YAML 优先级对 -c 测试的影响**：config.Load 的环境变量覆写优先于 YAML 值（BINFLOW_STORAGE__DATA_DIR 盖掉文件 data_dir）。gc -c 与 serve 同源同行为，不是回归；测试注释已写明防后人踩坑。
4. **docker_refs 聚合的枚举面**：走 Repos().List 的仓库集合；「refs 行存在但仓已删」理论上不可达（删仓调 DeleteRepoRefs），若真发生（契约破坏）该 refs 行不进 mark —— 与 metadata/doc.go 定界一致（此类行是垃圾，GC 恰好应回收其 blob）。
