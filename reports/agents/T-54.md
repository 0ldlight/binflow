# T-54 — F1 压测定位：TestV2ManifestConcurrentTagOverwrite 全仓并行负载下偶发 layer 500

- role: dev-go-core
- 日期: 2026-08-19
- 票据: T-54（源: T-43 QA 报告 F1 节，m2-done 前须定论）
- 结论先行: **F1 已定论并修复**。根因 = 假设 (a) SQLITE_BUSY 逃逸 busy_timeout（证据确凿，成功复现 5/8 轮并抓到服务端 ERROR 原文）；假设 (b) 映射面确有缺陷（busy 不该 500 UNKNOWN）已一并修；假设 (c) harness 冲突不成立，但 harness 的**取证盲区**（错误 body 被丢弃 + 捕获型 logger 吞掉服务端日志）是 QA run-1「无 ERROR 行」的原因，已补。
- **附带发现并修复（第二根因）**: `-count>1` 口径暴露 `anonSeedOnce` 进程级缓存跨迭代污染——`TestV2TokenAnonymousBothModes` 隔离重跑 19/20 FAIL（非负载 flake，是确定性隔离缺陷），不修则本票的验证口径（count=5 ×2）无法闭环。
- **附带发现并修复（第三根因，harness 类）**: `TestSingleflightExecutesOnce` 设计性死锁（fn drain 到达通道依赖「全员并入首个 flight」的假象）——定论 RUN-2 中挂死 33m54s 触发 storage 40m 包超时。纯测试文件修复（3.6 节）。
- **定论**: 修复后 `CGO_ENABLED=1 go test -race -count=5 -timeout=40m ./...` **连续两轮 12/12 全绿**（RUN-3/RUN-4，第 4 节）。核心修复集已由主会话提交（f21904b）；storage 测试修复与本终版报告为工作树待提交增量。

## 1. 复现（step 1）

手段: 临时诊断测试（同 20-writer 场景，失败时读响应 body + dump harness 捕获日志），`GOMAXPROCS=2` CPU 过订阅 + 双 race 测试进程配重，模拟全仓并行负载。

命令:

```
CGO_ENABLED=1 GOMAXPROCS=2 BINFLOW_T54_REPEAT=8 go test -race -run 'TestT54Diag' -count=1 -v ./internal/httpapi/
```

结果: **8 轮中 5 轮 FAIL**（round0/2/5/6/7）。决定性日志（harness 捕获型 logger dump 出的服务端行）:

```
level=ERROR msg="docker: blob node registration failed" repo=docker-local digest=9b9c979f... denied=false
  error="blob row 9b9c...: metadata: blobs put (9b9c...): database is locked (5) (SQLITE_BUSY)"
level=ERROR msg=access method=POST path=/v2/docker-local/acme/race/blobs/uploads/ status=500 duration_ms=13786
```

关键量化: 失败请求总耗时 **13.7~14.5s**（access 行 duration_ms），其中 blobs put 的 busy 等待烧完 5s 预算后以 SQLITE_BUSY 失败 → repo.Put 失败 → `writeBlobCreated` 渲染 500 UNKNOWN「blob stored but its repository record could not be written」。与 QA 观测（20 路之一 500、全仓负载敏感、单包重跑绿）完全吻合。

**QA run-1「无服务端 ERROR 行」的解释**: httpapi harness 的 logger 是内存捕获型（`newCapturingLogger`，harness_test.go:147），服务端 ERROR 根本不会进 `go test` 输出——该负证据无效，非「无日志」而是「日志被捕获不可见」。

## 2. 三假设排除（step 2）

| 假设 | 判定 | 证据 |
|---|---|---|
| a) busy_timeout 耗尽 | **成立（主根因）** | 上述 ERROR 原文 + duration 13.7s > 5s 预算。机制: WAL 单写者持锁期间被调度饥饿（race + 16 核被 12 个测试二进制过订阅；argon2 64MiB×p=4 每请求验证放大 CPU 压力；storage/fsync 风暴叠加），等待者 5s busy_timeout 烧穿。T-10 定 5000ms 时未考虑全仓并行 race 负载。 |
| b) 错误映射 | **成立（次因，一并修）** | busy 类瞬时错误落 `writeBlobCreated`/`writeStoreFailure` 的 default → 500 UNKNOWN。T-38 已为 storage.ErrEngineClosed 建 503 UNAVAILABLE 先例（同属「客户端应重试」类），busy 应同类。spec（docker-registry.md）对 503 无明确规定——置信度中，按 T-38 既有先例处理并在测试中固化。 |
| c) harness 数据目录/端口冲突 | **不成立** | 每测试独立 `t.TempDir()` + 独立 httptest 端口；复现时同目录无第二实例。真正的 harness 问题是取证盲区（body 丢弃 + logger 捕获），非冲突。 |

## 3. 最小修复（step 3）

### 3.1 busy_timeout 5000 → 15000（`internal/metadata/store.go`）

- `BusyTimeoutMs = 15000` 导出常量（DSN、`setupSQLite` 断言、三处测试断言统一引用）。
- 依据: 观测到的最坏停顿 ~14s 持锁跨度，15s 覆盖且有裕量。等待不会死锁: 现有事务无「读升级写」形态（每个 tx 首句即写），等待者等的是有限持有者。
- 复测: 修复后同等压力（GOMAXPROCS=2 + 双 race 配重）8/8 轮全绿，且 8×20 路全程零非 201——busy 全被 15s 预算吸收，连 503 都未触发。

### 3.2 busy 分类 + 映射 503（`internal/metadata/{api,store,substores}.go`、`internal/adapter/docker/{uploads,manifest}.go`）

- metadata: 类型化 `isSQLiteBusy`（`*sqlite.Error` 的 `Code() == SQLITE_BUSY/LOCKED`，非字符串匹配）；`ErrStoreBusy` 哨兵在 `wrapExec` 附着（`%w` 双包，穿透 repo/service 的再包装链）；导出 `IsStoreBusy(err)`。
- adapter/docker: 三处映射——
  - `writeStoreFailure`: busy → 503 UNAVAILABLE + `Retry-After: 1`，日志降 **WARN**（T-41 口径: ERROR 计数=真故障，限流不是故障）；engine-closed 维持 T-38 的 503 不加 Retry-After；其余维持 500 UNKNOWN。
  - `writeBlobCreated`（**F1 的事故点**）: 注册 busy → 503 + Retry-After + digest detail，文案保留「safe to retry」。
  - `writeManifestPutError`: manifest 发布面同负载暴露（20 路 PutTag/PutManifest/PutRefs），busy → 503 + Retry-After + WARN。
- token 面的 issuance 500 映射**未动**（T-37 在途票领域，见遗留）。

### 3.3 第二根因: `anonSeedOnce` 进程级缓存（`internal/adapter/docker/{anonseed,api,token}.go`）

- 现象: `go test -race -count=5` 下 `TestV2TokenAnonymousBothModes` FAIL（run-1 全仓复现）；隔离 `-count=20` **19/20 FAIL**（首轮必过、后续全挂）——非负载 flake，是 `-count>1` 暴露的确定性隔离缺陷，历史口径（count=1）永远不可见。
- 机制: `anonSeedOnce` 是包级 `sync.Once`。count 迭代 2+ 的 harness 换了全新 SQLite，once 直接返回迭代 1 的缓存 nil（不再对新库种 `_docker_anonymous`），`tokens.Issue` 在新库查无主体 → 500「token issuance failed」。其代码注释自称「failed seed 会在后续装配经 direct call 重试」——该 direct call 并不存在。
- 修复: 去重状态移到 Handler（`anonSeedMu sync.Mutex` + `anonSeeded bool`，生产不变量=一个 handler 一个 store 一次种子）；**失败不缓存**（下一个请求重试，瞬时库错自愈）——顺带兑现了原注释声称的语义。token.go 仅一行调用点改动（`h.seedAnonymousOnce(...)`），已注意与 T-37 在途 diff 的合并（改行不在其 hunks 内）。

### 3.4 取证补强（`internal/httpapi/docker_manifest_test.go`）

- F1 测试的 layer 失败分支原样 `drain` 丢弃 body → 补为读出 body 拼进失败消息（今后任何复发自带 spec 错误体自诊断）。临时诊断测试用完已删（其取证价值折入此处与两个新回归测试）。

### 3.5 新增回归测试

- `internal/metadata/busy_test.go`: 真驱动 SQLITE_BUSY（EXCLUSIVE 锁 + busy_timeout=0 对打）→ 类型分类、wrapExec 哨兵、跨包装链 IsStoreBusy、非 busy 不误报。
- `internal/adapter/docker/errors_test.go`: `writeStoreFailure` 三态（busy→503+Retry-After / engine-closed→503 无 Retry-After / 普通→500 UNKNOWN）+ `writeBlobCreated` busy 臂（经真实 `registerBlobNode` 缝注入）。
- `internal/adapter/docker/anonseed_test.go`: per-handler 隔离、成功缓存、失败重试自愈、nil store。

### 3.6 附带修复（第三根因）: `TestSingleflightExecutesOnce` 死锁挂死（`internal/storage/concurrency_test.go`，harness 类）

- 现象: 定论 RUN-2 中 storage 包 40m 超时（2406s; RUN-1 同代码 707s 绿）——`TestSingleflightExecutesOnce` 挂死 33m54s，goroutine 栈: 测试主协程 `wg.Wait()` + 一个 waiter 卡在 `singleflight.do` 的 `chan receive`（fn 内 `<-started`）。
- 机制: 原测试的 leader fn **drain 到达通道**，依赖「64 个 goroutine 全部并入首个 flight」。singleflight 只合并**已进入 do()** 的并发者——某 goroutine 在「已发送 announce、未进 do()」窗口被调度走，leader fn drain 完毕返回、flight 拆除，迟到者成为第二个 leader，其 fn 去 drain 一个永远无人再发的 channel → 永久挂死。与负载强相关（-race + 过订阅），与我方改动无关（storage 包不依赖 metadata），但毒化 `-count=5` 全仓定论口径（count=1 下窗口极小，历史从未触发）。
- 修复（保持断言意图，挂死确定性消除）: 到达计数改由测试主体做（n 个 announce 全部落 buffer 后才开 gate，任一 do() 未启动）；leader fn 改为持 flight 等 `release`；gate 开启后给 100ms 合并窗口再 release。fn 内不再有任何可能缺发送方的 channel 接收 → 结构上不可再挂死。`-run 'TestSingleflight|TestConcurrent' -count=20` 绿（82s）。
- 归属说明: storage 包非本票 area，但派单明示「根因在别处（如 harness）则只修 harness」——此为纯测试文件修复（不动 singleflight.go 生产码），归此授权。

## 6. 遗留 / 上游确认

1. **token 面 busy 映射归 T-37**（其票在途且 owns token.go）: `serveToken` 的 issuance 失败现渲染 500 `invalid_request`「token issuance failed」，若 tokens.Issue 遇 busy 类应同样 503；metadata.IsStoreBusy 已就绪可直接复用。
2. **writable 持锁时长可再压**: WAL + `synchronous=NORMAL` 能大幅降低 commit 持锁（fsync 不再逐 commit），但属持久性语义变更（断电可丢最后若干事务），应由 architect 评估 ADR-0007 后另票处理，本票不动。
3. **`-count=5` 全仓口径的 10m 默认超时不可达**（storage 结构性 16m）: 建议 Makefile/CI 若采用 count>1 口径须显式 `-timeout`；或 conductor 认可 40m 调整为定论口径。
4. **harness 捕获型 logger 的取证盲区**: 建议后续票在 `t.Verbose()` 或环境开关下把捕获行回放进测试失败输出（本票仅修了 body 丢弃一维）。
5. PRD 侧无涉（行为对齐 T-38 既有 503 先例 + HTTP 语义，非 Artifactory 对照项）。

## 7. 规格依据

- docs/reverse/docker-registry.md: 错误体 schema（errors[]/code/message/detail）与 UNAVAILABLE 码使用（T-38 框架）；503/Retry-After 无 spec 条目——置信度中，按「实现并在测试中固化」处理（errors_test.go 三态）。
- ADR-0007（SQLite 并发预算）、ADR-0006（blob-first 次序——busy 失败后的重试安全性依赖它）、T-41（ERROR 计数卫生 → busy 降 WARN）。
