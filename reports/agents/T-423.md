## 1. 机制与变更

### 1.1 根因（复现实证）

T-377 D1 的 `SQLITE_BUSY` 逃逸发生在**remote 缓存填充写链的元数据行写**上：每个拉取对象落 6 行元数据（storage 引擎内 upload_sessions 的 create+set-state 对、blob/node/cache-state 三个 upsert；registry-v2 面再加 manifest/tag/refs 行）。24 路并发风暴下（WAL checkpoint + fsync-per-commit 纪元），不走运的等待者在 store 自身 busy_timeout（15s，T-54）内抢不到写锁，逃逸成 `ErrStoreBusy` → 500。本机复现还暴露了 D1 未记录的**级联放大**：Append 的 set-state busy 失败被误标为 `errUpstreamBody`（上游体读故障）→ 仓被误标 assumed-offline 300s → 3 次 busy 逃逸放大成 9569 个假 404。

### 1.2 修复：store 之上的二次机会预算（busy retry budget）

`internal/storage/busy.go`（新）：`RetryOnBusy` + `BusyRetryPolicy` + `DefaultBusyRetry`（**4 次总执行（首试+3 次重试）、退避 250ms 指数倍增至 1s 封顶**）。契约：仅 busy-class（`metadata.ErrStoreBusy`）重试；非 busy 错误单次即返；调用方 ctx 取消即止（不替已走客户端付费）；预算耗尽返回最后一个 busy 错误（T-54 的 retryable 分类 intact）；每次重试 WARN 一行（机制可观测）。被包裹操作必须是幂等行写（upsert 或失败自清理的 create）——全部点位满足。退避的错峰本身也稀释了雷群同步。

接线（全部缓存填充写路径）：
- `internal/storage/engine.go`：BeginSession 的 upload_sessions 行 create 重试（**D1 的原发位点**；Options 增 BusyRetry 旋钮）。
- `internal/storage/session.go`：Append 的 set-state 状态持久重试（数据字节已落盘，簿记失败不再毒化会话）。
- `internal/storage/s3.go`：S3 臂行 create 同式重试（S3EngineOptions.BusyRetry）。
- `internal/remote/fetcher.go`：land() 的 blob/node/cache-state 三个 upsert + 负缓存 PutCache 走预算（EngineOptions.BusyRetry）；**Append busy 诚实性修正**——busy 类失败不再裹 `errUpstreamBody`、不再误标 assumed-offline（上游无辜）。
- `internal/repo/dockerremote.go`（area 外延，见 §6）：registry-v2（helmoci/docker）面的落地链 `landRemoteV2Core` 三 upsert、`cacheRemoteMissCore`、`recordRemoteManifestCore`（manifest/tag/refs）同式包裹——该面正是 T-377 D1 的原始现场，与 generic 面共用 storage 级会话行修复。

### 1.3 metadata 面零改动（architect 会签姿势）

`BusyTimeoutMs=15000`、DSN pragma、`wrapExec`/`ErrStoreBusy` 语义全部未动——store 契约不变，无正式会签触发。依据：ADR-0007 勘误明文「1000 并发验收若出现 SQLITE_BUSY 热点，升级到读写双池属允许的实现内优化（不改本决策）」——本修复比双池更保守（连接池形态不变，仅在其上加应用层重试预算），落在同一「实现内优化」许可带内。
