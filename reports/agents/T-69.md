## 显式决策（票内要求）

1. **N4 严格 404（T-63 review 转入）**：挂载拼写被 T-63 重写缝抹除、行级 package_type 决定分发——这是 T-63 自己钉死的契约（其 seam 测试断言 /api/pypi 拼写→npm 仓也路由到 npm handler）。npm 侧可实施且已实施的严格面：Handler 收到的任何请求若 repo 行 package_type != npm → 严格 404（"not an npm repository"，ClassReader 守卫，httpapi 分发已保证的前提下为纵深防御）；npm 命名空间内未识别路径（search/security/attestations/_external/-/all/.npm/** 等）一律 E-26 严格 404，绝不落入类 generic 行为。
2. **-rev PUT「假成功」与 npm 10 现实的调和（规格 §5 开放项的实测收口）**：libnpmpublish 10.9.8（本机实测源码 lib/unpublish.js）单版本 unpublish 的第一步就是 PUT `/<name>/-rev/<rev>` 且 body 为**去掉该版本的完整 packument**——若按规格字面"服务端不做事"，M27 必失败。实现：-rev PUT **恒 200 `{"ok":"updated package"}`**；body 为含 versions 的 JSON 对象时应用之（tarball 引用归一化回相对路径，存储保持协议中立）；body 为其它形态（M27-AC11 的占位字符串）零副作用。占位断言（200 + 包内容无变化）与 npm 真流程（版本确实移除）双测试钉死。
3. **M26 curl 探针的分支落位**：PRD M26 的 curl 直打（GET packument 回 PUT）body 无 _attachments——十步链按序会落 step7 400。实现为：deprecate 臂之后、step7 之前检查 body 声明的版本是否已存在（存在 → 403 `Cannot modify pre-existing version`）。效果：M26 探针 403 ✓、真新包无附件仍 400 ✓、`npm deprecate`（同形态+deprecated 标记）仍走 step6 201 ✓。
4. **integrity 比较按解码字节**：npm(ssri) 的 integrity 是**带 padding 的标准 base64**（实测捕获 publish 报文确证，含 `+`、`/`、`==`），非 base64url。比较改为解码四种 base64 变体后按字节比对（算法前缀必须 sha512）。
5. **login 与写 gate 的栈现实（T-63 review N4 注记的验证）**：全栈下 PUT 先过 httpapi 写 gate——匿名 login PUT 在 gate 处得标准 401 Basic challenge（不会到 adapter）；持 `_auth`（PRD M22c 等效凭据口径）或 Basic 时到达 handler → 201 + token。adapter 侧自足：principal 在则直接签发（body 指名他人 → 403），principal 缺席则校验 body 凭据（错 → 401），tokens 未装配 → 503。
6. **scoped tarball 文件名含斜杠段**：`@scope/pkg-1.0.0.tgz` 在 URL/storage 里是两段——route 解析把 `-` 之后（剥掉尾随 `-rev/<rev>` 对）的全部段 rejoin 为文件名，M25/M27 scoped 全链由真客户端验证。
