## 做了什么

### 1. 006 迁移（NB1）

`internal/metadata/migrations/sqlite/006_user_groups_username_index.sql`（新文件）：

```sql
CREATE INDEX idx_user_groups_username ON user_groups(username);
```

- **为什么**：`GroupsOfUser`（substores_console.go:169，`WHERE ug.username = ?`）在每次认证执行——fillGroups（internal/auth/groups.go:55）从 authenticator 与 token 两条路径逐请求富集 Principal.Groups。004 只给了 `PRIMARY KEY (group_id, username)`，group_id 打头，无法服务 username 单列查找 → 热路径全表扫。
- **命名**：`idx_user_groups_username`，对齐 `idx_tokens_user`/`idx_web_sessions_user` 的 `idx_<table>_<col>` 风格（T-97 草案③原名）。
- **幂等形态**：裸 `CREATE INDEX`、不带 `IF NOT EXISTS`——幂等性来自迁移器台账（ADR-0007：applied 版本跳过），与 001~005 全部先例一致；若误重放会以 "index already exists" 大声失败，是想要的失败模式。文件体内无事务语句（TestMigrationsHaveNoTransactionStatements 自动覆盖 006）。
- 004 文件头补了 3 行注释：声明该索引按勘误落在 006、迁移只追加勿回填 004（纯注释改动，台账只记版本不校验正文，无风险）。

### 2. EXPLAIN 前后对账（核心证据）

测试 `t115_user_groups_index_test.go` 用 `EXPLAIN QUERY PLAN` 固化 GroupsOfUser 的精确语句（与 substores_console.go 出货文本同构，仅空白不同；SQLite 计划细节以表别名渲染）：

| 形态 | 查询计划（实测） |
|---|---|
| pre-006（001..005，无索引） | `SCAN ug` + `SEARCH g USING INTEGER PRIMARY KEY (rowid=?)` + `USE TEMP B-TREE FOR ORDER BY` |
| post-006（索引就位） | `SEARCH ug USING INDEX idx_user_groups_username (username=?)` + `SEARCH g USING INTEGER PRIMARY KEY (rowid=?)` + `USE TEMP B-TREE FOR ORDER BY` |

`SCAN ug`（user_groups 全表扫）→ `SEARCH ug USING INDEX idx_user_groups_username (username=?)`，**热路径从全表扫变为索引定位**。两个方向都 pin 进测试断言（BEFTER 断言"无索引可用"，AFTER 断言"索引 seek 且无 SCAN"），`-v` 输出即对账记录（见下）。

### 4. 既有测试修复（迁移集演进的连带，本 area 内）

T-95 的 `usage_internal_test.go` 回放段用字面量 `DELETE FROM schema_migrations WHERE version = 5` 制造 005 待应用形态——**006 入集后 `MAX(version)=6`，005 不再 pending，回填被跳过**（实测 `legacy-a after backfill = 0, want 300`）。修复：回放改为清 `version >= 5` 台账行 + `DROP INDEX IF EXISTS idx_user_groups_username` + 清 repo_usage，使库真实回到 pre-005 形态（005、006 依次重放）。注释说明这是唯一必须显式点名 pre-005 切点的位置，其余版本引用全部动态走 `latestMigrationVersion()`（已核对：internal_test/snapshot_test/cmd backup 均动态，5→6 抬升无其他 collateral）。
