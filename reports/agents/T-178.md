## 做了什么

### 1. /readyz Secure bug（AC②）

`internal/httpapi/system.go`：

- 根因实证（独立探针程序，minio-go v7.3.0 module cache）：`minio.New` 要求 endpoint URL scheme 与 `Secure` 选项**一致**，不一致直接报错 `Endpoint url scheme "http" conflicts with the secure option`。原代码写死 `Secure: true`（注释称 minio-go 会按 scheme 处理——不实），http:// MinIO 端点在**客户端构造阶段**就失败 → /readyz 永久 503。
- 修复：新增 `secureFromEndpoint(endpoint)`——`://` 前缀按 scheme 判定（https→true，其它显式 scheme→false），无 scheme 保持 minio-go 的 TLS 默认（true）。`probeS3Storage` 改用该函数。
- 红绿验证：临时还原 `Secure: true` 后 `TestReadinessS3ProbeScheme` 两个 http 用例即以旧 bug 签名（"s3 client init … conflicts with the secure option"）转红，还原修复后转绿。

### 2. 服务端 S3 装配（AC①）

`cmd/binflow-server/main.go`（在 T-168 未提交改动之上做最小增量）：

- `openStack` 的存储装配抽为 `openStorageEngine(ctx, cfg, logger)`，按 `cfg.Storage.Backend` 分支：
  - disk（默认）：`storage.OpenEngine(dataDir, …)` 原行为不变（含启动会话清扫日志，磁盘路径错误文案逐字保留）。
  - s3：`openS3Engine` —— minio 客户端从 `cfg.Storage.S3` 构造（endpoint/region/bucket/access_key_id；secret 优先取 config.Load 解析进字段的 `SecretAccessKey`，为空回退 `os.Getenv(config.S3SecretEnvVar)`，两者皆空 fail-fast）；`UsePathStyle` 映射 `BucketLookupPath`；启动时 `BucketExists` 探测，bucket 不存在拒绝起服（OpenS3Engine 契约要求 bucket 已存在）；最终 `storage.OpenS3EngineWithClient` 装配，`BucketPrefix` 透传。
  - `storage.migration` 按 T-164 语义接线：`enabled && !completed` → 双写（disk+S3 两引擎 `storage.NewMigrationEngine` 包装）；`completed` 或未配置 → 纯 S3（completed 模式的 source of truth 就是 S3，不再包一层、不再开无用的 disk 引擎）；`enabled` 且 backend=disk → 拒绝起服（dual-write 的 S3 凭据只在 backend=s3 下被 config 校验，静默丢一半写入不可接受）。
- `newAssembledServer`：引擎为 `*storage.MigrationEngine` 时把 `Deps.Migration` 接上（迁移 REST 端点 GET/POST `/api/v1/storage/migration` 从 501 变可用）。
- **发现并修复一个上游缝**：`*storage.MigrationEngine.StatusView()` 返回具体类型 `*storage.MigrationStatusView`，而 `httpapi.MigrationStarter` 声明 `StatusView() any`——Go 方法集要求签名精确一致，直接类型断言**永远失败**（T-164 未做 cmd 装配所以从未暴露）。在 cmd 组合根加 `migrationStarter` 适配器（两方法原样转发，零行为），不动 storage/httpapi 的签名（跨区决策转 conductor）。
- 日志：s3 后端起服打 `s3 storage backend active`（bucket/endpoint/prefix）；双写打 `storage migration dual-write mode` + 磁盘清扫行；completed 打 `storage migration completed; s3 is the source of truth`。disk 路径日志不变。

### 3. 测试（AC③）

`internal/httpapi/system_s3_test.go`（package httpapi）：

- `TestSecureFromEndpoint`：8 用例表测 scheme→Secure 判定（http/https/大小写/无 scheme/空/非法 scheme）。
- `TestReadinessS3ProbeScheme`：内置 mock S3（HEAD bucket/PUT/DELETE 子集）+ 自签 TLS mock，表测三分支：http 活端点 → /readyz 200（修复本体）；http 缺 bucket → 503 含 "bucket does not exist"；https 端点 → 503 失败在 `s3 BucketExists`（证明客户端构造成功、真拨了 TLS），且断言不含旧 bug 签名 "conflicts with the secure option"。并断言 ready 分支真在 mock 桶里写过哨兵对象。
- `TestReadinessDiskProbeUnchanged`：disk 默认 /readyz 200 零回归。

`cmd/binflow-server/s3_stack_test.go`（package main）：

- 内置完整上传链 mock S3（bucket 探测、multipart begin/part/complete、copy、delete；解码 SigV4 streaming aws-chunked 帧——storage 包自己的 mock 靠 SigV2 凭据绕开这一点，生产客户端是 V4；complete 响应需含非空 `<Bucket>`，否则 minio-go 按内嵌 `<Error>` 解码）。
- `TestOpenStackS3BackendUploadsToBucket`：backend=s3 装配 → BeginSession/Append/Commit 全链上传 → blob 落桶（key=`blobs/<xx>/<sha>`，内容逐字节断言），且本地无 blobs/ 树；secret 仅经 `BINFLOW_STORAGE_S3_SECRET_ACCESS_KEY` 环境变量（env 腿实证）。
- `TestOpenStackS3Misconfigurations`：三负路径表测——secret 全缺（报文含 env 变量名）、bucket 不存在、migration.enabled+backend=disk 拒绝。
- `TestOpenStackMigrationDualWrite`：双写装配（引擎类型 `*storage.MigrationEngine`）→ 一次上传**同时**落盘（`storage.BlobPath` 文件内容断言）与落桶；`migrationStarter` 适配器满足 `httpapi.MigrationStarter` 且 `StatusView()` 返回 T-160 消费的 `*MigrationStatusView`（初始 idle）。
- `TestOpenStackMigrationCompletedS3Only`：completed → 不包 MigrationEngine、上传仅落桶、本地无 blobs/。
- `TestOpenStorageEngineDiskDefaultZeroRegression`：disk 默认分支经新选择器仍按文档路径落盘。
