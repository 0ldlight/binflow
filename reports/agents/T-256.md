## 一、五路径逐一自查表（ADR-0031「漏接为保守失败但逐一自查」）

| # | 路径 | 谁 acquire | 接线点 | release | 论证 |
|---|---|---|---|---|---|
| 1 | `Put/PutWithOptions`（流式上传） | 本路径 `commitBlob` 的 session Commit | `service.go` PutWithOptions：`putNode` 成功后 `releaseGCHold(committed.Sha256)` | ✅ 已接 | 引用已落库（node 行 + blobs 行）后才 release，满足 W-1 时序锚点；失败路径（quota 拒绝 / putNode 失败）**不 release**——blob 无引用、TTL 兜底回收，ADR 登记的保守方向 |
| 2 | `PutLandedBlob`（docker layer/config finalize、pypi 上传） | **调用方**（adapter）的 session Commit（同一请求内：uploads.go `writeBlobCreated` → Commit → `registerBlobNode` → PutLandedBlob——双 node 布局同请求建行的前提已按代码核实） | `service.go` PutLandedBlob：`putNode` 成功后 `releaseGCHold(ref.Sha256)` | ✅ 已接 | acquire 属 adapter 的 Commit、release 属知道元数据何时落库的 service——ADR 规定的 exact pairing；docker mount 走 PutFromBlob（见 #4）不在此列 |
| 3 | `PutManifest`（docker 第二步） | **无人**：manifest 体由 adapter step-1 `svc.Put` 落盘，该 Put 已按 #1 释放（<image>/blobs/<hex> node 行先于 PutManifest 存在）；layers 由更早的 PutLandedBlob 各自释放 | 不接线（godoc 注明前提：service 契约「body 先走 blob plane」，唯一 in-tree 调用方 docker/manifest.go:218→252 恒满足） | ⛔ 刻意不接 | holdSet 是 refcount 不是 owner-tagged：无 acquire 的 release 会剥掉并发 repush 同 digest 的在途 hold（重开 W-1）。漏 release 的保守方向在真漏时由 step-1 的释放兜住 |
| 4 | `PutFromBlob`（checksum deploy / docker mount / maven） | **无人**：本路径无 session Commit，引用的 blob 由更早调用落盘且已随其元数据释放 | 不接线（godoc 注明） | ⛔ 刻意不接 | 同 #3 的 refcount 论证；本路径的新鲜度保护 = mechanism A（apply 期 Live 复核见 node 行即跳过）。残留微窗（Live 查后、unlink 前落地引用）= T-255 已登记的 check-then-unlink 微秒级残窗类 |
| 5 | remote pull-through（`Engine.land`） | land() 自己的 session Commit | **接线在 repo 侧**：`service.go` getRemote——Fetch 成功且 `CacheState == remote.CacheMiss`（本调用确实落了新 blob）时 `releaseGCHold(res.Node.Sha256)`；HIT/STALE 不 release（避免剥并发 lander 的 refcount） | ✅ 已接 | land() 的 node 行在 Fetch 返回前已提交 ⇒ release 时序正确。**地理注记**：ADR/T-255 把第五路径列在 repo 名下，其代码实体在 internal/remote/fetcher.go（area 外）；在 getRemote（Fetch 返回 = 元数据已提交）接线的 happens-before 语义与在 land() 内逐行等价，且 HIT/STALE 门把 refcount-strip 场景（stale 拷贝 sha 与在途上传相同 bytes）一并关掉——零跨包改动 |

净效果：五路径中 3 个真 acquire 路径全部在「元数据事务提交后」释放；2 个无 acquire 路径刻意不释放并在 godoc 固化论证（乱接反而是缺陷）。

## 二、交付内容

### 1. repo 五路径 release（internal/repo/service.go）
见上表；`releaseGCHold` helper：空 sha / FolderMarkerSHA 短路；`ReleaseGCHold` 契约上不可失败，WARN 仅保未来实现可观测。

### 2. metadata `IsReferenced`（internal/metadata/api.go + store.go）
`Store.IsReferenced(ctx, sha256) (bool, error)`——单点存在性探测（`EXISTS(nodes) OR EXISTS(docker_refs)`，走 idx_nodes_blob / idx_docker_refs_blob），ADR-0031 mechanism A 的 Live 神谕。放聚合 Store（跨两个 sub-store 的语义）。测试 t256_isreferenced_test.go：node 半边 / docker 半边 / 双向翻转 / 未知 sha。

### 3. httpapi GC 调用面迁移 GCSweep + 删 legacy 调用面（internal/httpapi/system_gc.go）
- 消费侧 `GarbageCollector` 接口：`GC(cb)` → `GCSweep(storage.GCMarker)`——**legacy 形态的调用面就此删除**（t114 装饰器、t201 fake 同步迁移）。
- 真 marker `gcMarker`：Mark = liveChecksumSet（原样），Live = `metadata.IsReferenced` 单点。REST 面（serve 同进程）获得完整 W-2 闭合 + hold 集全保护——ADR 决策 4 的「--workers=1 解除前置」面。

### 4. serve.lock 跨进程门（cmd/binflow-server/servelock{,_unix,_windows}.go + main.go）
- serve 进程生命周期 flock `<data>/serve.lock`（unix flock / windows LockFileEx，与 datalock 同形态、**独立文件**——serve 不能占 .maintenance.lock 否则拒绝一切在线维护）；第二个 serve 同 data dir 启动即拒（§9 单实例的 pointed refusal）。
- CLI gate（§14.2-4 字面）：`--apply` 且显式 grace < 60s（`storage.MinGCHoldTTL`）且 serve 持锁 → 拒绝退出非 0，文案指 REST 面（POST /binflow/api/v1/system/gc——同进程享 hold 集）或停服窗口；dry-run 不拒 + K22 注记「candidates may over-report」；默认 grace 不受限。
- **新增 `--grace-seconds` flag**（中置信度裁量，已在测试固化）：--grace-days/--grace-hours 均为正整数（≥1h），§14.2-4 的「显式 grace < 60s」在原 flag 集下不可表达 = 死门。新增秒级 flag（正整数，胜过 hours/days——同「更精确者胜」规则）使 W24 CLI 菜谱可表达、gate 可测；additive，不改既有 flag 语义。

### 5. TTL 配置装配（internal/config + cmd）
`storage.gc_hold_ttl_seconds`：YAML + env（`BINFLOW_STORAGE__GC_HOLD_TTL_SECONDS`）+ Validate（0 = sentinel-default；负值拒；(0,60s) 拒启「下限 60s 拒启」）；装配进 disk / S3 / dual-write / CLI gc 四处 engine Options.GCHoldTTL / S3EngineOptions.GCHoldTTL。§8 已登记该键（无需文档改动）。

### 6. 压力 spec 进 CI（.github/workflows/ci.yml）
独立 step「GC concurrency stress (ADR-0031 §14.2-6)」：T-232 赛跑腿（storage 层 TestGCApplyRacingUploads… / TestGCInFlightUploadMidSweepHold / TestGCHoldRefcountSurvivesConcurrentDedup / TestGCHeldBlobSurvivesZeroGraceApply）+ 本票 repo 集成腿 TestRepoUploadsRacingZeroGraceSweep，`-race -count=3`，关键路径 Test 之后 Build 之前；step 注释写明 §14.5-5 顺序硬规则（T-268 解除 --workers=1 前必须在位，移除须与解除同变更集）。

### 7. repo 集成测试（internal/repo/gc_hold_wiring_test.go）
- TestPutReleasesGCHold：W24 菜谱（upload→删 node→grace=0 可收）+ 对照腿（裸 Commit 不 release ⇒ 不可收；release ⇒ 可收——证明断言能看见 held）。
- TestPutLandedBlobReleasesGCHold：adapter Commit + service finalize 的 acquire/release 配对。
- TestRemotePullThroughReleasesGCHold：MISS 落地即释放；HIT 不释放（refcount 保护腿）。
- TestRepoUploadsRacingZeroGraceSweep：4 上传者×8 blob（半共享 content 走 dedup refcount）+ 并发删 node 流（W-2 shaping）× 2 个 grace=0 apply hammer，不变量 = 幸存 node 的 blob 物理在场且**逐字节回读等于上传体**（t134 失败模式反置）。5 连跑零 flake（~3s/跑）。

## 四、规格置信度处理

- 高置信（ADR/§14.2 字面）：hold 生命周期、两道删除门、REST 响应形状零变、TTL 键、serve.lock 形态与拒启下限——直接实现。
- 中置信（测试固化）：① `--grace-seconds` flag——ADR 预设「CLI 显式 grace<60s」但既有 flag 集不可表达，裁量新增并 4 组矩阵测试钉死（echo/precedence×2/negative）；② getRemote 以 `CacheState==MISS` 为 release 门——ADR 未细到 cache-state 级，论证见自查表 #5。
- 无低置信项擅自定行为。

## 五、遗留

1. **storage 侧 legacy `Engine.GC` 方法体的物理删除**：生产调用面已全部迁移（全仓 `.GC(` 零非 storage 生产调用者），但接口方法 + 7 个 storage 测试文件仍在——internal/storage 属 dev-go-storage area，本票未越界删除；现在是一处机械改动（删 api.go/gc.go/s3.go/migration.go 的委托 + 测试换 GCSweep），建议随下一张 storage 票顺手收口，届时 ADR-0031 决策 3 字面（参数就地升级）完全达成。
2. `--grace-seconds` 是新增 CLI 表面：PRD 6.4 O3 flag 清单若被视作冻结契约，需 conductor/PM 追认（理由与形态见 §二.4；不加则 §14.2-4 的 CLI gate 为死代码）。
3. e2e 完整套件（--workers=1 下全量）未在本票全跑（非验收面；GC/governance/t134 相关面已跑绿）——T-268 解除并发时的全量 3 连绿是那边的验收。
4. 压力 spec 的 Playwright 形态（§14.2-6 原文「并行 docker push 流」）未入 CI：CI 现无浏览器 job（playwright.config 注明 QA 票落地）；Go 测试形态（T-255 storage 腿 + 本票 repo 集成腿）已按「或其 Go 测试形态」入关键路径。T-268 前若要补浏览器形态，需先有 e2e CI job。
