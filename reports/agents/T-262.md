## 1. 问题（T-249 遗留 2 的原始担忧）

T-249 把 packument 的「追加新版本」转换挪上 write 臂（`SkipOverwriteCheck`）后登记：`internal/replication/push_npm.go` 的合并写若以**非 admin principal** 运行，可能踩同一覆写臂——「其注释自称 merge 不整覆写，未在本票验证范围」。核心疑点：**引擎若以 Put 全量替换形态写目标 packument，T-249 追加判定会怎么裁决？**

## 2. 自查分析（先读后裁）

### 2.1 引擎的写面盘点（push_npm.go 全量）

引擎是 HTTP 客户端，**从不调用目标端 repo 层 API**（`Put`/`PutWithOptions`/`SkipOverwriteCheck` 选项全部由目标端 face 自选）。它只发三种请求：

| 面 | 函数 | 请求 | 目标端裁决链 |
|---|---|---|---|
| packument 读 | `fetchTargetPackument` | `GET /binflow/{repo}/{name}`（404=空文档） | 读面，无臂 |
| **发布面** | `publishNpmVersion` | `PUT /binflow/{repo}/{name}`，body=**单版本** publish 文档（`_attachments` 内联 tarball，`dist-tags:{}`） | `servePublish`→`publishWithTarball`：step3 write 检查（tarball 路径）→ step4 tarball 已存在则**无条件 403** → tarball `svc.Put`（新版本=新节点=无既有节点，覆写臂不触发）→ `savePackument(oldDoc, merged)`：**T-249 判定器**——追加 only → `SkipOverwriteCheck=true`（write 臂），否则严格 `Put`（DELETE 臂） |
| dist-tag 面 | `putNpmDistTag` | `PUT /binflow/{repo}/-/package/{name}/dist-tags/{tag}`，body=JSON-string 版本号 | 版本 manifest 不动 → 判定器追加 only → write 臂（spec §2.1：该面 403 族=无 write/annotate，从无 delete 要求） |

**关键事实**：push_npm.go 中不存在任何「整包 packument PUT」。合并发生在**目标端发布面内部**（`mergePublish` 逐版本折叠），引擎只交付目标所缺的单版本。T-249 遗留 2 预设的「Put 全量替换形态」在本平面**不成立**——这正是 T-195 D3 的设计裁定（文件头注释：引擎驱动与真实 npm 客户端**相同的**发布/dist-tag 面，无特权裸节点面）。

### 2.2 三场景推演表（对照 T-249 §2 判定表逐行推演）

源文档版本集 S，目标 packument 版本集 T，引擎 `missing = S − T`（按**版本字符串**求差，与数据无关）：

| # | 场景 | 引擎行为 | 目标端臂裁决 | 非 admin（read+write，**无 delete**）结果 |
|---|---|---|---|---|
| 1 | **目标无包**（T=∅） | GET 404 → S 全部 missing → 逐版本发单版本发布文档 | packument/tarball 均无既有节点 → 覆写臂**不触发**（repo-semantics §3：臂只对既有节点生效）；tag 面新建 → write 臂 | **通过**（全栈 phase 1 钉死） |
| 2 | **目标有包但仅缺新版本**（追加形态；T ⊂ S，T 侧版本 manifest 与源一致） | missing=S−T → 只发布缺失版本；tag 漂移走单 tag 面 | 服务端合并：old 的每个版本在 merged 中幸存且 manifest 逐字节不变 → `packumentAppendOnly=true` → **SkipOverwriteCheck → write 臂**（T-249 判定表第 1/2 行）；tarball 新节点 → write 臂 | **通过**。注：这是 T-247 P-1 的同一形态——**T-249 之前**此处对无 delete principal 必 403；本票证明修复天然覆盖复制引擎（全栈 phase 2 + deprecate 控制腿钉死） |
| 3 | **目标同版本数据不同**（真覆写；v∈T∩S 但 dist 摘要不同） | **引擎不发任何写**：v∉missing（版本字符串已在 T）→ 跳过；tag 若同指向则亦无漂移 → 仅 1 次 GET | **臂不可达**——引擎构造不出「改既有版本数据」的写（它只发 missing 版本的发布文档）；目标侧版本幸存（文件头注释明文 + ADR-0021 first-write-wins） | **无风险**（全栈 phase 3 钉死：双 task 成功、B 自有 tarball/shasum 原样，A 的字节从未落地） |
| 3' | 竞态臂：GET 与 PUT 之间目标先落了同版本 | 引擎发出发布文档 → 目标 step4 tarball 已存在 → **403「Cannot modify pre-existing version」**（§2.3 step 4，**无条件——admin 也 403**） | `classifyNpm`：403→`notRetryable`→**终态 failed task**，目标不动，不再发 tag PUT | 与 ADR-0021 推式冲突策略（first-write-wins：目标已存不同内容=终态冲突）一致（scripted 403 腿钉死：LastError 含 not-retryable 标记 + 403） |

### 2.3 裁定

**(a) 无风险——路径形态天然追加或全新，测试钉死现状。** 三层依据：

1. **形态层**：引擎对 packument 的唯一写路径是「目标所缺版本的单版本发布文档」，合并与豁免判定都在目标端；引擎永远不构造全量替换写。
2. **判定层**：引擎能发出的每种写，恰好全部落入 T-249 判定表的豁免行（追加新版本=write；dist-tag 移动=write；全新包=无臂）；会被判「维持 DELETE 臂」的形态（改既有版本 manifest）引擎造不出来，真造出来也会先被目标 step 4 的无条件 403 拦下（version immutability 在 tarball 层，先于权限臂）。
3. **策略层**：真覆写诉求（场景 3）被 missing-only 差集天然消解为目标版本幸存；竞态残余落入终态 403——两路都符合 ADR-0021 推式 first-write-wins，**不套用户覆写臂**（不存在「DELETE 臂拒掉合法镜像同步」或「反之误放行」的错配）。

不修复的理由：修复前提（引擎走全量替换形态）经查不成立；现状行为即复制语义的正确形态。

## 3. 规格依据（clean-room）

1. **docs/reverse/maven-npm-pypi.md §2.3 step 4**（置信度高）：tarball 路径已存在 → 403「Cannot modify pre-existing version」——版本不可变性落在 tarball 层且无条件（含 admin），场景 3'/3 的冲突闸门。
2. **docs/reverse/maven-npm-pypi.md §2.1**（置信度高）：`PUT /-/package/{name}/dist-tags/{tag}` 错误族=403 无 write/annotate，**无 delete 要求**——tag 面天然 write 臂。
3. **docs/reverse/maven-npm-pypi.md §2.2**：包级元数据是服务端维护的聚合文档（BinFlow 的 packument.json 节点为其存储形态）——引擎经发布面驱动它，与 T-249 的豁免粒度对齐。
4. **docs/reverse/repo-semantics.md §3**：覆写/DELETE 臂只对**既有节点**生效——场景 1 全新路径不触发。
5. **ADR-0021 决策 4（推式冲突，first-write-wins）**：目标已存不同内容 → 跳过/终态、目标不动。npm 平面的 missing-only 差集（常态）与 403 终态（竞态）是同一策略的两个实现位；engine.go 文件头 Q6/Q7 interim 注释与 T-162 报告的对账文字同源。
6. **T-249 判定表**（reports/agents/T-249.md §2）：追加=write、改既有=DELETE 臂、重发既有版本=无条件 403——本票逐行推演的基准。

低置信度处理：无（本票全部落点均在上述高置信度条款内；无新行为裁定）。
