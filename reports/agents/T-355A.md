## 1. D-5① forceConanAuthentication（T-340 AC1 尾段 / FR-110.2）

### 1.1 缺口机制（T-351 D-5 证据归因）

「字段 PUT 静默丢 / 匿名 ping 200」是三层各缺一块：

1. **httpapi typed transport 未携带字段**——`repoConfig` 是类型化传输结构，未声明的键在 `configJSON` 组装时丢弃（PUT 200、GET keyless）——与 T-329 D-E（helm enforce 对）完全同款；
2. **repo.validateLocalConfig 无类型门**——手拼 blob 畸形值静默存储；
3. **conan adapter 不消费**——匿名面照走普通内容 ACL。

### 1.2 实现

| 层 | 文件 | 改动 |
|---|---|---|
| 传输 | `internal/httpapi/repositories.go` | `ForceConanAuthentication *bool` 扁平指针字段（LOCAL 臂 `setBool`；显式 false 存活＝关闭往返可表达） |
| schema | `internal/repo/config.go` | `validateLocalConfig` probe 加 `ForceConanAuthentication *bool`（typing rides decode：畸形值 400 点名字段，byHash 同款姿态） |
| 消费 | `internal/adapter/conan/handler.go` | `classOf` 泛化为 `rowOf`（取整行——deb `configFor` 同一 ClassReader seam 先例）；`ServeHTTP` 在 class door 前加门：`p == nil && forceConanAuth(row.Config)` → **401 `unauthorized user` + `WWW-Authenticate: Basic realm="BinFlow Realm"`**（与 plane 既有 ErrUnauthorized 渲染同形），能力头族随行（规格 §2「每响应带头」含错误臂）；`forceConanAuth` 容错读（畸形 blob 读作 false，deb normalized() 姿态） |

语义边界（照 conan.md §2「匿名请求任意 conan 端点 → 401（v1/v2 数据端点逐端点断言）」逐字执行）：

- **ping 含在内**——客户端探测即遇 challenge＝「引导登录」（AC1 措辞）；真客户端腿实证（§5）；
- authenticate/check_credentials 自带凭据（p != nil）不受影响；
- **写动词匿名本就被 httpapi 匿名写门先拦**（JSON 信封 401——「写永不匿名」ADR-0009），到不了 adapter 门：测试对写臂只断状态、读臂断全形态（哪层拒绝是架构既定，非遗漏）；
- 门读 blob 于**所有 class**（local/remote/virtual）；REST 传输只落 LOCAL 臂（remote/virtual canonical 丢未知字段是既定设计——hand-seeded virtual 臂钉此契约）；
- 默认 false 维持（普通内容面 ACL：匿名读放行 / 写拒——`TestAnonymousWriteRefused` 姿态不变）。

## 2. D-5② cargo 409（T-340 AC2 / FR-110.4）——查证结论：**无行为缺口；补断言 + 记账修正案**

### 2.1 查证链（应派发单「查原文定形态」要求）

1. **reports/agents/T-340.md 全文未触及 cargo**——该票实际只承载了 AC1 前半（D-F packages/delete），AC1 尾段（forceConanAuthentication）与 AC2（cargo）双双零实现（T-351 D-5 判定对前者成立、对后者**不成立**，见下）。
2. **Artifactory cargo 表面唯一 409 语义＝CG-2 类 8**（remote search 上游异常 → `409 + errors 信封`；T-304 §3 表 Exception 臂）。**publish 面无 409**：T-304 D-3 取证 Artifactory 重复版本走 `isForbiddenOverwrite` → 401（匿名）/403（实名），有 d 权限→覆盖——「重复版本一律 409」的 CG-3 旧读法被终裁推翻（cargo.md §2/§5.3 as-built 2026-08-28：**无冲突臂**）。派发单所问「Artifactory cargo publish 的 409 语义在哪臂」答案：**不在 publish 臂，在 remote search 上游异常臂（类 8）**。
3. **该臂 BinFlow 自 T-316（commit ab080f9）起已实现并有测试**：`internal/adapter/cargo/remote.go` `serveRemoteSearch`——引擎 `StatusError ≥ 500` → `409 + errors 信封`（`TestRemoteSearchProxy` 死上游〔500 应答〕+ hardFail → 409 断言在案）。
4. **R-3/R-4 是登记分歧而非未实现**：cargo.md §8.1——R-3「默认姿态＝引擎 assumed-offline 收敛为 **404 unfound**（FR-20 全仓统一姿态优先，与 Artifactory 的 409 有登记分歧）；hardFail/超限 502 类 → 409（类 8 的硬错误臂）」；R-4「上游码透传受引擎映射约束（401/403/其余 4xx 折叠为 404 unfound）」。引擎侧映射核对（`internal/remote/fetcher.go` `mapTransportFault`/`downgrade`）：transport 故障（connection refused/reset/timeout——「真死上游」）→ markOffline → 无缓存副本 → hardFail ? 502 : 404-unfound。
5. **T-351 L24 判红是按 BOARD AC2 字面**（「死上游 search → 409」）——与规格自己的登记裁定冲突：QA 观察到的「404+errors 信封」恰是 R-3 登记姿态本体（默认仓、hardFail off）。**BOARD/PRD 记账矛盾，非代码缺口。**
